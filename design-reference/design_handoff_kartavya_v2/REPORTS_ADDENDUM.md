## What this section ships

### Three automated email reports

Sent by cron to **all admins + team owners** of every workspace.

| # | Cadence | Cron (IST) | Subject line                                | Excel filename                       |
|---|---------|-----------|---------------------------------------------|--------------------------------------|
| 6 | Daily   | weekdays 09:00 | `[Aekam] Daily report — Mon 18 May`     | `<slug>_daily_YYYY-MM-DD.xlsx`       |
| 7 | Weekly  | Mon 09:00 | `[Aekam] Weekly report — WK 20 (11–17 May)` | `<slug>_weekly_wkNN_YYYY.xlsx`       |
| 8 | Monthly | 1st 09:00 | `[Aekam] Monthly report — April 2026`       | `<slug>_monthly_YYYY-MM.xlsx`        |

Each email body contains: 4 KPI tiles (Completed / Due / Awaiting
approval / Overdue), a per-project breakdown table, a Champion call-out,
and an attachment row pointing at the same XLSX that is also actually
attached to the SES send. Weekly + monthly additionally render a
throughput bar chart; monthly adds a full leaderboard.

### In-app Generate Report screen

New route `/reports/generate`, sidebar item "Generate report" under
Operations (between Time Report and Templates).

Builder has 5 numbered blocks (Type → Projects → Team → Sections →
Delivery) and a sticky right column with a live preview of the cover
page, three export buttons (PDF / XLSX / CSV), and a recent-exports
history list.

### Generated PDF layout

5 letter-size pages (816 × 1056 @ 96dpi):
1. Cover + executive summary
2. Per-project breakdown
3. Champion + team leaderboard
4. Detailed task list
5. Throughput chart + methodology + colophon

PDF is generated server-side from a headless browser rendering the same
React components used in the in-app preview.

## On-demand cover — kind-aware

The cover (page 1) of an **on-demand** PDF must adapt to the report
`kind`. The automated cron always uses the weekly cover; the manual
Generate Report endpoint passes through the user's selected kind +
range and the renderer picks the matching component.

**Reference designs:** `report-pdf-covers.jsx` (`PdfCoverDaily`,
`PdfCoverWeeklyOnDemand`, `PdfCoverMonthly`, `PdfCoverCustom`) +
`report-pdf-covers.css`. Section "On-demand cover" in `Report PDF.html`.

| Kind     | Headline framing                       | KPI hint copy           | Extra cover module        | Generation stamp      |
|----------|----------------------------------------|-------------------------|---------------------------|-----------------------|
| daily    | Tactical: *"Today at Aekam — X done, Y left"* + live time | vs yesterday + 7-day avg | none — fits in stats grid | red `ON-DEMAND` badge |
| weekly   | *"A week of X closed tasks"* + WK number | WoW + 4-week avg        | 4-bar weekly sparkline    | red `ON-DEMAND` badge |
| monthly  | *"Month in review — X shipped"* + FY/Q tag | MoM + Q-to-date         | 4-bar weekly bars of the month | red `ON-DEMAND` badge |
| custom   | *"X days at Aekam — D1 to D2"*         | vs prior equivalent window | range-timeline rail with month-boundary marker | red `ON-DEMAND` badge |

**Stamp header** (top-right of every on-demand page, not just cover):
- Red `ON-DEMAND` chip (vs blue `AUTOMATED` chip on cron-sent reports)
- Kind label + Devanagari · `"Weekly report · साप्ताहिक"`
- Period text · `"WK 20 · 11–17 May 2026"`
- Duration line (custom only) · `"32 days · spans April + May"`

**Generated-by stamp** (above the colophon on the cover):
- `Generated by Keval Shah · Admin · on-demand · 18 May 2026 · 11:42 IST`

**Comparison baseline rules** (compute in `metrics.py`):

```python
def comparison_window(kind, start, end):
    if kind == 'daily':
        return [start - 1d, start - 1d]   # yesterday
    if kind == 'weekly':
        return [start - 7d, end - 7d]     # WK N-1
    if kind == 'monthly':
        return [start - 1mo, end - 1mo]   # previous calendar month
    if kind == 'custom':
        delta = end - start
        return [start - delta - 1d, start - 1d]   # prior equivalent window
```

The `delta_pct` on each KPI is computed from this baseline. Custom
range explicitly says "vs prior 32 days · 10 Mar – 10 Apr" so the user
isn't confused about whether it's a calendar comparison.

**Custom range timeline** — when the range spans 2+ calendar months,
render the timeline rail (`pdf-cv__rail`) with the boundary marker.
Pseudocode for which boundaries to surface:

```python
boundaries = []
d = start.replace(day=1) + 1mo
while d < end:
    boundaries.append(d)
    d = d + 1mo
# Render up to 3 boundary markers; if more, suppress middles and show "spans N months" instead.
```

**Acceptance:**
- All 4 cover variants render at 816×1056 with the right stamp + headline + comparison copy + extra module.
- Auto-cron weekly reports still use the blue AUTOMATED badge and the original `PdfCover` (with the executive summary block, not the trend sparkline).
- Custom range that spans only one month (e.g. 5–25 April) renders the timeline rail without a boundary marker.
- Daily on-demand can be regenerated mid-day — header time updates ("as of 14:32 IST · live"); two runs an hour apart produce different KPI values.

## Scale behaviour — project count thresholds

The same `ReportData` flows through email + PDF, but the **renderers
adapt** based on `len(data.projects)`. Implement these rules in BOTH
`render_xlsx`/email template AND `render_pdf` so they stay in lockstep.

| Count   | Email body                                                                | PDF page 2                                          |
|---------|---------------------------------------------------------------------------|-----------------------------------------------------|
| 1 – 8   | Full table (current `EmailWeeklyReport`)                                  | Full table with progress bars + callouts (`PdfProjects`) |
| 9 – 12  | Dense table (smaller rows, no Hindi subtitle column)                      | Dense table without progress bars (`PdfProjectsDense`)   |
| 13 – 24 | **Top 8 by activity + "Other (N)" roll-up row** (`EmailWeeklyReportScaled`) | Paginated: "Per-project (1 of N)" continuation pages (`PdfProjectsPaged1`, …) |
| 25+     | Same as 13–24 + body line "Open the XLSX for the full list"               | Adds a 1-page **Movers snapshot** in front (`PdfMovers`) |

**Implementation:**

```python
def select_email_template(n_projects: int) -> str:
    if n_projects <= 8:  return 'reports/weekly_full'
    if n_projects <= 12: return 'reports/weekly_dense'
    return 'reports/weekly_scaled'   # top-8 + rollup
```

```python
def build_pdf_pages(data: ReportData) -> list[ComponentName]:
    pages = ['cover']
    n = len(data.projects)
    if n >= 25:
        pages.append('movers')
    if n <= 8:
        pages.append('projects_full')
    elif n <= 12:
        pages.append('projects_dense')
    else:
        # paginate dense table — 12 per page
        for i in range(0, n, 12):
            pages.append(('projects_paged', i, i + 12))
    pages.extend(['team', 'tasks', 'trend'])
    return pages
```

**Ranking for "top 8 by activity"** = `completed + 0.5 * due + 0.3 * awaiting`.
Ties broken by `name` ASC (stable). Roll-up sums the remaining
projects' counts; roll-up label is "+ N other projects" with the first
6 dot-colors as bullets and the first 6 names as a hint string.

**Reference designs:**
- Email scaled: `EmailWeeklyReportScaled` in `email-reports-scale.jsx`
- PDF dense:    `PdfProjectsDense`   in `report-pdf-scale.jsx`
- PDF paged:    `PdfProjectsPaged1`  in `report-pdf-scale.jsx`
- PDF movers:   `PdfMovers`          in `report-pdf-scale.jsx`

All four artboards live in `Email System.html` (section "Reports at
scale") and `Report PDF.html` (section "At scale").

**Acceptance for scale rules:**
- Render weekly report with 1, 8, 9, 12, 13, 24, 25, 60 projects — each falls into the right template branch.
- 60-project XLSX still opens cleanly (no merged cells, no truncation).
- Movers snapshot shows top 3 + watch-list 3, sorted by the activity / overdue heuristics in `champion.py`.
- Paginated PDF: page numbers in the header read "Per-project (1 of 2)", "Per-project (2 of 2)" with continuation arrow in the footer of page 1.

### R1. feat(backend): report metrics service

Pure-Python module that computes everything the reports need. No HTTP,
no email, no rendering — just SQL → typed dict. Must be re-callable for
arbitrary date ranges so daily / weekly / monthly / custom all share one
implementation.

- New: `backend/services/reports/metrics.py`
- New: `backend/services/reports/champion.py`
- New: `backend/tests/services/reports/test_metrics.py`
- New: `backend/tests/services/reports/test_champion.py`

**Public API:**

```python
def build_report(
    workspace_id: UUID,
    period_start: date,
    period_end: date,
    project_ids: list[UUID] | None = None,   # None = all active
    user_ids:    list[UUID] | None = None,   # None = all non-client members
    sections: ReportSections = ReportSections.DEFAULTS,
) -> ReportData: ...
```

`ReportData` is a frozen dataclass with these fields (all needed by both
the email templates and the PDF renderer):

- `period`: `{start, end, kind: "daily"|"weekly"|"monthly"|"custom", label}`
- `scope`:  `{workspace, project_count, project_total, member_count, member_total}`
- `kpis`:   `{completed, due, awaiting, overdue, completed_delta_pct, overdue_delta}`
- `projects`: list of `{id, name, sanskrit, color, completed, due, awaiting, overdue, progress_pct}`
- `champion`: `{user_id, name, role, completed, approvals, focus_minutes, narrative}`
- `leaderboard`: list of `{user_id, name, role, completed, score}` sorted desc
- `throughput`: list of `{date, completed, approvals}` (one entry per day for daily/weekly, per week for monthly)
- `tasks`: list of all tasks touched in the period, with `{id, title, project, priority, assignees, due, status, time_actual_min, time_estimate_min}`
- `approvals_summary`: `{cleared, median_minutes, oldest_open_hours}`
- `cycle_time_days`: float

**Counting rules** (must match what the PDF page 5 methodology box claims):

- **Completed** = tasks moved to `done` column with `done_at` inside the period
- **Due**       = tasks with `due_date` inside the period (regardless of status)
- **Awaiting**  = currently in `in_review` column at end of period (uses live state on the period_end date)
- **Overdue**   = `!done AND due_date < period_end`
- **Approvals** = audit-log rows with `action='approve'` AND `entity_type IN ('task_request','work_review')`
- **Cycle time** = mean of `(done_at - created_at)` in days for tasks completed in the period

**Champion score** (`champion.py`):

```
score = completed * 1.0
      + approvals * 1.5
      + on_time_count * 1.2
tie-breaker: focus_minutes desc, then user.created_at asc (stable)
```

`on_time_count` = completed tasks where `done_at <= due_date`.

**Acceptance:**
- `pytest backend/tests/services/reports/` green
- Seed a workspace with the fixture in `backend/tests/fixtures/reports_seed.sql` (5 projects, 6 members, 50 tasks, 38 approvals) — `build_report` for WK 20 returns the numbers in the prototype's `email-reports.jsx` `EmailWeeklyReport` (Completed=50, Overdue=8, Champion=Priya Iyer with 12).

### R4. feat(backend): report endpoints + cron

REST surface for the in-app Generate page and the schedulers.

- New: `backend/api/reports.py` — registers under `/api/reports/*`
- New: `backend/cron/reports_daily.py`, `reports_weekly.py`, `reports_monthly.py`

**Endpoints (admin or team-owner only — gate via `requires_role(['admin','owner'])`):**

| Method | Path                              | Body / Query                                                  | Returns |
|--------|-----------------------------------|---------------------------------------------------------------|---------|
| POST   | `/api/reports/generate`           | `{kind, from, to, project_ids[], user_ids[], sections{}, formats[] = ['pdf'\|'xlsx'\|'csv'], deliver: 'download'\|'email', recipients[]}` | `{job_id}` |
| GET    | `/api/reports/jobs/:job_id`       | —                                                             | `{status, files: [{format, filename, size_bytes, signed_url}]}` |
| GET    | `/api/reports/history?limit=20`   | —                                                             | `[{id, kind, formats, generated_at, generated_by, files: [...]}]` |
| GET    | `/api/reports/schedules`          | —                                                             | `{daily: {enabled, recipients[]}, weekly: {...}, monthly: {...}}` |
| PATCH  | `/api/reports/schedules`          | partial `{daily?, weekly?, monthly?}`                         | echoes new state |

Generation is async — `POST /generate` enqueues a job (Celery/RQ — use
whichever the codebase already uses) and returns immediately. Frontend
polls `/jobs/:job_id` every 1.5s until `status == 'done'`. Typical job
completes in 1.5–4s.

**Cron handlers** all share one entry point:

```python
def run_scheduled_report(kind: Literal['daily','weekly','monthly']) -> None:
    for ws in list_workspaces_with_reports_enabled(kind):
        data = build_report(ws.id, *period_for(kind))
        files = render_all(data, formats=['xlsx'])    # email default = xlsx only
        urls  = [upload_to_r2(f) for f in files]
        recipients = resolve_recipients(ws, kind)     # admins + team owners
        send_report_email(ws, kind, data, files, urls, recipients)
```

**Acceptance:**
- `POST /api/reports/generate` with valid body returns job_id in <100ms.
- Job completes within 5s for a workspace of ≤200 tasks.
- Member or client role calling any endpoint → 403.
- Cron runs in staging deliver actual emails to a test admin inbox.
