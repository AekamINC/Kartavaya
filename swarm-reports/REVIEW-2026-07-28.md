## 1 · Security findings, severity-ordered

### 1.1 — HIGH — Ganit separated-duty check has a live bypass until PROPOSED_074 lands
`middleware/module_levels.py:182-205` gates the Ganit `approver` rung
(cancel-invoice, pay-vendor-bill — `routers/ganit.py:604,1887`) through
`staging.org_module_approvers`, a table that doesn't exist yet
(`PROPOSED_074_module_approvers.sql`, unapplied). While it's absent, the
function **falls back to `if await _org_role(...): return`**
(`module_levels.py:188-190`) — meaning today, on Ganit specifically, an
`org_owner`/`org_admin` satisfies the approver check with no explicit grant,
which is exactly the case separated duty exists to prevent ("admin must NOT
satisfy approver on vetana/ganit"). This is a documented, deliberate stopgap
(the comment explains it exists so Ganit doesn't lock every org out of paying
vendors), not an oversight — but it means the rule is not actually enforced for
this module today.
*Vetana's equivalent enforcement IS live and correct* — `routers/vetana.py`
reads real `org_member_modules.role='approver'` rows, and
`PROPOSED_071_vetana_approver_backfill.sql` has already been applied (confirmed
via `role_tiers.py` comments recording the live check: both orgs with Vetana
active hold a real approver row). Payroll approval is not broken.
**Verified**: read `module_levels.py:182-205`, `ganit.py:46,604,1887`,
`role_tiers.py:306-324` (`level_satisfies` correctly refuses admin at the
approver rung for both modules — the bug is the fallback, not the rule).
**Decision-gated**: fix is to apply `PROPOSED_074`; not something to patch
around in code without the owner choosing the approver-grant model (see §7).

### 1.2 — HIGH — Ganit contract signing links still 404 in practice
`services/esign_service.py:104` mints signer tokens for
`staging.ganit_contract_signers`, and the backend now has a correct handler for
them at `routers/ganit.py:1293-1354` (`/api/v1/ganit/sign/{token}` +
`/otp`/`/verify`/`/submit`). But the one public page every signer link actually
points at, `frontend/src/pages/SigningPage.jsx` (route `/sign/:token`,
`App.jsx:137`), unconditionally calls `/v1/esign/verify/${token}` — which looks
the token up only in `staging.sign_signers` (`routers/esign.py:322-336`) — with
no detection or fallback to the Ganit path. Every Ganit contract signer still
gets the page's generic "This doesn't exist, or it was deleted." Two
independent review lenses (security-ledger verification, design-conformance
batch 3) confirmed this against current code and found no fixing commit for
either file. **Not fixed this session** — see §7; the two candidate fixes
(teach `SigningPage` both protocols, or unify the token namespace) are an
architectural choice, and this flow is public-facing with legal weight
(IT Act 2000 e-sign), so it needs a tested fix, not a patch made without a
browser.

### 1.3 — MEDIUM — Signing order (`sign_order`) is stored but never enforced
`routers/esign.py:493-566` (`POST /verify/{token}/sign`) checks only that the
individual signer's own status is `pending`, the document isn't
cancelled/expired, and OTP is verified — it never checks whether earlier
signers in `sign_order` have signed yet. Signer 3 can sign before signer 1.
Same gap in the Ganit path (`esign_service.py` never references `sign_order`
at all). **Verified**: grepped every reference to `sign_order` in both files —
only used in `ORDER BY` (listing) and on insert, never as a gate.
**Not fixed this session** — enforcing it is a straightforward change in
isolation, but this is the same public signing flow as §1.2, already carrying
one open architectural question, and both should be fixed and tested together
rather than in two separate uncoordinated patches this close to handover.

### 1.4 — MEDIUM — E-sign completion produces no signed document, so a signature is repudiable
`_generate_signed_certificate` (`esign.py:698-752`) uploads and hashes a JSON
certificate, not a signed PDF — no signed document exists anywhere, and no
completion email is ever sent to the counterparty (confirmed: no email call
anywhere after line 559). A dispute has nothing durable to point to.
**Verified**: read the full function, confirmed no PDF-generation or email
call exists on the completion path. **Decision item** — this needs a product
call on what "signed document" means for the flow (render + stamp the original
PDF? attach the JSON cert as an appendix? both?), not a five-minute fix.

### 1.5 — MEDIUM — `apply_project_template` has no ownership check (NEW finding)
`routers/templates.py:103-146` — creating/deleting a project template checks
`created_by`; **applying** one (`POST /projects/{template_id}/apply`) does not.
Any authenticated user who knows or guesses a `template_id` (`ptmpl_<10 hex>`,
~40 bits) can pull another organisation's template config — column names,
custom fields, and sample task titles/descriptions — into their own team.
`project_templates` carries no `org_id` at all; `PROPOSED_076_org_id_add_
nullable.sql:102-103,112` already documents this table as a deliberate "global
pool" pending a product decision on whether it should be. So the inconsistency
here isn't `apply`'s omission alone — `list_project_templates` (which *does*
restrict non-staff to their own `created_by` rows) contradicts a "templates are
global" reading, and `apply`'s omission contradicts a "templates are private"
reading. Both can't be right at once.
**Verified**: read `templates.py` in full; cross-checked against
`PROPOSED_076:100-113`. **Not fixed** — needs the owner's call on the data
model (see §7) before either endpoint's behaviour can be called correct.

### 1.6 — LOW — `org_admin` bypasses `require_module`'s grant check entirely
`middleware/subscription.py:146-155` — `org_owner`/`org_admin` skip the
per-user grant/level block completely (deliberate, per
`role_tiers.py:74-78`'s `ORG_MANAGEMENT_ROLES` comment), so nothing currently
limits which modules an org_admin can reach even though the settled Tier-2 rule
is "org_owner decides which modules an org_admin can reach." This was already
on the owner's decision list in `_STATE-2026-07-27.md` §4 item 5 — confirmed
still open, not re-litigating it as new.
**Verified**: read `subscription.py:146-191` directly — the write-level
enforcement added for the viewer-write fix (see §1 fixed-list) only applies
inside `if not org_role:`, so it doesn't touch this path either.

### 1.7 — LOW — Pahchan's declared self-scope is unreachable
`role_tiers.SELF_SCOPED_MODULES = {vetana, manav, pahchan}`, but
`routers/pahchan.py:47` gates on plain `require_module("pahchan")`, not
`require_module_or_self`. An employee with no grant row is refused by the gate
before the self-lookup logic at `/me` (`pahchan.py:484-523`) ever runs — Manav
and Vetana both correctly use `require_module_or_self` and work as intended.
**Verified**: read `pahchan.py:47`, `manav.py:33`, `vetana.py:36` side by side,
and `role_tiers.require_module_or_self` (`role_tiers.py:492-575`).
**Not fixed this session, deliberately** — this is not a one-line gate swap.
`_gate` is shared by every route in the file (roster, review, admin settings),
not just `/me`; swapping it globally would admit self-scoped (ungranted)
callers to routes that were never audited to filter down to "your own row
only," which risks trading a false-refusal bug for a real cross-employee data
leak. The correct fix mirrors `manav.py`'s pattern — a route-by-route audit,
not a blanket swap — and needs to be checked live, which this pass can't do.

### 1.8 — LOW — No live RLS enforcement in either schema (documented, not independently re-verified)

## 2 · Bugs

### B1 — FIXED, confirmed — viewer could write on 210/234 module-gated routes
`middleware/subscription.py:169-191`, commit `16d3d45`. Now reads the actual
grant level and requires `level_satisfies(held, EDITOR, module_code)` for write
requests. Caveat: only applies inside the `org_member` branch — see §1.6,
org_admin still bypasses it, which is the same underlying gap, not a new one.

### B2 — Python 3.11 vs 3.13 syntax gap is a sandbox artifact, not a product bug
Running `pytest` under this sandbox's default Python (3.11.15) fails
collection outright:
`SyntaxError: f-string expression part cannot include a backslash` in
`services/doc_render.py:443` and `email_service.py:1173`. This is PEP 701 —
Python <3.12 forbids a backslash inside an f-string's expression part; 3.12+
allows it. **`backend/Dockerfile:1` pins `python:3.13-slim`**, which is what
Railway actually runs, and 3.13 has no issue with this code. Confirmed by
building a matching 3.13 venv and running the full suite clean (§4). Not a
finding against the product — worth recording so the next person who hits this
in a different sandbox doesn't mistake it for a regression.

### B3 — graha_web_forms.auto_assign_to has the same UUID/TEXT mismatch as the three columns PROPOSED_083 already documents
See §4 (new-tables check) and §6 (what I fixed — added it to the proposal).

### B4 — `escalation_chain.py` ticket lookup has no org_id filter, but is unreachable
`services/skills/action/escalation_chain.py:31-33` — `SELECT ... WHERE
id=$1::uuid` on the entity table, no `org_id` predicate. Confirmed via grep
that `escalate()` is imported nowhere and called nowhere in the backend — this
is dead/unwired code, so the gap has no live exploit path today. Not patched:
the function takes no `org_id` parameter to filter by (it currently *derives*
org_id from the row), so a correct fix means changing the signature once a
caller exists — speculatively editing unreachable code without that context
risked getting the eventual contract wrong. Flagged for whoever wires up the
escalation feature.

### B5 — `graha_tickets` / `approval_requests` naming collisions, both currently harmless
- `graha_tickets`: two handlers want different shapes from the same table
  (`escalation_chain.py` wants `assigned_to`/`description`; `dristi.py:1102-
  1108` only reads `priority/status/category/created_at/resolved_at`). Since
  nothing writes to this table and `escalate()` is dead code, this is inert
  today but will surface the moment someone wires escalation up. Column shape
  could not be confirmed without DB access — flagged unverified in §8.
- `approval_requests` (no prefix) looks like an accidental near-duplicate of
  the real, migration-backed `staging.graha_approval_requests`
  (`040_approval_chains.sql`). `services/reminder_service.py:66-86` reads the
  no-prefix table for a "stale pending approvals" reminder that can never fire
  because nothing anywhere inserts into it. Not a crash risk (background scan,
  already correctly un-org-scoped like its siblings), just dead and likely a
  naming mistake worth the owner's attention (§7).
