# backend/migrations/

Database schema changes. Run against Railway Postgres in order.

## Numbering convention

`NNN_description.sql` — three-digit prefix, ascending. Never re-number.
Python migration scripts (`*.py`) are for one-off data migrations only;
schema changes must be `.sql`.

| `097_billing_updated_by.sql` | ⏳ Pending | **Who raised the fee.** One nullable column, `staging.org_billing_lines.updated_by TEXT`. 096 gave the table `created_by` and `ended_by`, which answer "who opened this charge" and "who stopped it" and not the question anybody actually asks — *who changed what this client pays, and when*. Amending in place is the DESIGNED path (096: ending a line and reopening it at the new price puts two rows of one kind in one invoice period and no index refuses the second), so a price change is an UPDATE to a standing row — and that row recorded `updated_at` and no author. `services/billing_lines.py:update_line` says so about itself in shipped code and names this migration as the fix. **TEXT, not UUID** — `user_549c9cac35aa`; 030 and 092 are the two scars, and a third actor column of a different type on the same table would be worse than either. **No backfill**: the author of a past amendment was never recorded anywhere, so there is nothing to backfill *from*, and 096's rule holds — inventing an author is worse than admitting there isn't one. NULL is readable against the `updated_at` that already exists: `updated_at = created_at` never amended, `updated_at > created_at AND updated_by IS NULL` amended before this column. **It is the LAST WRITER, not a history** — one column holds one name; a real amendment trail is an append-only second table and a real design decision, not something to smuggle in as a column. No CHECK (its two neighbours carry none, and a rule covering one of three identical columns looks enforced and is not), no index (nothing queries lines *by* author). **Locks:** one `ALTER TABLE … ADD COLUMN`, `ACCESS EXCLUSIVE` on `org_billing_lines` until COMMIT — nullable, no default, so a catalog update **without a table rewrite** (PG 11+), microseconds of work. The risk is acquisition: it queues behind any open transaction on the table and blocks every reader that arrives after it. Blast radius is the billing console, the top-up dialog and the invoice builder — **not** the whole product, unlike 096's ALTER on `organisations`. `SET LOCAL lock_timeout='5s'` makes the bad case a clean rollback. **APPLYING IT RECORDS NOTHING BY ITSELF**: the column stays NULL until `services/billing_lines.py` takes an `actor_id` on `update_line` (and sets `updated_by` wherever it already sets `updated_at`), adds it to `_LINE_COLS`, and returns it **only under `actors=True`** — it is an Aekam staff id and `GET /v1/billing/me/lines` hands its body to the tenant — and until `routers/billing.py:org_update_billing_line` rebinds `_=Depends(…)` to `user=` and passes it |
| `098_outbound_log.sql` | ⏳ Pending | **What left the building.** One new table, `staging.outbound_log`, one row per ATTEMPTED send on any channel. It exists because AWS said 2,586 of 3,000 SES message units had been used in August and the honest answer to "how many emails have you sent?" took an hour of inference and is still only a floor — **nothing in this product recorded a send**. `routers/vetana.py` mails every employee a payslip with a PDF attached on every payroll run, the E2E suite ran payroll 16 times against an org of 71 employees, and all ~960 went to `@example.com` — reserved by RFC 2606, so every one a hard bounce against the SES identity **production shares**. Railway rotates logs per deployment, so even the `logger.info` line is gone. A log line is not a record; a row is. **This file and `services/outbound_log.py` are ONE CONTRACT, coupled by name in both directions**: `_INSERT_COLUMNS` lists the thirteen columns it writes, `_split_channel` quotes `outbound_log_channel_ck` in its warning text, `_as_bytes` exists because of the `bytes >= 0` CHECK, `_detail` strips exactly the four keys `outbound_log_no_body_ck` refuses, and `_INSERT` omits `id` because it is GENERATED ALWAYS. **A disagreement between them is SILENT**: that module treats `42703 undefined_column` as "the table is not what we were promised", sets `_dormant`, discards the buffer, logs ONE warning and never writes again for the life of the process — so a single renamed column produces one line in a log that rotates away, then silence, which is the exact condition this table exists to end. Verification step 2 is the two-second check for it. **`id` is `BIGINT GENERATED ALWAYS AS IDENTITY`, not a UUID**: this is the highest-insert table in the product and a random key scatters every insert across the index, so the writer carries its own correlation id in `detail->>'event'` and reads the assigned key back with RETURNING rather than upserting on a key it chose. **The constraints are affordable only because the writer salvages a poisoned batch one row at a time.** It flushes up to 500 rows in one `INSERT … UNNEST`, where naively one CHECK/NOT NULL/FK violation would erase 500 records of sends that really happened; `_write_batch` catches SQLSTATE class 23 and re-runs the batch row by row, so a violation costs the offending row and the other 499 land. **If that salvage path is ever removed, every CHECK here must be reconsidered in the same commit.** That is the real difference from 095's ledger — a ledger row failing *must* fail the spend, a log row failing must **never** fail a send. `channel` and `status` ARE checked (a typo drops rows out of a question silently); `purpose` and `provider` are not (a new notification must not need a migration to be logged). Senders speak a compound vocabulary — `push:expo`, `social:facebook` — and the writer, not the schema, translates it into `channel` + `provider`; `whatsapp` is in the CHECK although nothing sends it yet, so the first real WhatsApp message is not the unlogged one. **No message bodies, ever**, and `outbound_log_no_body_ck` refuses `body`/`html`/`text`/`content` in `detail` — a tripwire, not a boundary, with the writer stripping them first. The trap that nearly fired: `social_publisher._guarded` passes `(text or "")[:80]` — the customer's own post — as its detail, and `outbound.begin()` has the same positional signature as the old `suppressed()`, so the mechanical conversion would have persisted client content and looked correct in review. `subject_or_title` is NULL for social **on purpose**; a future author who "fixes" that NULL reopens it. Four indexes for three questions: `(org_id, ts DESC)`; **`(lower(recipient), ts DESC)` — query it as `lower(recipient) = lower($1)` or you get a sequential scan and, for a mixed-case address, a false "we never emailed them"**, which is the worst wrong answer this table can give; a **partial** `(ts DESC) WHERE status IN ('queued','failed')`, safe only because the status vocabulary is CHECKed — **the migration that adds `bounced` must widen the CHECK and this predicate in the same file**; and **BRIN on `ts`**, kilobytes instead of hundreds of megabytes, which answers the whole-month AWS question and serves the retention DELETE. **Retention: 400 days, deleted not archived** — 400 and not 365 so "what was August *last* year" is still answerable, one window with no early anonymisation, and **not per-org** because this is Aekam's record of Aekam's own sending. Enforced by adding one batched, draining DELETE to `staging.cleanup_old_data()`, which the existing `retention-cron` already calls daily at `POST /api/internal/cron/retention` — **no second job**; partitioning was rejected because a missing future partition turns a forgotten maintenance task into a month of missing sends. **⚠ `staging.cleanup_old_data()` is called by `routers/scheduler.py:60` and is defined in NO migration in this repo** (it arrived in `2b1c4442` — three Python files, no SQL): either it was created by hand and lives nowhere in version control, or the daily retention cron has been failing since 2026-07-23 and nothing in this database is being pruned. This file does not guess — it RAISEs a WARNING at apply time and leaves the function alone. **Locks:** one statement touches a live relation — the FK takes ShareRowExclusiveLock on `organisations`, blocking writes (not reads) for a catalog update at 3 rows; no ALTER on any existing table at all, nothing scanned, nothing rewritten. **Applying it records nothing by itself, and worse — `_dormant` is per-process and never resets, so you MUST REDEPLOY after applying** or a running process keeps logging nothing while the table sits there looking correct and empty |

## Running a migration

```bash
# Apply a single file against Railway Postgres
psql "$DATABASE_URL" -f backend/migrations/007_rls_and_indexes.sql
```

Or use the Railway console for one-off scripts.

## Rules

- **Never edit an applied migration.** Create a new numbered file instead.
- Every new table needs a matching entry in `seed.py` for dev data.
- Every new column that is read in Python needs a `row_to_task()` or
  equivalent Pydantic model update in `server.py` or the relevant router.
- After applying a migration, update the Status column above.

## Cross-folder impact

| When you add a migration… | Also update… |
|---|---|
| New table | `seed.py` (dev data), relevant router, relevant frontend hook/page |
| New column on `tasks` | `row_to_task()` in `server.py`, `TaskOut` model, relevant frontend page |
| New column on `users` | `auth_router.py` `/auth/me` response, `AppShell.jsx` if user data is cached |
| New index | No code change needed, but note it here |
| New billing-line column (`org_billing_lines`, `invoice_billing_lines`) | `services/billing_lines.py` is the only writer — a router may read, none may INSERT/UPDATE. A line is **ended by setting `period_end`, never DELETEd**; `invoice_billing_lines.line_id` is `ON DELETE RESTRICT` so the database refuses it. If the column changes what an org is charged, check `staging.v_org_platform_line_drift` is still empty afterwards. If it is an **actor** column (a `public.users.user_id`) it is **TEXT, never UUID** — see 030, 092 and 097 — and `_row_to_line` must expose it only under `actors=True`: this table has no tenant writers, so every id in it is Aekam staff, and `GET /v1/billing/me/lines` hands that body straight to the client |
| New outbound-log column (`outbound_log`) | `services/outbound_log.py` is the **ONLY** writer — no router and no other service may INSERT or UPDATE it; reads are open. **The migration and that module are ONE CONTRACT and they name each other**: `_INSERT_COLUMNS`, `outbound_log_channel_ck` (quoted in its warning text), `_as_bytes` ↔ the `bytes >= 0` CHECK, `_detail` ↔ `outbound_log_no_body_ck`, and `_INSERT` omitting `id` ↔ `GENERATED ALWAYS`. Change one side and change the other in the same commit. A column this table has that the module does not name is dead; a column the module names that this table lacks is `42703`, which the module reads as "the shape is wrong" — it goes dormant for the life of the process after ONE warning and logs nothing further. **That failure is silent, so redeploy after applying anything that touches this table** and re-run the column-name and constraint-name checks in 098's verification block. **Never add a column that can hold a message body** — no second `jsonb`, no `payload`, no "first 200 chars for debugging": a payslip body is somebody's salary and a campaign body is the client's content. **New constraints are cheap only because of `_write_batch`'s class-23 salvage**, which re-runs a poisoned 500-row batch one row at a time so a violation costs one record instead of 500. If that path goes, every CHECK on this table has to be re-argued. Any new index must be created `CONCURRENTLY`, outside a transaction — this is the highest-insert table in the product — and **a migration that widens `outbound_log_status_ck` must widen `idx_outbound_log_trouble`'s predicate in the same file**, or the new status is invisible to the only query that looks for failures. If the column changes what retention must remove, update the DELETE in `staging.cleanup_old_data()`, not a new cron |
| New credit column (`hub_org_credits`, `org_member_credits`, `hub_org_credit_transactions`, `credit_prices`) | `services/credits.py` is the **ONLY** reader/writer. No router may name a credit column directly — `tests/test_credits_isolation.py` walks the tree and fails if any of those four table names appears in a second file. Add the column, then add the accessor there |
