   states, missing interactions, missing effects.

## Credentials at rest — finish what Aadhaar started

`services/encryption.py` (Fernet, `enc::` prefix, idempotent, legacy plaintext
passes through) is wired for `manav_employees.aadhaar` only. Live audit of the
cloud database on 2026-07-28 found what else is stored:

| Column | Rows | State |
|---|---|---|
| `organisations.r2_secret_access_key` | **2** | **plaintext — the only live exposure** |
| `hub_social_accounts.access_token` / `refresh_token` | 0 | empty |
| `varta_business_accounts.access_token_enc` / `webhook_verify_token` | 0 | empty |

**Do NOT encrypt the `*_key` columns** — `file_key`, `logo_key`, `object_key`,
`photo_key`, `resume_key`, `results_r2_key`, `evidence_key`, `signed_file_key`
are R2 **object paths**, not secrets. They are the lookup path; encrypting them
breaks file retrieval outright.

The three empty columns are the cheap win: wire encryption on their write paths
**now**, before the first row lands, and no backfill is ever needed. The R2
secret needs both a write-path change and a backfill of its 2 rows.

`r2_secret_access_key` is the strongest case in the list — a Cloudflare R2
credential in plaintext means a database dump or a leaked read-only connection
string yields write access to every org's file storage.

Write and read paths are DONE and shipped in `f3461218` — R2 secret encrypted
on both admin write paths and decrypted in `storage.py`; social access and
refresh tokens encrypted on both `hub_publish.py` INSERTs, decrypted at read in
`social_publisher.py`, and re-encrypted on the token-refresh UPDATE. What
remains is the key and the two backfills.

### Running the backfills — RUN THEM ON RAILWAY, not locally

**`backend/.env` points `DATABASE_URL` at `127.0.0.1`.** Running either
backfill as-is encrypts the LOCAL Postgres, leaves every cloud row plaintext,
and reports complete success while doing it.

**The fix is NOT to repoint local `.env` at Supabase.** That makes every future
local test run write to the production database by default — the exact hazard
that destroyed 24 attachments across 13 tasks once already. A one-off task is
not worth a permanent loaded gun.

Run them on the `kartavya-staging` Railway service instead, where
`DATABASE_URL` already points at Supabase and where `FIELD_ENCRYPTION_KEY` will
be set. Nothing secret has to leave Railway and no connection string gets
pasted anywhere.

    railway run python -m scripts.backfill_aadhaar_encryption --dry-run

Whatever the mechanism, **state in the report which database was hit.** A
backfill that reports success against the wrong database is worse than one that
fails, because it looks finished.

### Rollback

Supabase **Pro includes daily backups and point-in-time recovery** — that is
the rollback for this, and it is better than a manual dump because it covers
any moment rather than only when someone remembered to run one. Confirm PITR is
enabled in the dashboard before the first `--commit`.

A manual `pg_dump` of the cloud database is not possible from the dev machine:
`pg_dump` is not installed there and both local env files point at localhost,
so the cloud credentials are not present — by design, and worth keeping that
way.

Procedure, in order — do NOT reorder:

1. **The owner generates `FIELD_ENCRYPTION_KEY` and sets it on the
   `kartavya-staging` Railway service.** This step is his: Railway is not
   authorised from here, and a key must never be generated into a chat, a
   screenshot or a commit. Two were burned that way on 2026-07-28.
2. Confirm the same key is in the environment the backfill will run under, and
   that `services.encryption.key_source()` returns `FIELD_ENCRYPTION_KEY` and
   not `JWT_SECRET`. Both scripts refuse otherwise, deliberately — a backfill
   under the fallback ties the data to the auth secret and cannot be undone.
3. From `backend/` (not the repo root), `pip install -r requirements.txt`.
   Without it this fails on `import asyncpg`. PowerShell rejects `&&`.
4. `python -m scripts.backfill_aadhaar_encryption --dry-run` — expect **3**.
5. `python -m scripts.backfill_r2_secret_encryption --dry-run` — expect **2**.
6. `--commit` each only after its dry run reports the expected count.
7. **Then prove the round trip.** After the R2 backfill, open a page that loads
   a file for one of those orgs. If storage breaks, the decrypt path is wrong
   and the plaintext is already gone. A dry run that looked fine is not proof.

If the key is not set when the session runs, do **everything else** and report
the backfills as blocked on the owner. Do not work around the refusal, do not
set a key yourself, and never fall back to `JWT_SECRET`.

### Key handling — non-negotiable

`FIELD_ENCRYPTION_KEY` has **no re-key path**. Lost or changed, every encrypted
field is unrecoverable, and nothing fails at rotation time — it surfaces later
as unreadable values. Store it durably before use. Never generate it into a
chat, a screenshot or a commit; two keys were burned that way on 2026-07-28 and
had to be discarded.

The backfill script refuses to start unless the key came from
`FIELD_ENCRYPTION_KEY` rather than the `JWT_SECRET` fallback — deliberately,
since a backfill under the fallback ties the data to the auth secret and is the
one mistake that cannot be undone.

Running it needs the backend's dependencies: `pip install -r requirements.txt`
from `backend/`, then `python -m scripts.backfill_aadhaar_encryption --dry-run`
from that same directory. PowerShell does not accept `&&` — use separate
commands or `;`.

### The genuine gap: `hub_kb_chunks` has no retrieval indexes

Verified against the live database. The table carries only btree indexes on
`org_id`, `client_id`, `document_id` and the primary key. Missing:

- **IVFFlat index on the embedding column** — without it every similarity
  search is a sequential scan over every chunk
- **GIN index on `to_tsvector(chunk_text)`** — the `ts_rank` half of the hybrid
  search in `rag.py` has nothing to use either
- **`indexed_at` column**

`AI_AGENT_PLAN.md` calls this "Migration 051", but 051 was taken by
`org_signatory_fields`, so it was never written under any number.

Invisible today because the knowledge base is nearly empty. It degrades
linearly the moment the two client firms upload real documents, and RAG quality
is the AI behaviour they will judge fastest.

Write it as a new numbered migration. Two things to get right:

- **Build on the empty table.** IVFFlat is cheapest to create now and would
  need a costly rebuild later — this is the ideal moment, not a reason to wait.
- **`lists` must suit the row count.** The usual rule is `rows/1000`, minimum 1.
  On an empty or tiny table use a small value and say in the migration that it
  needs revisiting once the corpus is real, rather than picking a number that
  silently becomes wrong.
- Confirm the `vector` extension is present before assuming IVFFlat is
  available.

## Continuous, not a step at the end

### The passwordless path — build it safely or not at all

This is an authentication bypass. Built carelessly it is a backdoor in a
product two accounting firms are about to hold their clients' financial data
in. Non-negotiable properties:

- **Staging only.** Gated on an environment variable that is absent in
  production, and it must FAIL CLOSED — if the variable cannot be read, no
  token is issued. Never gate on `NODE_ENV`-style inference alone.
- **Short-lived and single-use.** Minutes, not hours. Consumed on use.
- **QA org only.** It must refuse to mint a session for any user outside the
  designated QA test org, so it can never reach a real customer account.
- **Audited.** Every issue and every use writes an audit row, like the platform
  support bypass does.
- **Never on `main`.** Staging branch only, and it must be obvious in review
  what it is — no innocuous naming.

Check first whether something already serves this before writing new code: the
invite-accept flow issues a token, and `platform_support_sessions` was designed
for impersonation (the table does not exist yet — see the deliberately-absent
list). Reusing an audited existing path beats adding a second way in.
