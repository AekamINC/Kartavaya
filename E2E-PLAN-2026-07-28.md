## Phase 0 — design gap analysis FIRST, then build, then test

This is not a test-only session. The order is **render → compare → implement
what is missing → then test**. Testing a page before it matches the approved
design just produces findings that the implementation would have changed anyway.

1. **Render both sides and compare.** Open each `design-handover/` reference and
   the live staging page side by side. `design-reference/` JSX/CSS is the real

2. **List every divergence** — not just layout. Missing components, missing
   states, missing interactions, missing effects.
3. **Implement the gaps into `staging`.** Full stack where a gap needs backend
   support, not just the CSS.
4. **Then** run the element-level testing below over the corrected pages.

## Tabs are nested — do not stop at the top row

Modules do not have "four tabs". They have tabs **inside sections, inside
pages**, and second-level tabs inside those. The top tab row is the part
everyone clicks; the nested ones are where defects survive untouched.

For every page: enumerate the full tab tree — top level, every section within
it, every sub-tab inside each section — and visit all of them. If a tab reveals
another tab strip, that is another level to walk. Do not report a page as
covered until every leaf has been opened.

## What counts as an event

**Every interactive element is an event.** Not "test the Ganit module" — that is
one line item hiding forty. If code was written to make something happen, that
something is an event and it gets exercised and looked at:

- every button, every icon button, every link
- every tab, including the ones nobody demos
- every drawer and modal: open, interact, close by X, close by Esc, close by
  clicking outside
- every dropdown, select, date picker, search box, filter, sort control
- every form field: valid input, invalid input, empty submit, boundary values
- every popover, tooltip, context menu, confirmation dialog
- every toast and inline validation message
- every empty state, loading state and error state
- every table: pagination, column sort, row select, bulk action
- assignment, reassignment, unassignment
- comments: add, edit, delete, @mention resolving to a real person
- drag and drop where it exists (Kanban columns, touch drag)

Target is **not** 50 — 50 is the floor. A single module page with four tabs, a
create drawer and a detail drawer is comfortably 30 events on its own.

## Continuous, not a step at the end

Three things stay open for the whole session and are checked after **every**
navigation, not once at the end:

1. **Browser console** — any error or warning. A React key warning, a failed
   prop type, an unhandled rejection. Record the page and the action.
2. **Network panel** — every 4xx and 5xx, every CORS failure, every request that
   hangs or retries. Note the route and the payload shape.
3. **What actually rendered** — a 200 that renders an empty table is still a bug.

A page is not "passing" because it loaded. It passes when it loaded, rendered
real content, and produced no console or network noise doing it.

**Creating them is possible; typing their password is not.** The owner's

### The passwordless path — build it safely or not at all

This is an authentication bypass. Built carelessly it is a backdoor in a
product two accounting firms are about to hold their clients' financial data
in. Non-negotiable properties:

- **Staging only.** Gated on an environment variable that is absent in
  production, and it must FAIL CLOSED — if the variable cannot be read, no
  token is issued. Never gate on `NODE_ENV`-style inference alone.
- **Short-lived and single-use.** Minutes, not hours. Consumed on use.
- **QA org only.** It must refuse to mint a session for any user outside the
  designated QA test org, so it can never reach a real customer account.
- **Audited.** Every issue and every use writes an audit row, like the platform
  support bypass does.
- **Never on `main`.** Staging branch only, and it must be obvious in review
  what it is — no innocuous naming.

Check first whether something already serves this before writing new code: the
invite-accept flow issues a token, and `platform_support_sessions` was designed
for impersonation (the table does not exist yet — see the deliberately-absent
list). Reusing an audited existing path beats adding a second way in.

### Then test properly, as each user

- `admin` must NOT satisfy `approver` on `vetana` and `ganit` — separated duty.
- A viewer reads and **fails to write** — the 210-route gate — and the failure

- The nav hides what the API refuses, and the API still refuses if the nav is
