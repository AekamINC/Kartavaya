## Findings that are not about automation

These sit underneath any engine. All four are now in `TASKS.md` under *Now*.

### 1 · The realtime publication — has a date on it

`supabase_realtime` contains exactly one table: **`staging.samvada_messages`** — 1,174 real tenant
messages, **RLS off, zero policies**. Publishing a table the anon role cannot be scoped to is a
cross-tenant exposure. The codebase spotted this itself — `useChannelMessages.js` refuses to
subscribe *for precisely this reason* — and then nobody reverted the publication.

**Latent, not live:** I fetched the deployed staging bundles and searched them. No Supabase URL, no
key. Vite inlines those literally at build time, so `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`
are unset for that build, the client is null, and both realtime hooks no-op.

**How it goes live:** `docs/CLOUDFLARE-OWNER-ACTIONS.md` step B3 lists `VITE_SUPABASE_ANON_KEY` as
one of eight variables to enter into the new Cloudflare Pages project, Production **and** Preview,
on **12 August**. Fix it before then — drop the table from the publication, or give it a policy.
One statement either way.

The mirror image: `useRealtimeTasks` subscribes to `public.tasks`, which is **not** in the
publication. Live board updates have never worked. The hook's own header says the publication step
must be done "once in the Supabase SQL editor"; it never was.

### 2 · Shadow tables — the product depends on a schema instruction failing

`activity_events`, `time_entries`, `field_definitions` and `field_values` exist in **both**
`public` and `staging`. `public.activity_events` holds 1,238 rows and is still receiving them;
`staging.activity_events` is empty. Core PM refers to all four **unqualified**.

`DB_SCHEMA=staging` is set on Railway and `db.py:108` issues `SET search_path TO staging, public`,
which would resolve those names to the empty copies. The data proves it is not taking effect.

So restore that routing — a pooling-mode change, the 5432 fallback connecting, a DSN `options`
parameter — and Core PM activity, time entries and custom field values silently start writing to
empty tables. The task engine's `set_field` writes unqualified `field_values` too.

### 3 · Scheduled reminders ignore quiet hours

`services/push_service.prefs_allow` reads `notification_prefs` including `quiet_start` /
`quiet_end`, fails open on a DB error, and has its own parity suite. It gates
`create_notification`, `send_push` and the task-reminder dispatch.

`reminder_service.process_pending_reminders` — the hourly job that produced all 331 reminders —
calls `send_email` and `send_expo_push` **directly** and never asks. Unnoticed because everything it
sends is suppressed.

## Two mistakes I made, and what they cost

**1 · A path with a space in it silently skipped seven specification files.** My first sweep looped
over `find … -name "*.md"` unquoted, and `design-reference/Kartavaya Redesign/` word-split. Seven
files were never scanned — and one of them, `MESSAGING-ATTENDANCE-SPEC.md`, is where
`varta_auto_replies` is specified. **The fifth automation surface was missed by a shell quoting
bug**, not by judgement. Re-run with `-print0`/`read -d ''`. Any sweep that reports "I checked
everything" should first prove its file list is complete.

**2 · Proposal 41 proposed a mechanism this codebase has already tried and abandoned.** 41 said the
event actor would travel via `SET LOCAL kartavaya.actor`. The app connects through **PgBouncer**
(port 6543, `statement_cache_size=0`) and almost every write is a bare autocommit `pool.execute` —
`SET LOCAL` outside a transaction sets nothing. And `STAGING_SETUP.md` documents RLS policies built
on exactly this idea, which measurably do not exist. **Corrected in 42:** triggers record *what
changed* with the actor NULL unless a transactional path set it; the app emits *who did what* at the
sites that need it; and a condition may only reference the actor on an event type that carries one.

Both are the same lesson in different clothes: **check that your instrument works before trusting
what it reports.**
