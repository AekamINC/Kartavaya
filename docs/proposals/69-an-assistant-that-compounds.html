69 · An assistant that compounds

The owner asked what LLM fundamentals belong in the database and the files so Sahayak learns and improves over time without a database bill to match. Measured against the live system on 2026‑08‑19, the honest answer inverts the question.

The finding in one line. Sahayak is not expensive and it is not short of storage — it is slow. Lifetime spend across every AI call ever made is $2.19, the whole database is 82 MB, and the assistant's tables are 0.8 MB of that. Meanwhile the average answer takes 7.3 seconds, while a provider already in the routing chain answers in 195 ms and costs nothing.

Proposal 49 predicted this without the data: speed is a provider property, and the fastest providers are the free ones. The table is now the evidence. Two of the three fastest providers cost nothing and are already wired.

Storage is not the constraint, and the 82 MB is not what it looks like. The largest object in the database is public.tasks at 34 MB — but its rows and indexes are only 752 kB together. The other 33 MB is TOAST overflow, and it is one column: attachments holds 32.36 MB, concentrated in six task rows created on 29–30 July. Two of them — "Custom Fields" and "Custom Fields - Board" — carry 13.7 MB each; every ordinary task is about 2 kB. That is file bytes stored inside the row instead of in R2, which the product already pays for and already uploads to elsewhere. Six screenshots are 40% of the database, and no AI feature put them there. Tracked separately from this proposal; it is an attachment-path defect, not an assistant one.

2 · The correction worth making first

A model does not learn from your database. Nothing written to Postgres changes a single weight, and at 208 messages across 29 conversations there is not enough signal to learn from statistically even if it did. Anyone proposing fine-tuning at this volume is proposing an expense that also welds the product to one vendor.

What compounds is not the model. It is three things around it:

  • Retrieval — what gets put in front of the model before it answers.
  • Vocabulary — whether it knows what your words mean.
  • Evaluation — whether anyone can tell that a change made it better.

All three are cheap, all three are curated by people rather than learned from data, and all three survive swapping the model underneath — which matters here, because the model will be swapped: it has changed four times already this quarter.

3 · The seven mechanisms, ranked by measured value

A · A latency budget, and a chain ordered by it not built

The largest felt improvement available, and it costs nothing

Routing today is a hardcoded chain in _select_providers(), ordered by an idea of quality that no measurement supports. The result is 94 calls sent to a provider averaging 15 seconds while a free 195 ms provider sits in the same list. Order the chain by measured p50 latency from hub_ai_logs, give each task a latency budget, and demote any provider that misses it. The data to do this already exists and is already being written — nothing new is stored.

B · A glossary the answer is grounded on exists, not machine-readable

Kilobytes of files; the single biggest quality lever

Sahayak's business failures are vocabulary failures, not intelligence failures. The product already knows that a client is the company, that unpaid invoices stay editable, that GSTIN blocks nothing, that UPI is one ID per platform, that "paid" only ever comes from bank reconciliation — but that knowledge lives in CLAUDE.md and in people's heads, not anywhere the assistant can reach. Move it into versioned term files, inject only the terms a question actually touches, and every product decision you make from now on improves the assistant as a side effect. That is the compounding the owner asked for, and it is a text file.

C · A golden eval set in CI not built

Files, no database, runs on a free provider

Question in, and the facts the answer must contain, the sources it must cite, the things it must refuse. Run on every push against a free model. Without this, no one can say whether any change in this document helped — including the model swaps that keep happening. It is the difference between improving and merely changing.

D · Full-text search first, vectors second 720 GIN indexes, none on the KB

Free; fixes the knowledge base without embeddings at all

The knowledge base has never returned a single result to anybody — 90 citations ever made, none from it — and embeddings were only one of four independent reasons. One of the others is that its text search matches the whole question as a single literal, so a real question can never match. Postgres full-text search fixes that for nothing, and this codebase already runs 720 GIN/tsvector indexes elsewhere, so it is a well-trodden path here. Vectors become a second opinion fused with the lexical ranking, not the foundation.

E · A feedback ledger that something reads table and endpoints exist, 0 rows

A few text rows

staging.ai_feedback exists, with record, list and stats endpoints already written — and it holds zero rows. Nothing has ever been captured, so nothing can be learned. Wire the thumbs, then make every thumbs-down a candidate eval case: complaint becomes test, test becomes fix, fix never regresses. That loop is the entire flywheel, and it is the cheapest thing in this document.

F · Verified question → metric mappings 107 metrics exist, no mapping store

A small table that only grows when a human approves a row

The analytics registry holds 107 metrics whose SQL has already been reviewed and probed against the live database. Teaching the assistant to choose a metric is safer and cheaper than teaching it to write SQL, and every approved mapping is a permanent improvement that no model change can undo.

G · A conversation summary and a token budget not built

Cheaper and better at the same time

History today is the last ten messages, raw, with no token budget: a long answer can crowd out the question, and turn eleven is simply forgotten rather than summarised. Roll older turns into a short summary and cap what is sent. Long noisy context makes answers worse, so this is one of the rare changes that cuts cost and raises quality with the same edit.

4 · The one everybody asks for first, and why it waits

H · A semantic answer cache defer

Right idea, wrong month

Cache an answer against the question's meaning and serve repeats for free. It is the standard advice, and the measurement does not support it yet: of 104 questions ever asked, 102 were distinct — two repeats in the product's lifetime. A cache would cost storage and correctness risk (every cached answer must be invalidated when the data behind it moves) to save $0.00.

Build it when the trigger fires, not before: repeat rate above ~20%, or spend above ~$50/month. Both are one query away from being known at any time, and the cache is a week of work whenever that day comes.

6 · What this proposal refuses to do

  • Fine-tuning. 208 messages is not a dataset. It would cost real money, freeze the product to one vendor, and improve nothing measurable.
  • Embedding everything by default. This is where database bills genuinely explode. Embed the knowledge base, and nothing else, until a measurement says otherwise.
  • An external vector database. pgvector 0.8 is already installed, and the database stays on Supabase permanently.
  • LLM-extracted "user memory" on every turn. A model call per message to learn preferences, at this volume, buys guesses at the price of the thing it is guessing about.

7 · Build order

Phase 1 — free, no migration, no owner decision the whole compounding core

Latency-ordered routing (A), the glossary (B), the eval set in CI (C), full-text KB search (D), the feedback ledger wired into the evals (E). Every one is files, existing tables, or query changes. Nothing here needs a migration on the shared database and nothing needs approval beyond this page.

Phase 2 — small, still cheap after phase 1 is measured

Question → metric mappings (F) and conversation summaries (G). Both want the eval set from phase 1 in place first, so their effect can be proven rather than asserted.

Phase 3 — the migration, only when it earns itself owner decision, deferred

Embeddings and the semantic cache. This is the only part that touches the schema, and the only part that needs the owner's word — because the vector column has to be widened and the shared database means production feels it. It is free to do now only because the chunk table is empty; that stays true for as long as the table stays empty.

8 · The single decision this defers to the owner

If and when phase 3 runs, the embedding model is a fork with no going back cheaply:

  • bge-m3 at 1024 dimensions — free on the HuggingFace key that is already set and already works; measured English/Hindi similarity 0.899. Needs the column widened from vector(768), which is free only while the table is empty.
  • e5-base at 768 dimensions — fits today's column with no migration, measured English/Hindi similarity 0.938, but truncates near 512 tokens while chunks are 500 words, so chunk size must drop to about 350 words or every chunk silently loses its tail.

OpenRouter serves no embedding models at all — its catalogue was listed to confirm it. There is no third option that costs nothing.
