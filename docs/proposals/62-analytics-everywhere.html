Analytics in every module, and a dashboard the client builds

Today analytics is a module you buy. It should be a property every module carries: buy Ganit, get Ganit's numbers. On top of that, one dashboard the org assembles itself — its own widgets, its own columns, its own date range, downloadable everywhere — with a sensible default so nobody starts at a blank page.

1 · What is actually there today

Dristi is further along than its reputation. It already has eight pivot sources, saved dashboards, scheduled reports and CSV/XLSX/PDF exports, and — unusually — it already gates on the source module rather than on dristi alone, so a dristi grant does not hand somebody the payroll ledger.

The three faults

Fault 1 — no date range. Of every Dristi read, only POST /query accepts date_from/date_to. /overview and /sales take no time parameter at all and are effectively all-time; /revenue takes months and nothing else; every export takes none. "Show me last quarter" is not expressible, and neither is any year-on-year comparison. This is the first thing to fix because everything else inherits it.
Fault 2 — analytics is priced as a module, so most clients see none. An org that buys only Ganit gets a /stats call and no report at all, because the reporting lives behind the dristi entitlement. That is backwards: the numbers about a module are part of the module's value, and withholding them makes each module look thinner than it is.
Fault 3 — the dashboard is not really the client's. dristi_dashboards.widgets is a JSONB blob with no position, no size, no column selection and no per-user copy. There is an is_default flag and no preset behind it, so a new org lands on an empty builder and has to invent its own KPIs on day one.

2 · What people actually ask analytics for

Three findings from the current practitioner literature shaped the design more than any feature list:

  • Start from a metric layer, not from dashboards. Teams that ship dashboards first and add governance later rebuild under a live product at several times the cost, and metric disagreement between two screens destroys trust faster than a missing chart.1 Define each metric once, in code, and let every surface render the same definition.
  • Progressive disclosure beats density. Show the one number that answers "is everything all right?", then let the reader drill.2 Our current overview tab does the opposite — it opens with a wall of counters.
  • Own the model, rent nothing that carries business logic. The data model, metric definitions and tenant isolation are the parts that make analytics a priced capability instead of a cost centre.3 We already own all three; what is missing is the layer that names them.

Alongside that, the per-domain research says the same thing everywhere: users want interactive reports — change the dates, drill in, choose columns, take it away as a file — and they want alerts when a number moves, not a dashboard they must remember to open.2,4

3 · The design: one metric registry, three surfaces

A metric is declared once, in the module that owns it. Dristi, the module's own analytics tab, and the export/schedule machinery are three renderers over the same registry — not three implementations.

# backend/analytics/registry.py — declared by each module, never by Dristi
@metric(
    key="ganit.dso",
    module="ganit",                       # entitlement falls out of this line
    label="Days sales outstanding",
    unit="days", format="number:0",
    grain="month",                        # the smallest bucket it is meaningful at
    dimensions=("client", "invoice_type", "currency"),
    sensitivity="financial",              # drives the role check, see §6
    drill="ganit.invoices",               # what a click opens
    sql=lambda w: f"""
        SELECT {w.bucket}(invoice_date) AS period,
               SUM(total * (CURRENT_DATE - invoice_date)) / NULLIF(SUM(total),0) AS value
          FROM staging.ganit_invoices
         WHERE org_id = $1::uuid AND is_active AND {w.date_clause}
         GROUP BY 1 ORDER BY 1""",
)

Three consequences worth stating plainly:

  1. Entitlement is not a separate check. A metric carries its module, so the catalogue a caller sees is the intersection of the registry and their reachable modules — exactly the rule /widget-types already applies to the eight pivot sources, applied to everything.
  2. Ratios are never stored and never averaged. DSO, win rate, attrition, CTR and utilisation are computed from summed numerators and denominators over the chosen window. The mean of daily rates is not the rate for the period, and a dashboard that gets this wrong is wrong quietly.
  3. The registry is testable. One test walks every declared metric, runs it against the window with a bound org_id, and asserts it returns the declared shape. A metric that no longer compiles fails the suite instead of failing a client's screen.

The universal analytic contract

Every analytic in the product — module tab, Dristi widget, scheduled report — answers the same request shape, so the frontend has one component and the user learns one set of controls:

GET /api/v1/analytics/run
   ?metric=ganit.dso
   &from=2026-04-01&to=2026-06-30      # explicit range; presets are frontend sugar
   &compare=previous_period             # or previous_year, or omitted
   &bucket=month                        # day | week | month | quarter | year
   &group_by=client                     # any declared dimension
   &filter[payment_status]=overdue
   &columns=client,invoiced,collected,overdue,dso   # the client's own column choice
   &format=json                         # json | csv | xlsx | pdf — same URL

format being a parameter rather than a separate endpoint is what makes "download this exact thing I am looking at" true rather than approximately true: the download runs the same query with the same window, the same filters and the same chosen columns. Today's /exports/{report_type} can only export five fixed reports with no window at all.

Saved views, which is what "customised by the client" really means

CREATE TABLE staging.analytics_views (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id      UUID NOT NULL REFERENCES staging.organisations(id) ON DELETE CASCADE,
    user_id     UUID,                     -- NULL = an org-wide view
    scope       TEXT NOT NULL,            -- 'dashboard' | 'module:ganit' | 'widget'
    name        TEXT NOT NULL,
    layout      JSONB NOT NULL DEFAULT '[]',   -- [{metric, x, y, w, h, viz, columns, filters}]
    date_preset TEXT DEFAULT 'last_30d',  -- the view's own default window
    is_default  BOOLEAN DEFAULT FALSE,
    shared      BOOLEAN DEFAULT FALSE,
    created_by  UUID NOT NULL,
    updated_at  TIMESTAMPTZ DEFAULT NOW()
);

A personal view shadows the org view of the same scope, and the org view shadows the shipped preset. Nobody ever sees a blank canvas, and nobody is stuck with somebody else's layout. The existing dristi_dashboards rows migrate in as scope='dashboard', user_id IS NULL.

4 · The catalogue, module by module

Every metric below is computable from tables we already have. Where it is not, the line says so. This is the actual build list for phase D3 onward.

Graha — CRM 5 reports exist

Pipeline velocity, conversion, rep performance, forecast and source analysis are already endpoints. What is missing is aging, concentration and the whole service side.

  • Pipeline value by stage — and stage-to-stage conversion, not just counts
  • Win rate = won ÷ (won + lost), by rep, source, size band
  • Sales cycle — median days created → won
  • Deal aging — open deals with no activity in 30/60/90 days
  • Lead → deal conversion by source and lead_score
  • Average deal size and its trend
  • Client concentration — share of revenue in the top 5 clients
  • Ticket volume by priority and category
  • Resolution time — resolved_at − created_at, median not mean
  • Contacts added per period, by type

Ganit — accounting one /stats

The highest-value module to instrument, and the thinnest today. Indian SMB finance teams ask for ageing, DSO and the GST returns above everything else.5

  • Invoiced vs collected per month, with the gap named
  • Receivables ageing — 0–30 / 31–60 / 61–90 / 90+ buckets
  • DSO and its trend
  • Top debtors with days overdue and last payment date
  • Collection rate = amount_paid ÷ total
  • Expense by category, and expense vs revenue
  • Gross margin per month and per project
  • GST summary — output tax by month and HSN, for GSTR-1 preparation
  • TDS deducted by section and deductee
  • Payment lag — median issue → payment days
  • Cash-in trend from reconciled bank rows, the only source of "paid"

Vikray — sales orders one /dashboard

  • Order value and count, by status
  • Average order value and trend
  • Product mix — revenue share by product
  • Repeat rate — customers with more than one order
  • Target attainment against the stored targets
  • Order → invoice lag, which is where revenue leaks
  • Customer concentration via client_id

Manav — HR one /stats

Headcount, turnover, time-to-fill and absenteeism are the four every HR dashboard opens with.6

  • Headcount now, and the joiners/leavers bridge for the period
  • Attrition % — annualised, and voluntary vs involuntary
  • Tenure distribution and average tenure
  • Department and designation mix
  • Span of control per manager
  • Time to fill — needs a requisition opened-at date we do not store yet
  • Confirmations due in the next 30 days
  • Leave liability — accrued balance in days and in rupees

Vetana — payroll one /dashboard

  • Payroll cost per month, per department, per head
  • Statutory totals — PF, ESI, PT, TDS by month
  • Overtime hours and cost
  • Salary band distribution — and the compa-ratio if bands are configured
  • Payroll as a share of revenue, which needs Ganit as well
  • Run status — runs pending, approved, disbursed

Pahchan — attendance nothing

Reachable only by god-mode roles today, deliberately, and any analytic here must keep that boundary — aggregate by team, never a per-person feed for a manager who is not entitled to it.

  • Attendance % by day, team and shift
  • Late arrivals against the shift policy
  • Absenteeism trend, unplanned versus approved
  • Hours worked and their reconciliation into Vetana days
  • Geofence exceptions and offline punches reconciled inside the 72-hour buffer

Prachar — marketing one /dashboard, ads partly built

This is where proposal 60's spine plugs in: once ad and site metrics land in analytics_metrics_daily, they are just more registry entries.

  • Sends, opens, clicks, bounces per campaign — rates from sums
  • List growth and unsubscribe rate
  • Event attendance — registered vs attended
  • Ad spend, CPL, ROAS (needs proposal 60)
  • Channel attribution — leads by graha_contacts.source

Core — projects, tasks, time nothing, and it ships with every org

Not a purchasable module, which is exactly why its analytics matter most: every single org has this data. Burn, utilisation and margin are what PM buyers ask for.7

  • Tasks by status, overdue count, and throughput per week
  • Cycle time — created → done, median
  • Burndown per project against its due date
  • Workload — open tasks and hours per person
  • Billable vs non-billable hours from time_entries
  • Utilisation % per person and team
  • Project margin — time cost against invoiced, joining core to Ganit
  • Approval turnaround — raised → decided

The remaining six nothing today

  • eSign — requests sent, signed %, median time to sign, abandoned by type
  • Varta (WhatsApp) — sends by template, delivery and read rate, reply rate, template rejections, cost per conversation
  • Sanvaad — message volume and active participants per channel, response time. Aggregate only: no analytic may expose message content or read state to anyone but its owner
  • Srijan / Sahayak — credits spent by skill and by user, cost per run, failure and refund rate, scraper spend against the actor price list
  • Niyam — rules fired, actions executed vs suppressed, failure rate, and which rules have never fired at all
  • Pay — links sent vs paid, median time to payment, reconciliation lag

5 · What the client actually touches

Every module gets an Analytics tab

Same component everywhere, driven by the registry filtered to that module: a KPI strip, three or four charts, and a table under them. It ships with a sensible default layout, and it is editable — add a metric, drop one, choose the table's columns, set the window, download. Buying one module buys its analytics.

Dristi becomes the cross-module surface

Dristi's job narrows and improves: it is the only place that joins modules — payroll against revenue, time cost against invoices, ad spend against won deals. The five hardcoded tabs become shipped presets built out of registry metrics, so they can be edited rather than only viewed.

The controls, everywhere, identically

  • Date range on every analytic, with presets (today, 7d, 30d, this month, last month, this quarter, FY to date — April-start, since this is India) and an explicit custom range through DateInput, never a native date input.
  • Compare to previous period or previous year, shown as a delta on every KPI.
  • Column chooser on every table, persisted per user per view, with the chosen set carried into the download.
  • Download on every analytic in CSV, XLSX and PDF — same query, same window, same columns.
  • Schedule — any saved view can become a recurring emailed report, reusing dristi_scheduled_reports, which already handles delivery windows and logs.
  • Drill — clicking a bar opens the underlying rows, filtered, in the module's own list page. This is the feature that turns a dashboard into a tool.

Dristi carries the module tabs too

The tab strip from the demo is not only a demo device — it belongs in Dristi itself. Dristi opens on the cross-module dashboard and then offers one tab per module the org owns, each showing that module's own analytics. The same component renders it whether the user arrived from the module or from Dristi, so there are two doors into one room rather than two rooms.

Two rules keep it honest: the strip lists only modules the caller can actually reach, so it is never an advertisement for a locked screen; and the module tab shows the module's default layout, not the org dashboard, because "Ganit analytics" should mean the same thing everywhere.

How it should look

The surface gets the treatment the rest of the product is moving to — a tinted ground with a soft colour mesh, glass panels over it, and real depth so a dashboard reads as layers rather than as a grid of flat rectangles:

  • Glass on capability, never on operating system. One @supports ((backdrop-filter: blur(1px)) or (-webkit-backdrop-filter: blur(1px))) gate; a browser without it gets a solid panel that still reads correctly. The existing [data-platform="win"] opt-outs are the thing to remove, not to copy — the Windows exclusion is what took the glass off ten surfaces.
  • Glass needs something to blur. A backdrop filter over a flat background looks like a flat background. The fixed mesh is what makes the effect visible, and it is why the panels look like glass rather than like grey cards.
  • Depth by elevation, not by borders. Two shadow tokens — resting and lifted — plus a one-pixel inner top highlight, so a widget rises on hover the way the approved animation direction asks.
  • New accent. Indigo primary with a warm amber second and teal third; the series colours are drawn from the same family so a chart never fights the chrome.
  • All of it as tokens (--glass-tint, --glass-alpha, --glass-blur, --glass-sat) matching the names editorial.css already uses, so this ports across rather than forking the design system.

6 · Every export is the client's own paper

Today a Dristi export is anonymous. The PDF branch builds <h1>Revenue report</h1> and a table; the XLSX writes the same title into cell A1. No org name, no logo, no address, no GSTIN, no period, nothing to say who produced it or when — which is a problem the moment a client forwards it to their accountant.

Meanwhile services/doc_render.py already has letterhead(), with logo embedding as a data URI, per-org accent colours, an address block and a GSTIN line that marks "not set" rather than omitting it. Ten document builders use it — invoice, payslip, quotation, statement, GSTR-3B, TDS challan, agreement, signed e-sign artefact, project report. Dristi's exports are the only PDFs in the product that bypass it.

  • PDF renders through doc_render: the org's name and logo, the report title, the exact window, the generation timestamp, and the org's accent on the rule. No GSTIN, no address, no phone — owner's decision, 17 August 2026. An analytics export is a working document for the firm's own people, and one they may hand to their client; it is not a tax document, and a GSTIN on it invites the reader to treat it as one. That makes the letterhead call here a narrower variant than the invoice path uses.
  • XLSX gets the same identity in a header block above the summary — org name, period, generated-at — and one sheet per widget below it.
  • CSV stays machine-readable, so branding goes in the filename (suryodaya-textiles_ganit-analytics_2026-04-01_2026-08-17.csv) and nowhere else. A comment banner in a CSV breaks the first parser it meets.
  • Our mark stays small: one line in the running colophon — a small half-lotus and "Prepared in Kartavya" — next to the org's own confidentiality line and page number. It is the client's document with our signature on it, not our document with their name on it.
  • The colophon lives in the reserved page-tail strip doc_render already keeps, so adding it costs the content nothing and cannot orphan a final line onto its own sheet.

7 · Access, privacy and the things that must not leak

  • Every metric carries its module; the catalogue is intersected with reachable modules, and a metric whose module is unreachable is not merely disabled in the UI — it is absent from the response.
  • sensitivity adds a second gate for payroll, attendance and platform cost metrics, so a project-level role with Vetana view still cannot pull individual salaries.
  • Aggregates below a small-count threshold suppress rather than round: one person's salary is not anonymous because it is labelled "average".
  • No analytic renders a user, member or org UUID — the existing check-rendered-ids ratchet applies to every new widget.
  • Project-only roles and org clients see project and task metrics and nothing else, per the settled role model.

8 · Making it fast without lying

  • Registry queries are org-scoped and date-bounded by construction; the window is never optional at the SQL layer even when the UI defaults it.
  • A nightly rollup fills analytics_metrics_daily (proposal 60's table, reused) for the expensive metrics — payroll cost, DSO, utilisation. Cheap metrics stay live.
  • Every response states as_of. A rolled-up number that is eleven hours old says so; nothing pretends to be real time when it is not.
  • Cache key is (org, metric, window, group_by, filters, role). The role belongs in the key — leaving it out is how one user's cached result reaches another.
  • PgBouncer: cast every ambiguous parameter expression. An untyped $1 + $2 is an instant 500, and it has cost us a whole feature before.

9 · Build order

D1 — the window, retrofitted ~1 session

Add from/to/bucket to all five Dristi reads and to the exports, defaulting to last 30 days so nothing breaks. Smallest change with the largest immediate effect, and it is the prerequisite for every phase below.

D2 — the registry ~2 sessions

backend/analytics/: metric declaration, window builder, the /api/v1/analytics/catalogue and /run endpoints, format negotiation, and the walk-every-metric test. Port the eight existing pivot sources and the five report tabs into it so there is exactly one definition of revenue.

D3 — saved views and the builder ~2 sessions

analytics_views, the layout grid, add/remove/resize widgets, column chooser, personal-over-org-over-preset resolution, and the migration of existing dristi_dashboards rows.

D3b — branded exports and the new surface ~1 session

Route every export through doc_render.letterhead(), add the org identity block to the XLSX header and the org-scoped filename to the CSV, and put the Kartavya colophon in the page tail. Ship the glass and depth treatment and the Dristi module-tab strip at the same time, since both are surface work on the same screens.

D4 — the money modules ~2 sessions

Ganit and core PM metrics from §4 — ageing, DSO, GST summary, utilisation, project margin. Ship the default Analytics tab for both. These two cover every org.

D5 — the rest of the catalogue ~3 sessions

Graha, Vikray, Manav, Vetana, Pahchan, Prachar, then the remaining six. Each is a registry file plus a default layout, which is the whole point of D2.

D6 — presets and first-run ~1 session

Shipped role presets — founder, finance, sales head, HR, delivery lead — chosen at org setup from the modules the org actually bought, so the first login shows a populated dashboard.

D7 — alerts ~1–2 sessions

A threshold on any metric raises a Niyam notification — DSO over 45, attendance under 90%, pipeline coverage under 3×. This is the feature that makes the dashboard stop needing to be opened, and Niyam already has the delivery path.

10 · Risks, plainly

Metric drift is the real failure mode. If the module tab and Dristi ever compute revenue differently, both lose credibility. The registry exists to make that impossible; adding a metric anywhere else must fail review.
Time-to-fill and a few HR metrics have no data. Several listed metrics need a column we do not store — requisition opened-at is the clearest. Those are marked in the catalogue and either get a small migration in D5 or get dropped; they must not ship as zeroes, because a zero looks like an answer.
Export cost. An unbounded XLSX over a two-year window will time out on Railway before it finishes. Every export gets a row cap and a paged path, and says what it truncated instead of silently returning less.
The shared database. D2 and D3 add tables; D4 onward only reads. Nothing here writes to an existing table except the one-time dristi_dashboards migration in D3, which runs against production data because there is only one database. It gets a dry-run count and a reversible shape — new table, old rows left in place.

11 · Recommendation

Do D1 this week regardless of everything else — a reporting module that cannot answer "last quarter" is the single most visible gap in the product, and it is a day's work.

Then D2–D4, which is where the shape of the thing is decided. After D4 every org, on every plan, has real numbers about its money and its work, and the client can rearrange them, choose its columns, set its dates and download the result. D5 is then a queue of similar, low-risk files rather than a design problem.

Hold D7 until a week of D4 usage is visible. An alert on a metric nobody looks at is noise, and we have learned that lesson once already with automation.
