An analytics spine, not a connector zoo

Supermetrics sells one thing: every marketing number a client has, in one normalised table, refreshed while you sleep. We already ingest Meta ads end to end. What we lack is the part that makes the second source cheap. This proposes building that part first.

What we already own

Supermetrics capabilityKartavya today
OAuth per client, credentials sealed services/connector_credentials.py — per-client → org → env resolution, sealed secrets have
Ad platform ingest services/ad_insights.py against Graph v21.0 — accounts, campaigns, daily insights meta only
Query API over the metrics routers/prachar_ads.py — campaigns, insights, overview, AI analysis have
Scheduled refresh Nothing. Sync is a manual POST /accounts/sync a human has to press. none
Normalised schema across sources prachar_ad_insights is Meta-shaped: fixed spend/impressions/clicks/ctr/cpc/cpm/roas columns. none
Blended cross-source reporting Impossible — there is only one source in the table. none
Destination (Sheets / BigQuery / Looker) None, and deliberately so — see the recommendation. none
The gap is not connectors. It is the spine: a normalised fact table, an adapter contract, and a scheduler. With those, a new source is a ~200-line adapter. Without them, every source is another module.

The shape

One fact table

Every source reduces to the same grain: on this date, for this entity, this metric had this value. Long, not wide — so a new source adds rows, never a migration.

-- migration 1xx: the analytics spine
CREATE TABLE staging.analytics_accounts (
    id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id               UUID NOT NULL REFERENCES staging.organisations(id) ON DELETE CASCADE,
    client_id            UUID REFERENCES staging.graha_clients(id) ON DELETE SET NULL,
    source               TEXT NOT NULL,       -- 'meta_ads' | 'ga4' | 'google_ads' | ...
    external_account_id  TEXT NOT NULL,
    name                 TEXT,
    currency             TEXT DEFAULT 'INR',
    timezone             TEXT DEFAULT 'Asia/Kolkata',
    connector_ref        UUID,                -- which sealed credential to use
    is_active            BOOLEAN DEFAULT TRUE,
    cursor_date          DATE,                -- last day we consider settled
    last_ok_at           TIMESTAMPTZ,
    last_error           TEXT,
    consecutive_failures INT DEFAULT 0,
    UNIQUE(org_id, source, external_account_id)
);

CREATE TABLE staging.analytics_entities (    -- campaign, ad set, page, property, listing...
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    account_id   UUID NOT NULL REFERENCES staging.analytics_accounts(id) ON DELETE CASCADE,
    entity_type  TEXT NOT NULL,               -- 'campaign' | 'property' | 'channel' | 'account'
    external_id  TEXT NOT NULL,
    parent_id    UUID REFERENCES staging.analytics_entities(id) ON DELETE CASCADE,
    name         TEXT,
    attrs        JSONB DEFAULT '{}',          -- objective, status, budget: source-specific
    UNIQUE(account_id, entity_type, external_id)
);

CREATE TABLE staging.analytics_metrics_daily (
    org_id     UUID NOT NULL,                 -- denormalised: every read filters on it
    account_id UUID NOT NULL REFERENCES staging.analytics_accounts(id) ON DELETE CASCADE,
    entity_id  UUID REFERENCES staging.analytics_entities(id) ON DELETE CASCADE,
    date       DATE NOT NULL,
    metric     TEXT NOT NULL,                 -- 'spend' | 'impressions' | 'sessions' | 'leads'
    value      NUMERIC(20,6) NOT NULL,
    currency   TEXT,                          -- set only on money metrics
    synced_at  TIMESTAMPTZ DEFAULT NOW(),
    PRIMARY KEY (account_id, entity_id, date, metric)
);
CREATE INDEX idx_amd_org_date   ON staging.analytics_metrics_daily(org_id, date DESC);
CREATE INDEX idx_amd_org_metric ON staging.analytics_metrics_daily(org_id, metric, date DESC);

Derived metrics are not stored. CTR, CPC, CPM and ROAS come out of prachar_ad_insights and become views over sums, because a stored ratio cannot be re-aggregated — averaging seven daily CTRs is not the week's CTR, and that is exactly the bug a blended report would otherwise ship.

One adapter contract

class SourceAdapter(Protocol):
    source: str                     # 'ga4'
    label: str                      # 'Google Analytics 4'
    metrics: tuple[str, ...]        # what it can emit, for the metric catalogue
    lookback_days: int              # late-attribution re-pull window

    async def list_accounts(creds) -> list[AccountRef]: ...
    async def list_entities(creds, account) -> list[EntityRef]: ...
    async def fetch_daily(creds, account, since: date, until: date) -> AsyncIterator[Fact]: ...

Fact is (entity_external_id, date, metric, value, currency). The adapter never touches SQL; the spine upserts. That single rule is what keeps a new source at 200 lines and stops each adapter inventing its own idea of a day boundary.

One scheduler

/cron/analytics, authenticated by CRON_SECRET like the rest, nightly at 03:00 IST. Per active account:

  1. Refresh entities — cheap, and it catches renamed and new campaigns.
  2. Re-pull from cursor_date - lookback_days to yesterday. Conversions get attributed late; a 7-day re-pull is the difference between a report that settles and one that is quietly wrong for a week.
  3. Upsert on the primary key, then advance cursor_date.
  4. On failure record last_error, bump consecutive_failures, and at three raise a notification through Niyam rather than failing silently.

Rate limits are per account, not global, so accounts run sequentially inside an org and orgs run concurrently behind a small semaphore. Meta's limit is a sliding hourly budget; the adapter surfaces the retry-after and the spine backs off instead of hammering.

The order to build it

A1 — the spine ~1 session

The migration above, the adapter protocol, the upsert path, and a metric catalogue table so the UI can label things without hardcoding.

A2 — Meta moves in ~1 session

Rewrite ad_insights.py as the first adapter. Backfill prachar_ad_insights into the fact table and keep the existing /api/prachar/ads/* responses identical on top of views. No frontend change and no user-visible change — that is the point.

A3 — the scheduler ~1 session

/cron/analytics, cursor and lookback logic, failure counters, backoff, token refresh. Ships unarmed; arm it after reading a week of runs, the way Niyam was armed.

A4 — GA4, the proof ~1–2 sessions

Second adapter. GA4 first because the API is free, every client already has it, and it is shaped nothing like ads — sessions and users, not spend. If the abstraction survives GA4 it will survive Google Ads. If A4 needs spine changes then the spine was wrong, and it is far better to learn that here than at source six.

A5 — the blended report ~2 sessions

The reason to own the backend at all: one page per client, spend from Meta beside sessions from GA4 beside leads, invoices and payments from our own CRM. Supermetrics cannot do that last column, because it does not hold the client's pipeline. We do.

A6 — export, not sync ~1 session

CSV and XLSX download plus a scheduled emailed PDF, reusing the existing report machinery. Not a Google Sheets connector — see the recommendation.

What will bite

Token expiry. Meta long-lived tokens die at 60 days and we have no refresh path. Today a human presses sync and it works, so nobody has noticed. Under a nightly cron every client silently goes dark two months after connecting. Refresh handling belongs in A3, not in a later polish pass.
Developer-token paperwork. GA4 and Meta need only OAuth. Google Ads requires a developer token with a review that takes weeks, and LinkedIn's Marketing API is a partner application. Plan the calendar around the approvals, not the code.
Row volume. One client, five metrics, 200 campaigns, daily, is roughly 365k rows a year from a single source. Postgres is fine with that, but only with the composite primary key doing the deduplication and a monthly rollup once a client crosses two years. Do not let the raw fact table become the only read path.
The shared database. Staging and production are one Supabase instance. This migration creates new tables and touches no existing rows — except the A2 backfill, which reads prachar_ad_insights and writes the new tables, and it hits production data the moment it runs anywhere. It gets a dry-run count first.

Recommendation

Build A1–A4 and stop to look. Four sessions buys a normalised, scheduled, two-source pipeline, and GA4 is the honest test of whether the abstraction holds.

Do not chase connector count. Supermetrics wins that fight forever — a hundred sources and a sales team. We win a different one: we are the only pipeline that already knows which of those clicks became a project, an invoice and a payment, because Kartavya holds all three. The blended report in A5 is the product; the connectors are just what feeds it.

And skip the Sheets destination. Every hour spent syncing our numbers into someone else's spreadsheet is an hour spent making our own dashboard optional.
