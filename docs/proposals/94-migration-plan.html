1Supabase Singapore → India: possible, cheap, and still wrong

The Pro plan is not the deciding factor. There is no in-place region change on any plan.

What Supabase actually offers

From the Supabase docs, Change Project Region: a project is bound to its region at the infrastructure level. The only path is create a new project in ap-south-1 (Mumbai) and migrate into it. Pro changes nothing here — it buys PITR, read replicas and larger compute, none of which move a region. Project transfers move organisations, explicitly not regions. Read replicas are read-only and cannot be promoted as a region cutover.

The move itself is small

Measured live: the database is 64 MB with seven extensions (pg_stat_statements, pg_trgm, pgcrypto, plpgsql, supabase_vault, uuid-ossp, vector) — all available on any Supabase project. The app talks to Postgres over asyncpg with a DATABASE_URL; there is no Supabase Auth, no Supabase Storage, no Edge Function to carry (@supabase/supabase-js sits in frontend/package.json but nothing in frontend/src imports it). A dump/restore of 64 MB is minutes, not hours.

What changes on cutover: the project ref, so DATABASE_URL and the pooler host on every Railway service, plus the two hardcoded toacecaewujfxjfrjwco.supabase.co entries in connect-src — one in frontend/vercel.json, one in frontend/public/_headers.

Why it should not happen now

  • Railway has no India region — California, Virginia, Amsterdam, Singapore. The backend physically cannot follow. Backend and DB are co-located today (measured: a 404 with no DB and /api/health with one SELECT 1 both return ~0.31 s from the UK — zero delta is the adjacency).
  • Every query gains ~50–60 ms. The worst handler, vetana.py POST /payroll/process, issues 14 sequential queries → up to +840 ms on one request. That is a felt regression on the product's slowest screen.
  • R2 cannot be pinned to India. Jurisdictional restriction is EU and FedRAMP only. For an accounting product the documents are the books, so a DB-only move buys no real residency.
  • It is a production cutover, not a staging one. Staging and production share one Supabase project; a region move takes both down together, while main is 1,822 commits behind staging.

This is the decision already recorded on 2026-07-27 and nothing measured today overturns it. Recommendation: no.

The condition that would change the answer

Residency is a hosting change, not a database change. Reopen only when all three land together: an India-region host for the backend, India-resident object storage for the documents, and a stated legal requirement. Moving Postgres alone is the expensive half of a move that delivers none of the benefit.

2Vercel → Cloudflare: yes, and the code half is already done

Blocked on owner actions, not on engineering — but two files have drifted since they were written.

The build work landed on staging and is inert: Vercel reads vercel.json + api/, Pages reads _headers / _redirects + functions/, and each ignores the other's. W1–W4 are done (public/_headers, public/_redirects, functions/i/[token].js replacing api/og.js); W5, the analytics swap, is deliberately staged for cutover day. The runbook is docs/CLOUDFLARE-MIGRATION.md; the owner checklist is docs/CLOUDFLARE-OWNER-ACTIONS.md.

Two blockers found today in frontend/public/_headers

Both would ship broken on day one of Pages, and nothing catches either — frontend/scripts/check-csp-hash.mjs reads vercel.json only, so the Cloudflare CSP is entirely unguarded.

  1. The CSP hash has drifted. _headers allows sha256-4pEVfXQ1F7eho+kcMi5Ain6DIWMGHPGjtPExuWptQ+I=; the live hash in vercel.json is sha256-JtAu+6V2X/sONIJ0daMfltBe8H1N8hZ9kn7S9IFO4hk=. The pre-paint script that sets data-theme / data-platform would be refused on every load, for every user — no build failure, no red test, just a frame of the wrong theme.
  2. Mappls is missing entirely. _headers predates the move to the client-side SDK. vercel.json allows sdk.mappls.com, apis.mappls.com, tile.mappls.com, *.mappls.com across script-src, style-src, style-src-elem and connect-src; _headers allows none of them. Territory maps would be dead on Pages. worker-src 'self' blob: is also missing.

Fix: regenerate _headers from the vercel.json CSP with the Vercel hosts swapped for the Cloudflare pair, and extend check-csp-hash.mjs to validate both files — proving it fails first, in both directions, exactly as the vercel.json guard was proven.

4SES on kartavaya.com

Region is settled. The work is a domain identity, four DNS record groups, and one piece of missing code.

Facts, read live

  • AWS_REGION=ap-south-1 on Railway — Mumbai, matching the console. This was carried as an open question; it is now closed by reading the variable, and it agrees with the 287 messages SES has accepted.
  • FROM_EMAIL=Kartavaya <no-reply@aekaminc.com>.
  • SES is out of the sandbox: 50,000/day, 14/sec.
  • Identities in ap-south-1: unicodegroup.com verified; aekaminc.com UNVERIFIED (only the address is); kartavaya.com absent.

The default sender is unsigned today — and that is what kartavaya.com fixes

Every message from an org without its own sender rows — Aekam Inc, E2E, UK AekamINC — goes out as no-reply@aekaminc.com, which SES accepts only because the address is verified. The domain is not, so those messages carry no DKIM signature.

Owner's decision, 2026-08-28: do not verify aekaminc.com. Once kartavaya.com is verified and FROM_EMAIL points at it, kartavaya.com is the fallback and aekaminc.com stops sending altogether. Verifying it would be work with a scheduled expiry date. This makes the kartavaya.com identity urgent rather than optional — it is the fix for the unsigned mail, not a later nicety.

Which zone the records go in — decide before the Cloudflare cutover

kartavaya.com DNS is still on Vercel nameservers, and the domain carries no MX, SPF, DKIM or DMARC at all (audited 2026-08-08). Two options:

  • Add them at Vercel now (recommended). The unsigned-mail window closes this week instead of after the nameserver switch. Cost: the six records must appear in the A2 zone export and be re-created by hand in Cloudflare — one repetition, on a zone that is being rebuilt line by line anyway.
  • Wait for Cloudflare. Built once, but every fallback mail stays unsigned until propagation completes.

Either way: do not switch FROM_EMAIL until SES reports the identity verified — an unverified From is a hard MessageRejected, not a degraded send.

What to build, in order

  1. Decide the sender domain. Recommendation: kartavaya.com becomes the product sender (it is the domain the recipient is already looking at), with no-reply@kartavaya.com as FROM_EMAIL. Keep unicodegroup.com exactly as it is — nine verified purpose rows, per-org.
  2. Verify the domain identity in ap-south-1 — identities are per-region and a us-east-1 identity is invisible to the running client.
  3. Easy DKIM — three CNAMEs, *._domainkey.kartavaya.com → *.dkim.amazonses.com. In Cloudflare these must be DNS-only (grey cloud); proxying a DKIM CNAME breaks it.
  4. Custom MAIL FROM subdomain, e.g. mail.kartavaya.com — one MX to feedback-smtp.ap-south-1.amazonses.com (priority 10) and one SPF TXT v=spf1 include:amazonses.com ~all. Without it the envelope domain is Amazon's and SPF does not align; DMARC then rests on DKIM alone.
  5. DMARC at _dmarc.kartavaya.com, starting v=DMARC1; p=none; rua=mailto:…. Read reports for two weeks, then p=quarantine, then p=reject. Never start at reject.
  6. Switch FROM_EMAIL to Kartavaya <no-reply@kartavaya.com> on both Railway environments, once and only once SES reports the identity verified. From that point aekaminc.com sends nothing and needs no records. (VAPID_MAILTO and VAPID_SUBJECT still read no-reply@aekaminc.com — those are push contact addresses, not senders, and need no DNS; change them for tidiness or leave them.)
  7. One configuration set per purpose, and click tracking OFF for transactional — rewriting a link inside an invoice reads as phishing to corporate filters. ON is fine for marketing@.

SSL is not the question; feedback is

Cloudflare will issue and renew the certificate for kartavaya.com and www automatically — correct, and irrelevant to deliverability. Nothing on this list needs TLS: DKIM, SPF, MAIL FROM and DMARC are DNS records, and none of them is proxied.

What will get the domain marked as spam is the missing bounce path. There is no SNS endpoint in any router and outbound_log has no bounced status — the vocabulary is queued · sent · suppressed · failed. A bounce is asynchronous: SES accepts, the row is written sent, and the bounce arrives minutes later to nobody. That is exactly how 960 payslips were "sent" and hard-bounced. AWS reviews at 5% bounce and suspends at 10%, and this product cannot currently see either number.

So: do not attach an SES configuration set / SNS event destination yet — it would publish into nothing. The work is code, scoped separately: a webhook router, SNS subscription confirmation and signature verification, a bounced status, and suppression that acts on it. It should land before kartavaya.com sends at volume.

The other two things that damage a new domain's reputation

  • Warm up. A brand-new sending domain sending thousands on day one is the textbook spam signal. Start with transactional volume only, ramp over ~2 weeks, and leave the existing verified unicodegroup.com traffic where it is.
  • ~1,600 fake-domain rows remain in data tables (contacts, registrations, employees, candidates, signers, campaign contacts, vendors, invites). None sits in an automatic path, but any campaign, payroll or e-sign run mails them for real. Use the AWS mailbox simulator addresses agreed in proposal 93 — they are reputation-exempt — and never @example.com, which hard-bounces by definition.
