0.1 · Why — and it is not "does the product work"

"Imagine giving a client a completely new org, and then they start using it and things break and they are not happy. Start from thinking that you are the client who will be using this."

"Every function works" and "a new customer's first week works" are different questions — and the second is the one that loses customers.

Three consequences, unchanged by any rescope:

  1. Delete first, then build from zero. A suite written against a populated org can silently depend on rows it did not create. It passes, and nobody knows whether the code works or a client simply happened to already exist.
  2. An emptied org is not a new org. Unicode keeps its profile, GSTIN, state, R2, senders and series — the configured lane. UK AekamINC has its configuration cleared too and is built from nothing — the brand-new lane. Two fidelities, and no sixth organisation.
  3. A new customer does not work in dependency order. They try payroll on day one with no employees, and open Reports before anything exists. That disorder is where the ugly failures live, which is why Suite 00 drives the cold start in the wrong order on purpose.

And what v5 adds to the why: this run happens on production, so the question becomes sharper again — not "would a new customer's first week work", but "is a real customer's data safe while we find out". Every gate in §1 exists for that second half.

0.3 · Operating standards — non-negotiable, and each one is a scar

  • Never call anything missing without a live query — and a schema-qualified negative is a fact about THAT SCHEMA ONLY.
  • Prove the check fails before trusting it. Mutations need UNIQUE anchors: a replace(…, 1) that hits an identical block in the wrong function is a false green in the proof itself.
  • Measure live exposure before fixing — latent and active need different urgency and different reports.
  • Never infer an outcome from a return value. send_email returns True when the gate suppresses; 1,562 rows read sent against 1,562 suppressed. The row is the evidence.
  • Code shipped is 🟡. A customer completing the flow is ✅.
  • A test that fails on a correct fix is a defect in the test — it teaches people to edit tests, which is how a real bug gets buried.
  • Report faithfully — blocked, skipped and partial included. A silent cap reads as full coverage.

0.4 · The four judgements this seat owns and may not delegate

#JudgementWhy it cannot be handed off
1Product bug or test bug?The axis stop-and-fix stands on. Get it wrong and you either edit a test to hide a defect, or fix code that was never broken.
2Latent or active?Has the hole been walked through yet. Different urgency, different report, different disclosure.
3Reversible or not?Decides whether it needs confirming first. On production this is the judgement that matters most.
4Broken, blocked, or excluded by decision?Three different sentences. Collapsing them makes a plan look finished when it is not — and it is how an item sits still while each side waits for the other.

0.5 · The three rules of this programme

Rule 1 — every row is typed by a user

Playwright fills the real form and clicks the real button. No SQL seeding. No API shortcut.

It is the easiest rule to break quietly, because posting to the API is far faster than driving a form and the suite still goes green — reporting coverage it does not have. Enforced by scripts/check-e2e-no-bypass.mjs, which holds at 5 named baseline violations and may shrink, never grow.

Rule 2 — stop and fix, and prove which it was first

Read the wire, the page context, or the Railway deploy log before writing the words "product bug".

Applied so it does not deadlock: a finding that blocks the suite is fixed now; one that does not is filed with evidence and the suite continues. What is never allowed is continuing and not filing.

Rule 3 — never write without asserting the org first

assertOrg() asserts the org ID, never the name.

The name is what got corrupted: a platform_admin credential resolved every request into Aekam Inc through platform_bypass, the save genuinely succeeded, and the suite went green while renaming the one org this programme guarantees is untouched. Write suites use org-scoped accounts only. God mode is Suite 19 and nothing else.

0.6 · The seven suite rules — each learned from a FALSE finding

Every one of these blamed the product for something that was the test's own fault.

0.7 · How it is driven — the interaction vocabulary IS the deliverable

A row landing in a table proves the write path and says nothing about whether the drawer opened, the drag persisted, the tooltip appeared, or the button was reachable by keyboard. Every defect this product has shipped in those classes was invisible to the database.

Each interaction asserts its own observable consequence — never merely that it did not throw.

EventDriven byWhat must be true afterwards
Clicklocator.click()a request fired, or the DOM changed, or navigation happened. Zero of three = a dead control — that triple is Suite 22.
TypepressSequentially(), never fill()the value commits and survives a reload. Contact search is server-side and does not fire on typing — a Phase 8.0 fault clicked an unfiltered table and opened the wrong record.
SelectselectOption(), setDate()the value binds to the row. No native <input type=date> exists in this product — use DateInput.
Dragmouse.move / down / move×N / upthe persisted column_id / sort_order after a reload. dragTo() fires two events and HTML5 dnd ignores it.
Hoverlocator.hover()the revealed action is visible and clickable.
KeyboardTab loop reading activeElementfocus order sane, Enter/Space activate, Escape closes every modal and drawer. Fixed by hand once; React Aria was rejected. Now pinned by e2e/a11y.spec.ts.

v5 adds one line to this table's logic: the eighteen disciplines in §4 are the same idea applied one level up. "It rendered" is to "it is accessible, fast, translated and works in Safari" what "it did not throw" is to "the drag persisted".

What the decision changes elsewhere

  • .env.e2e carries a note reading "Set dry on production 2026-08-30 for the 93 rerun. OWED BACK AFTER THE RUN: production OUTBOUND_MODE=…". That note is now superseded — the owner has decided live. Update it rather than leaving two instructions in the tree that disagree.

What production forbids that staging tolerated

  • No write-path probes. Validation is never tested by writing to see what happens. Read the wire, read the form, read pg_constraint.
  • No prefix deletes, ever. E2E and Aekam Inc share the platform bucket under staging/. The R2 sweep is key-list driven, from the database, with nullif(btrim(col),'') — the naive predicate inflates the list ~3×.
  • No DROP without the schema named. A prefix is not a stack. R9′ drops two backup schemas by name, one at a time, and neither is dropped to make room for the other.
  • A migration is preceded by a five-section risk report. Unchanged from the standing rule.
  • RLS is re-checked after every DDL. A new table without RLS is a cross-tenant leak that produces no error and no log line. Run the Supabase security advisor; treat a new rls_disabled_in_public as a breach, not a lint.
