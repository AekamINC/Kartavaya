Operating standards — non-negotiable, and each one is a scar

  • Never call anything missing without a live query — and a schema-qualified negative is a fact about that schema, not the database. That exact mistake closed Phase 6.4 on nothing.
  • Prove the check fails before trusting it. Mutations must use unique anchors: a replace(…, 1) that hits an identical block in the wrong function produces a false green in the proof itself.
  • Measure live exposure before fixing. Latent and active need different urgency and different reports.
  • Never infer an outcome from a return value. send_email returns True when the gate suppresses — 1,562 rows read sent against 1,562 suppressed. The row is the evidence.
  • Code shipped is 🟡. A customer completing the flow is ✅.
  • A test that fails on a correct fix is a defect in the test — it teaches people to edit tests, which is how a real bug gets buried.
  • Report faithfully, including blocked, skipped and partial. A silent cap reads as full coverage.

The four judgements this seat owns, and may not delegate

  1. Product bug or test bug? — the axis stop-and-fix stands on.
  2. Latent or active? — whether a hole has been walked through yet.
  3. Reversible or not? — which decides whether it needs confirming first.
  4. Broken, blocked, or excluded by decision? — three different sentences in the report, and collapsing them is how a plan looks finished when it is not.

1The rule this plan is built on

Every row is typed by a user. Playwright opens the page, fills the form, picks from the real picker, uploads the real file and clicks the real button. Nothing is inserted by SQL and nothing is posted straight to an API — because a row created by SQL proves the table exists, and only a row created by a click proves the product works. That is the whole point of the exercise and there is no exception anywhere in §4.

It has a cost worth naming: this is slow. ~22,000 browser interactions is an overnight run, not a five-minute one. §6 sets out the runtime and how it is sharded.

The goal, restated by the owner 2026-08-28 — and it is not "does the product work"

"Imagine giving a client a completely new org, and then they start using it and things break and they are not happy. Start from thinking that you are the client who will be using this."

That is a harder and more useful target than the one this plan was built around. "Every function works" and "a new customer's first week works" are different questions, and the second is the one that loses customers. Three consequences follow, and they change the plan:

  1. Delete first is right — settled below, on the owner's reasoning rather than mine.
  2. An emptied org is not the same as a new org. After the wipe, Unicode still has its profile, GSTIN, state code, R2, senders, document series, compliance settings and module subscriptions. A real new customer has none of that. So UK AekamINC becomes the brand-new-org lane: its product configuration is cleared too, and wave 1 builds it from nothing through the real screens. Unicode stays the configured-org lane. Two fidelities, both worth having, no sixth organisation needed.
  3. A new customer does not work in dependency order. Our waves are efficiency-ordered — people before payroll, clients before invoices. A real person wanders: they try payroll on day one with no employees, open Reports before anything exists, click Invoices before adding a client. That disorder is where the ugly failures live, and it is tested by Suite 00 below.

What "driven as a user" means — the interaction model

Owner, 2026-08-28: it is not enough to check that a row appeared. Click, motion, and every other event are what the customer actually experiences, so those are what get checked.

A row landing in a table proves the write path. It says nothing about whether the drawer opened, whether the drag persisted, whether the tooltip appeared, or whether the button was reachable by keyboard. Those are the product to the person using it. ⚠ Correction to the row above: without a webhook, the product cannot learn a bounce happened

I wrote that the bounce and complaint addresses prove "does the product mark the address and stop re-sending". Checked, and it cannot — there is no bounce feedback path at all.

  • No SNS or SES notification endpoint exists. No router accepts one.
  • outbound_log has no bounced status. The vocabulary is queued · sent · suppressed · failed. The code even anticipates the gap — billing.py:1745 talks about "the place nobody would think to update when a webhook adds bounced" — but that webhook was never built.
  • A bounce is asynchronous. SES accepts the message, the row is written sent, and the bounce arrives minutes later to nobody. This is exactly how 960 payslips were "sent" and hard-bounced.

So what the 45% actually proves, stated honestly: the full send path runs for 176 addresses — composition, sender resolution, per-purpose routing, SES acceptance and the outbound_log row. That is real and worth having. What it does not prove is bounce handling, because there is none to test. The simulator makes those bounces free and harmless rather than reputation-damaging, which is why it is still the right choice — but it does not by itself create the feature.

Building it is code, not SES configuration: a webhook router, SNS subscription confirmation and signature verification, a bounced status, and the suppression logic that acts on it. That is a piece of work in its own right and I have not folded it into this programme's estimate. Say if you want it scoped separately.

  • Nothing proves the bucket holds only what we think. Deleting by enumeration removes exactly the objects the database references and leaves anything else untouched — which is the right default for a store nobody has audited.

Aekam Inc is now positively isolated: its files are in the platform bucket, which is a different bucket from either org being wiped. That strengthens the §12 no-touch guarantee from a procedure into a physical separation.

So the sweep is driven from the database, not from the bucket

  1. Enumerate every key the target orgs reference, from the tables that hold them — graha_documents, manav_assets, pahchan_enrollment_photos, punch photos, generated invoice and payslip PDFs, samvada_message_attachments, hub_kb_documents, expense and task attachments, org logos.
  2. Subtract the protected set's keys — any object referenced by the 20 Aekam Inc team tasks or their comments. That is the "excluded files must not be deleted" guarantee, and it is enforced by set arithmetic rather than by care.
  3. Subtract anything not under an org — personal/<user_id>/ and shared/ keys belong to people and to no org, including the users being kept.
  4. Delete exactly that list, key by key, with the count reported. No prefix deletes, no bucket-level operations, ever.
Sequencing gate: the inventory must be captured in R2, before the rows are deleted in R4. After R4 the references are gone and the objects become unfindable orphans — paid for, unreachable, and impossible to attribute. Capturing it late is the one ordering mistake that cannot be undone.

DECIDED 2026-08-28 — delete first, then build from zero

I proposed writing the suites first, against the still-populated orgs, on the practical grounds that blank screens are harder to write selectors against. The owner chose delete first, and the reasoning is better than mine was.

A suite written against a populated org can silently depend on rows it did not create. It passes, and nobody knows whether it passed because the code works or because a client happened to already exist. Building from zero makes that impossible — every suite must create what it needs or fail immediately, which is the self-sufficiency the whole programme depends on. It also means the build agent sees the day-one empty states rather than inferring them, and those are the screens no one has looked at since the data arrived.

The order stands as tabled: R0 → R1 freeze → R2 backup → R3 protected → R4 delete → then build and run from empty. What makes it safe is R2: the restore is proven by performing one before R4 deletes anything, so an empty org is recoverable if the suites turn out harder than expected.

What it costs, stated plainly: parallelism. Build and run are no longer separable — a payroll suite cannot be written until an employee suite has run and left employees behind. So the 12-way build fan-out collapses into the dependency waves of §14, and the calendar stretches accordingly. Revised total: 20–25 days rather than 17–20.

How stop-and-fix works with agents

An agent that hits a failure stops, reports, and waits — it does not diagnose and it does not fix. I triage; who fixes is chosen by what broke. Sibling suites within the same wave continue, since they are independent by construction; the next wave does not start, because building on unfixed foundations is exactly what stop-and-fix exists to prevent.

⚠ Building from zero raises the cost of a wave-1 failure. With no data behind it, a defect in auth or org settings blocks all eight waves rather than one branch. That is the price of the from-zero decision and it is worth knowing in advance: the earliest waves are the ones to watch.

Why agents do not self-fix: an agent that both writes the test and rules on whether the test or the product is wrong will, under time pressure, edit the test. That is the one failure mode that makes this entire programme worthless — a green run over a broken product. The judgement is deliberately held outside the hands that wrote the code.
