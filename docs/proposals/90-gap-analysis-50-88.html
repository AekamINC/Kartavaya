Proposal 90 · Gap analysis

Everything from 50 to 88 — what shipped, what is wrong, what is left

A verified accounting of thirty-nine proposals. Every status was checked against the live database or the running code this session, not remembered — because in this repo, half of all historical "it's built" claims were stale, and this document caught more of them.

2026-08-25 · 802 claims audited across 70–88, quick-scanned 50–69 · 3 blockers re-verified by hand against the live DB · companion to proposal 82 (which this supersedes on status)

The one-paragraph verdict. Roughly 70% of the promised engineering exists, but only about a third of it can be used end to end by a customer. Everything from 55 to 68 shipped and works — the drop-off starts at 69, exactly where proposal 82 predicted "everything from 72 onward is paper." The dominant failure is not missing code; it is schema + API + tests with no screen and no data: 48 tables hold zero rows, and 16 columns that gate headline features are 100% NULL with no way to enter them. Fixing the six worst write-paths — one week — turns roughly eighteen already-built features back on.

2What is wrong right now

Not "unbuilt" — actively wrong, or false, in the running product. The first three were re-verified by hand against the live database this session.

1Payroll will pay ten people who have left. The payroll-run query joins manav_employees on is_active=TRUE with no last-working-day guard. Live: 10 employees with a past offboarding date are still is_active. vetana.py:945. (73, 75)

2Every payslip deducts a flat ₹200 professional tax regardless of state. A populated 9-row slab table (Gujarat/Maharashtra/Karnataka) exists and is read by nothing; 1,105 of 1,112 payslips carry the constant. vetana.py:542. (78, 79)

3Two billing endpoints 500 on first call. Both INSERT INTO ganit_invoices name a column gst_rate that does not exist and omit invoice_number (NOT NULL, no default). Verified against the live schema. Shipped with zero tests touching the router. client_billing.py:402, 632. (87)

4Draft invoices are dunned on client statements & counted as revenue. 79 drafts worth ₹1.16 cr print on the statement of account; Dristi revenue counts 102 drafts. The one-line fix that landed in gst_period.py was never applied to documents.py:281 or dristi.py:332. (73)

5A cross-tenant leak in the newest router. client_billing.py:188 never checks the client belongs to the org; the sibling creators in the same file do. (87)

6The public /security page says the product has no MFA. TOTP, login challenge, recovery codes and org enforcement shipped 23 Aug; the page was last touched the day before. Plus three undisclosed AI sub-processors (OpenRouter, HuggingFace, Groq) on the very page written to unblock the sale. (81)

Two proposals that contradict each other

86 vs 87 on client billing. 86 specified ALTERing graha_clients and a client_billing_lines table; 87 said graha_clients needs "None" and built differently. 87 won — but 86's "Prorated Salary Calc" is now owned by neither, and HR doesn't do it either (it prorates by attendance, never by joining date).

87's central justification is false. It argues "procurement already gates on require_module('ganit')" — but the live code is require_module("kray"); proposal 85 minted that module the day before. The conclusion may be right; the argument isn't.

4Structural problems — visible only across proposals

  1. Schema + API without a screen — the dominant pattern. Eight features have a table, a route, tests, and no caller: compliance settings, Pahchan consent, skill acknowledgement, the storage browser, billing-anchor, pause, quota-proration, client_obligations. Every one was recorded as shipped.
  2. 48 zero-row tables. Five compliance registers with ~30 routes and 4 UI tabs; both platform-invoice tables; every WhatsApp table; every TOTP table. The product has been built for a firm that has not started using it.
  3. 16 feature-gating columns 100% NULL with no write path — salesperson_id, cost_price, vendor MSME fields, contact_id on expenses, reporting_to, state_code, photo_key, billing_profile_id and more.
  4. Four models built twice — sales_commissions* (dead, uuid) vs live manav_commission*; an empty hr_*/pay_* stack beside live manav_*/vetana_*; two doc-number allocators; two report schedulers.
  5. The dated-law store isn't wired to the engines that need dates. statute_calendar (45 rows) is read by skills only; vetana.py hardcodes the ESI ceiling, PT, PF and both TDS ladders.
  6. Nobody wrote a test that executes the SQL. 992 lines of billing router shipped with two fatal INSERTs and a tenancy hole and zero tests touching the file.

6The plan — recommended order

1Open the six write paths. Highest fan-out item in the entire arc. salesperson_id on invoice/order; vendor MSME fields; cost_price onto the line; expense contact_id; employee state; holiday state_code. This single week turns on ~18 features already built, tested and inert — per-person turnover, commission, the leaderboard, gross profit, margin, consultant P&L, the MSME clock, the Kray Overdue KPI, ageing, client profitability, PT-by-state. 1 week.

2Fix the six things the product gets wrong today (§2). Different files, run in parallel with #1. The only items where a customer is harmed by using the product as built — one writes payslips for people who have left. 3 days.

3Start the owner ledger today — none of it is engineering. The 9 legal strings; correct the MFA paragraph and add the 3 sub-processors before any production deploy. Counsel has the longest lead time and gates the first CA sale — start it now.

4Make the billing engine executable, then arm it. Fix the two INSERTs → fix the proration sign → make recurring recur → then arm /cron/billing. Arming first would fire the broken sweep. 2 days after decisions land.

5Give the eight invisible features a screen. Compliance settings, Pahchan consent, skill ack, storage browser, the Due tab, billing-anchor, pause, quota-proration. Each is a table + route + tests already paid for — a screen is the cheapest remaining unit of value. 1 week.

6Connect the statute calendar to payroll & invoicing. Until then "dated law" is a feature of the AI shelf, not the product. 1 week.

7Freeze new modules; retire the duplicates; add one rule: no proposal may call a table/column missing without a live query in the document, and no router ships without one test that executes its SQL. Both failure modes here are cheap to close and neither has been.
