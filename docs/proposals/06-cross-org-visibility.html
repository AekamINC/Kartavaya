The three that are scoped are scoped by accident: they happen to also hold an org_admin row in Aekam Inc. Remove that row and they join the top seven. Nothing in the code intends the difference.

Three defects, not one

1 · No org row means no limit at all
A platform account that is not an org_admin somewhere falls through to a query with no WHERE on organisation. This is the whole leak, in one line — backend/server.py, get_visible_team_ids.
if await is_org_admin(user_id):
    org_id = await admin_org_id(user_id)
    if org_id:
        ... WHERE org_id=$1        # scoped
    else:
        SELECT team_id FROM teams WHERE deleted_at IS NULL   # every team, every org
2 · Which org you see is nondeterministic
admin_org_id is LIMIT 1 with no ORDER BY, and it never looks at the org you actually switched into. If you are org_admin in two orgs, Postgres picks one — and may pick differently on the next request. That is your account.
SELECT org_id FROM staging.user_roles
 WHERE user_id=$1 AND org_id IS NOT NULL
   AND role_code IN ('org_owner','org_admin') LIMIT 1   -- no ORDER BY, no active-org input
3 · Ordinary members leak across orgs too
Below the admin branch, visible teams are unioned from team_members with no org filter. Anyone sitting on teams in two organisations sees one merged task list, whichever org the switcher says they are in. This is not a god-mode problem — it applies to everybody.

What I would change

1 · Make the unrestricted branch impossibleNo org context resolves to no teams, never to all of them. Fail closed — the same rule modules_for() already uses for unknown roles.
2 · Scope every visibility helper to the active orgThe org you switched into, passed in — not one guessed with LIMIT 1.
3 · A test that fails on today's codeA platform account and two orgs; assert it sees exactly one. Every defect this project has found passed a green build, so the fix ships with the check, not a note.
4 · Then the data sweepPlatform accounts off client teams, snapshotted first.
One caution worth saying plainly. This touches the helper that nearly every list endpoint calls to decide what a user may read. Narrowing it is right, and it can also hide rows from people who legitimately see them today — a member on teams in two orgs will stop seeing the merged list they are used to. That is the intended outcome, but it will look like data loss on the first run, so it wants a careful test pass rather than a quick patch.
