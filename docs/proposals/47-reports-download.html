The CRM report — what goes in it

One document, five sections, matching the five reports already on the Reports tab, over the period the tab is showing. Not five separate downloads: a firm sends a report, not a folder.

  1. Cover and summary — your organisation's name, logo and address; the period; deals opened, won, lost, and the value of each.
  2. Conversion — how many deals reached each stage, and the rate between them. The funnel, as a table and as a bar.
  3. Forecast — open pipeline weighted by probability, with expected close dates.
  4. Pipeline velocity — average days in each stage, and the deals sitting longest.
  5. Sources — where the deals came from, by count and by value, so spend can be pointed at what works.
  6. By person — the rep-performance numbers, and this is the one section that is permission-gated: a member who cannot see per-rep figures gets a report without it rather than an error.

Three formats, and they are not the same document

FormatWhat it is forWhat it contains
PDF Sending to a client or a board. Presentable. All six sections, laid out, with your logo, GSTIN and address in the header and the period and generation date in the footer. A4, the same renderer the invoices use, so the typography already matches.
Excel Working with the numbers. One sheet per section plus a raw Deals sheet — every deal in the period with its stage, value, owner, source, territory and dates.
CSV Importing somewhere else. The raw Deals sheet only. A CSV cannot hold six sections, and pretending otherwise produces a file nothing can read.
The PDF carries your organisation's details, not Kartavaya's. Name, address, GSTIN and logo come from the org record — the same source the invoices use. If those fields are empty the report still generates, with the header simply omitted: GSTIN and PAN are non-mandatory and block nothing.

How it is built

Nothing new is invented. There are three pieces and two of them exist:

  • services/report_generator.py already renders PDF and Excel from a data dict. It gets a second data shape, not a second renderer.
  • routers/reports.py already streams a download with the right headers and a URL-encoded filename.
  • The only new code is a _fetch_crm_report_data() that calls the five existing report queries and returns one dict.

One endpoint: GET /v1/graha/reports/download?days=90&fmt=pdf|excel|csv. One button on the Reports tab, with a format menu. It obeys the period already selected on the tab, because a download that ignores the filters on screen is a bug report waiting to happen.

What it will not do

  • No scheduling in this pass. There is a report scheduler for projects; pointing it at CRM is a separate change and emailing reports on a timer is how a firm accidentally mails a client their own pipeline.
  • No charts in the PDF beyond simple bars. A chart library in the PDF renderer is a large dependency for decoration.
  • No custom report builder. Different feature, and a much larger one.
