What does not work

Which features a customer believes they have and does not, which of them you sell, and the order to close them in. Five auditors, code read at 99edfb4b and measured against the live database, 5 August 2026. Sanvaad and Sahayak were excluded — they were being rebuilt while this ran.

Eight
Eight features a customer believes they have do not actually work, and every one of the eight is something you sell rather than dead code. The worst is the Overdue tile in Ganit, which also sits on the Today dashboard: it counts a status that nothing in the product has ever written, so both screens read “Overdue: 0 · nothing past due” while 199 tax invoices worth ₹3.11 crore are past due right now — ten of them Unicode Group's, worth ₹2,98,068. The same tile shows the MSME 43B(h) warning only when the count is non-zero, so a firm with a genuine 43B(h) exposure is told it has none. It is one line of SQL, and the payables half of the same strip already does it correctly. Against that: forty-two paths were traced end to end and found working, including the whole payroll engine, e-signature, the four GST and Tally exports, recording a payment, and the entire core task product — and not one screen in the app calls an endpoint that does not exist.

TRACED END TO END, AND GENUINELY WORKS — YOU DO NOT HAVE TO WORRY ABOUT THESE

This is the point of the exercise, not the padding. Every item below was followed hop by hop — the button, its handler, the network call, the route, the SQL, the table — and then checked against real rows in the live database. It is also the evidence that the eight above were traced rather than guessed at: the same method that found them cleared these.
Recording a payment
Writes the payment and moves the invoice. 476 payments live; the status mix really does shift — 329 paid, 146 partial, 237 unpaid.
Sales order → invoice
The Rule-46 completeness check runs before the invoice serial is drawn, and balance_due is written explicitly. The “born fully paid” bug is fixed in the code as it stands.
The four exports
Tally XML, GSTR-1 JSON, GSTR-3B working paper and the TDS challan are all wired, with the right verbs and the right prefix. An empty period is refused with a message naming what was held back, rather than shipping an empty file.
Payables overdue
Computed from the due date, correctly — the counter-example sitting in the same KPI strip as row 1, and the exact predicate that fixes it.
The payroll run
27 runs, 998 payslips. Salary structures, attendance, leave, loans, expense claims and statutory deductions all read and applied.
The payslip PDF
A real file, not a row — real bytes, a download header, and attached to the employee's email. The download button correctly turns a refusal into a readable reason instead of a broken file.
Payroll approval
A genuine four-eyes rule, checked against module grants. Approving decrements the loan balances and marks the expense claims paid.
Attendance → payroll
Pairs punches with approved corrections, honours the shift and overtime policy, offers a dry run first, and deliberately refuses to overwrite a day HR typed by hand.
Leave
Checks the balance before accepting, writes the decision, updates the balance and emails the employee. 217 requests live.
Employee PII
Masked on both the HR screen and the payslip read; the reveal is gated and writes an audit row every time.
Marketing “Send now”
Genuinely fixed and correct end to end. The preview and the send share one audience query, so the number in the confirm dialog is the number actually mailed.
E-signature, whole module
The signed PDF is assembled from the original bytes, hashed, stored, and its link re-signed on every read. The 22 documents completed before the fix are surfaced honestly with an “Assemble signed document” button rather than quietly left broken.
CRM automations
These really do fire — five real trigger points, six action types, a log table and working run counters. (Marketing's automations, by contrast, have no engine at all.)
Task attachments
Upload stores both the link and the object key, and every read re-signs from the key — so links do not rot. This is the pattern the CRM's Documents tab is missing.
Task reminders
The one background job that is genuinely scheduled and genuinely runs: 343 reminders, 165 sent, most recent 4 August. It claims work under a lock, so two runs cannot double-send.
The core task product
Approvals (queue, decision, board move, email), the activity feed (1,204 events), time tracking (287 entries), bulk edit, on-demand report download — a real PDF or Excel file streams back — and global search, which handles Devanagari and Gujarati correctly.
Dristi's own analytics
Every tile is real SQL. Not one placeholder or hard-coded number in the router, and a module the org has not bought is named as withheld rather than drawn as a zero.
Frontend → backend, as a whole
All 582 production call sites resolve to a real route with a matching method. Zero dead links. Whatever else is wrong, no screen is calling into thin air.

WHAT WAS CLAIMED AND THEN DISPROVED

Every claim below was raised by an auditor, or is a belief already written down in this project, and then killed by finding the wire. Several make the picture smaller. One makes it larger. This is the part that should make you trust the eight above.

ClaimedActually — and the wire that was foundWhy it matters
“Exports never worked.” A standing belief in this project since 28 July. Not true on the money side. All four Ganit exports are wired with the correct verbs and the correct prefix: the Stats tab's four buttons reach the Tally, GSTR-1, GSTR-3B and TDS-challan handlers, and an empty period is refused with a message naming the held-back documents. The belief predates the fix. Do not re-raise it for these four.
“The sales-target fix is a one-word column swap.” No. Both columns are text since migration 092, so the type cast has to come out too — leaving it in repeats exactly the mistake 092 fixed on the other side of the same join. A careless fix makes the join silently stop matching again, with no error.
“Fixing that column will make the target boards show real numbers.” No. In the test org all 120 assigned deals belong to one person who holds no target, so the corrected query still returns 0 there until somebody sets a target for a real assignee. With the wrong column it is ₹0 for every org forever. With the right one it is merely 0 until the data exists. Do not judge the fix by the seeded numbers.
“The payslip tells the admin to go and set the missing UAN.” It tells them nothing. The advisory banner has been a deliberate no-op since your ruling of 3 August, and the document-check payload is returned by exactly one endpoint in the whole codebase — invoices. No payroll screen reads it. The admin is not misdirected to a field that does not exist; they are simply never told. Quieter, not better — the input box is still missing.
“720 payslips are marked disbursed, so money went out against missing bank accounts.” No money moved. “Disburse” is a manual status flip by an approver. There is no payment rail anywhere in payroll — no NEFT file, no bank advice, no transfer. Nothing was misrouted. The missing account blocks a readiness check and a printed line, not a payment.
“The missing ESI number is doing damage now.” Latent. 0 of 998 payslips have ever deducted ESI; the setting defaults off. It bites the first org that switches ESI on. The UAN half is live and material. The ESI half is a trap set for later.
“An employee with a wrong clock-out loses that day's pay.” Overstated. HR can enter the day directly, and the attendance publish step explicitly refuses to overwrite a hand-typed row. This dropped that finding from critical to high. What is genuinely unreachable is the employee's own request and its approval trail — not the pay.
“Twenty drip sequences and sixty steps were authored over the product's life and none ever sent.” Wrong framing. All twenty belong to one org — the test org — and every one was seeded in a single batch at 03:51 on 3 August. No customer has ever pressed Enrol. The finding rests on the code (no query on the schedule column exists anywhere), not on row counts. The row counts were dropped from it.
Migration 092's own comment: “nothing in the codebase writes it … there is no broken user flow to repair.” It saw the fact and drew the opposite conclusion. Three live screens compute a rupee figure from that column. The cast it added stopped the query erroring and made the silent zero permanent instead. Self-satisfying commentary, pinned by a passing test — the exact trap that has burned this repo before.
“Eight billing routes have no caller.” They all have one. The billing tab passes a base path into a shared component, which composes the eight URLs from it. Nearly filed as a finding; killed before it was written down. A search for a literal URL is not proof of a missing caller. Half the “orphans” in past audits died this way.
“Somewhere a screen calls an endpoint that does not exist.” None does. All 582 call sites resolve; the five apparent misses are query-string templates and the three suspicious ones are dynamic action names whose every possible value exists. A clean negative. The failure in this product is one-directional: things built and never connected, not things called and missing.
The recurring-invoice finding as first written. Understated, not overstated. Verification added a fourth break (auto-send has no reader anywhere) and a ninth phantom column. The corrections did not all point one way. Included so the rest reads as measurement rather than argument.

WHAT WAS NOT CHECKED

  • Sanvaad and Sahayak were not audited at all. Both were being rebuilt while this ran, so their files were off-limits. That is two of the twelve modules, and it leaves fourteen routes in the Sahayak tree that could not be resolved either way — their would-be callers live in the excluded screens. It also means the “thirty-four invisible images” shape was never re-checked in the module it came from. Someone should re-run this sweep on those two once the rebuild settles.
  • Forty-seven lower-severity findings were not verified. They are recorded as raised, not as true. Half the claims in this repo's past audits turned out to be stale, and of the twelve claims that were checked in this pass, ten needed correcting. Treat that list as leads to trace, never as a to-do list. Some of it is almost certainly right — the “only two crons exist” claim in it is corroborated by finding 6 — and some of it is almost certainly wrong.
  • Nothing was run. Not one HTTP request was sent, no endpoint was called, and no write probe of any kind was made. Everything here is code read on disk plus read-only queries against the live database. Where a claim says “this would fail”, that is derived from the schema, not observed.
  • The deployed revision was not confirmed. All of this is measured against this branch at 99edfb4b. Nobody checked that Railway is running the same commit — and this repo has been caught by exactly that before.
  • The mobile app was not audited. It is mid-edit. It was searched, so that nothing was wrongly called “uncalled”, but no file in it was reviewed. A feature that only the mobile app reaches would not appear in this report at all.
  • Whether email actually leaves the building could not be answered from data. The outbound log holds one row in total, because that table landed yesterday. The send code paths are correct as read; there is not yet enough history to confirm delivery from the database rather than from the code.
  • Nine routers were scanned, not read. WhatsApp, scrapers, documents, activity, uploads and the org settings routers. A scan suggests they are fine. That is suggestive, not the same as tracing them. Do not treat them as cleared.
  • Two things that are new, not broken. The rewritten credits service and the billing-lines mechanism both shipped in the last two days and have not run in production yet, so their tables read empty. That is “not used”, not “no-ops” — flagged only so the next reader does not file them as findings. The first real credit spend after this deploy is worth watching.
  • One thing left ungraded. The payroll run derives working days as calendar days minus Sundays and never joins the 38 public holidays on file. Whether that is intended could not be settled from the code, so it is named here rather than counted above.
The honest summary. Most of this product works. The payroll engine, e-signature, the tax and Tally exports, recording a payment, the order-to-invoice bridge, leave, the whole core task product and the analytics module were traced end to end and are sound, and no screen in the app calls an endpoint that does not exist. Eight things do not work, all eight are things you sell, and seven of the eight are one defect repeated: a screen and a backend that were both built and never joined. Two of the eight are a single line each. Two more are frontend-only. The remaining four need a module written and one cron service added. None of it needs a migration, and none of it touches money that has already moved.
