Sanvaad — messaging design system

Extending the existing system, not replacing it. Studied against Slack, Discord, WhatsApp and iMessage; expressed in the k-* / editorial.css token vocabulary, because npm run check rejects a raw hex.

The problem

A Sanvaad message is a flat row: avatar, name, timestamp, text. It is a log. Every message looks identical whoever sent it, so reading a conversation means reading names. What the four reference products all do — and Sanvaad does not — is make authorship visible before you read a word: side, colour and shape carry it.

What each reference gets right

ProductThe idea worth taking
WhatsAppSide + tail. You never read a name to know who spoke.
iMessageA run of messages is one shape, not five. Only the last bubble keeps its tail.
SlackReactions are first-class and cheap to add. Threads stay out of the main flow.
DiscordPer-channel colour identity. You navigate by colour, not by reading the list.

What Sanvaad already has

Consecutive groupingisContinuation — same sender, same day, within 5 minutes. Bubbles look wrong without this, and it is already written.
Reactions, threads, presence, mentionsAll shipped. This is styling, not new capability.
The per-instance colour pattern--glyph, --av-bg, --pc, --c. Colour arrives as an inline custom property. Nothing new to invent.
No sense of who is speakingEvery row identical. This is the whole change.

Pattern · Channel colour

Eight tones. Assigned when a channel is created and then stored, so it never changes — and because it is stored, it can also be edited, which a hash could never allow.

The eight tones

Eight, not twelve: past eight, adjacent hues stop being distinguishable at 22px and the colour stops being a navigation aid. Saturation sits in the 40–55% band the module palette already uses, so a channel tile cannot be mistaken for a status chip.

The colour goes on the glyph tile, not the left border. .ch already carries border-left: 3px solid transparent for one purpose — .ch.on turns it --primary to mark the selected room without shifting the row. Putting channel identity there would collide with selection, and the selected channel would lose its own colour exactly when you are looking at it.

Where the value comes from — and why not a hash

A color column on samvada_channelsSet at INSERT from the next tone in rotation. Migration 100, plus a backfill for the six channels that exist.
Stored beats derivedA hash off the channel id would be stable — but unchangeable. You asked to customise things in the module; a stored column is what makes that possible at all.
Rotation, not randomness"Random" on six channels collides — the birthday problem gives roughly a 60% chance two share a tone. Next-free-in-rotation guarantees the first eight are all distinct, which is what "different colour per channel" actually means.

Decisions

Native emoji, no image spritesEvery target platform renders them. A sprite sheet is ~400 KB and a licence question for nothing.
Frequently-used is per person, stored locallyNo schema, no request. The row that matters most is the one you build yourself.
Search is keyword, not fuzzyA curated ~1,500-emoji list with keywords is ~40 KB and lazy-loaded when the picker first opens — it must not sit in the main bundle.
Existing endpoint, unchangedsamvada_message_reactions.emoji is already free text. The backend needs nothing.

What must not break

sanvaadWiring.test.jsxWalks .ch rows positionally and asserts class names contain unread. An inline custom property touches none of it — but the bubble change rewrites .msg markup, and that file exists precisely because prop chains broke silently before. Read it before editing Message.jsx.
failureStates.test.jsx mounts ChannelList with channels={[]}Colour lookup must tolerate a missing id rather than throw.
No dangerouslySetInnerHTML, everMessage.jsx's header calls this out as a security boundary: a channel message is a string one colleague typed that renders in every colleague's browser. Bubbles are CSS. Nothing about this change needs raw HTML.
contrast-baseline.json must not growIt carries two Sanvaad failures already and its own header says shrink it. Reversed text on a filled bubble is the likeliest new failure — check it before shipping, not after.
Scope, honestly. The bubbles, the tails, the run grouping and the channel tones are styling on top of behaviour that already works — a day, maybe a day and a half. The emoji picker is its own component with a lazily-loaded dataset, call it another half day. Nothing here needs a backend change except one column and one migration for the channel colour, which exists so you can change it later.
