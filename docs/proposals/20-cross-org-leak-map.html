The cross-org leak map

What one organisation's data can reach today, who can reach it, and the order to close it in. Code read at 99edfb4b and measured against the live database, 5 August 2026. Four auditors, twelve findings, ten distinct defects after the duplicates are merged.

Yes — ten paths
One org's data can reach another org's user today, through ten separate defects. Nine of them permit a write, not just a read; one is read-only. Eight need an Aekam staff account — but two need no role at all, only a signed-in account and a task's id. Both leaks you were told about last time are still real: the X-Org-Id header still selects the tenant with no membership check, and the team-visibility helper still returns every team in the database for 7 of the 10 platform accounts. The other eight are new. The permitted surface is three things — a user count, an org-admin invite, an email change — and the actual surface includes payroll, Aadhaar files, biometric attendance, invoices, member rosters, seat caps, prices, and a permanent delete.

THE PERMITTED SURFACE — AND WHETHER IT EVEN WORKS

1 · The count of users works
A number. Rendered on the billing console. This one is implemented and is the only permitted action that is fully working.
2 · Invite an org admin partly
Adding an existing account as an org admin works (POST /api/v1/admin/orgs/{id}/members). Inviting a brand-new person 404s from the console — reported by one auditor, not independently re-verified by me.
3 · Change the org email no screen
The field exists on PATCH /api/v1/org/profile, but there is no cross-org screen for it, and that endpoint also accepts GSTIN, PAN, TAN and bank_details in the same body. The one permitted write is bundled with the most dangerous ones.

THE TEN, RANKED

Ordered by: writes before reads; payroll, HR, bank and biometric data before member identity, and member identity before task metadata; permanent damage before reversible — and, as a multiplier over all of it, how many accounts can reach it and how little they have to do. Ties break on blast radius. The top five are shared middleware, which is why they are both the worst and the cheapest to fix.

WHAT IS ALREADY CORRECTLY SCOPED — YOU DO NOT HAVE TO WORRY ABOUT THESE

The single most useful thing in this document. The module data itself — payroll, HR files, attendance, invoices, CRM, sales, marketing, analytics — is correctly scoped at the SQL level. Every by-id write in those routers carries AND org_id=$n::uuid. Their exposure is inherited entirely from who gets to pick the org, which is defect 1. That is why one middleware fix closes nine modules at once, and why this is a resolver problem rather than 400 endpoint problems.
Vetana — payroll
All six mutating routes carry AND org_id=$n, behind the module gate plus an explicit level check. Salary structures, payroll runs, disbursement, loans.
Manav — HR files
Update and deactivate are WHERE id=$1 AND org_id=$2; Aadhaar and PAN pass through encryption before the SET list is built.
Pahchan — attendance
Punch review and enrolment approval are org-scoped, require an org role as well as the module, and each writes an audit row. The file deliberately declines the shortcut and says why.
Ganit, Vikray, Graha, Prachar, Dristi
Every by-id write org-scoped; the handful with no literal predicate pass org_id into a service helper as an argument. Invoice generation re-loads the order under its org.
The org switcher
GET /v1/org/memberships lists only orgs you actually hold a row in — no platform widening. This is the one place your rule is already implemented, and it is the pattern to copy.
Search and bulk task edit
Both re-narrow the broken team helper against the active org. They are the reason those two surfaces did not inherit the 29-team bleed — and the proof the correct pattern already exists in this codebase.
The header, for ordinary users
A caller with no platform role is properly validated — the membership query must return a row or it is a 403. A customer cannot forge their way into another tenant. The hole is confined to the platform codes.
org_members.py
The correctly-written twin of the admin_orgs routes: refuses to delete an org owner, filters sensitive modules out of grants, validates the whole list before deleting anything, clears stale grants on removal.
The role table itself
Fails closed — an unknown role inherits nothing, not everything. Separated duty holds: payroll admin does not climb into payroll approver.
The sensitive-module audit
Genuinely works and is genuinely restricted to god mode: 277 rows in the live audit table, most recent 5 Aug, each carrying org, user and module. Non-god platform roles are refused payroll, accounting, HR and attendance outright.
Automations, time entries, doc numbering
Automations require an active membership with no platform bypass — the only file in the task core that gets this right. Time entries key on the owner. Document numbering is org-scoped with an allow-listed table name.
Invite escalation
A customer cannot self-grant the legacy admin flag; that grant needs a platform owner. Invite tokens are no longer returned by the list endpoint. Both pinned by tests.

WHAT WAS NOT CHECKED

  • Nothing was tested against the running product. Not one HTTP request was sent and no write probe was run. Everything here is code read on disk plus read-only SELECTs against the live database. The attack paths are derived from the dependency graph, not executed.
  • The deployed revision was not confirmed. All of this is measured against this branch at 99edfb4b. Nobody checked that the Railway service is running the same commit — and this repo has been caught by that before.
  • Sanvaad is unaudited. routers/messaging.py and routers/hub_chat.py were off-limits, being edited by another swarm. A mechanical scan showed org_id in nearly every handler, with one exception (channel mute), but no one opened them. 1,102 message rows exist, almost none of them Aekam's.
  • Srijan / Sahayak was not read. routers/hub.py depends on the org resolver in roughly 44 places, so it inherits defect 1 — but its own per-client guards were not verified.
  • Nine routers were scanned, not read. WhatsApp, scrapers, documents, activity, uploads, org security, org invites and org profile. The scan showed org predicates present. That is suggestive; it is not the same as reading them. Do not treat these as clean.
  • The e-sign token was not examined. The four /verify/{token}/* routes are unauthenticated by design and keyed on a signer token alone. Its entropy, and whether it is ever written to a log, were not checked. If it is guessable or leaked, those are unauthenticated cross-org writes onto signed documents.
  • The 58 org-less tables were counted, not traced. Each one is a candidate for this same class of bug, and each would need a per-table trace of every query that touches it. That is its own audit.
  • Whether any of this has already happened. Most of these paths write no audit row at all, so for them there would be nothing to find either way. What can be said: task_clients has zero rows, so the approvals grant has never been used in this database; and the 277 sensitive-module crossings that do exist were all made by an account that is a genuine member of the orgs it entered.
  • Whether the database has any backstop. Row-level security was not confirmed on or off. Every path reads through a service-role pool, so RLS almost certainly would not apply — but nobody ran the query, so nobody should assume it.
  • The frontend was not treated as a control, and should not be. Only the org switcher and the API client were reviewed, to establish how easily the header is set. The answer is: one stored browser value, and from a terminal, nothing at all.
The honest summary. Most of this product is correctly scoped. Payroll, HR files, attendance, invoicing, CRM, sales and marketing all carry the right predicate on every write that was read. What is not scoped is the layer that decides which org you are acting as, and one helper that decides which tasks you can see. Those two, plus the console routes built on top of them, are the whole of it. Fixes 1 through 6 are five one-line predicates and two missing checks; three of them delete a test that currently asserts today's behaviour, which is the real work. Nothing in the first six needs a migration.
