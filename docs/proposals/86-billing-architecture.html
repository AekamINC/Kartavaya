Billing Architecture Plan

Gap analysis and implementation roadmap — Kartavya by Aekam Inc

Two tiers. Aekam bills orgs for the platform (exists, mostly manual). Orgs bill their own clients through modules like Sales, CRM, Procurement (does not exist at all). Module settings for org-level customization (partially exists).

17 capabilities exist  ·  31 are missing  ·  6 phases proposed

III. Implementation Plan

P1 Billing Cycle Engine Foundation — everything else depends on this

What to build

  • Billing anchor per org — add billing_anchor_day (1–28) to organisations; default to signup day
  • Period advancement cron — daily job that rolls current_period_start/end and next_billing_date forward when the period expires
  • Billing direction flag — billing_direction enum (advance/arrears) on org_billing_lines so each line knows when it is due
  • Trial expiry check — the cron also downgrades orgs whose trial_ends_at has passed
  • Pause enforcement — require_module middleware returns 403 on status='paused' with a message to the org owner

Schema changes

  • ALTER organisations ADD billing_anchor_day SMALLINT DEFAULT 1
  • ALTER org_billing_lines ADD billing_direction TEXT DEFAULT 'advance' CHECK (IN ('advance','arrears'))
P2 Proration & Mid-Cycle Changes The core math — prorated charges and credits

What to build

  • Proration service — services/proration.py: given (amount, cycle_start, cycle_end, event_date), return prorated charge. Handles 28/29/30/31-day months
  • Plan upgrade proration — when admin_set_plan changes tier mid-cycle, calculate credit for unused days at old rate and charge for remaining days at new rate; write both as billing lines
  • Module co-termination — when a module activates mid-cycle, prorate to align with the org's billing anchor
  • Proration threshold — config: if remaining days ≤ 3, waive the micro-charge and start billing next cycle
  • Retroactive/backdated adjustments — admin endpoint to create a billing line with a past period_start for late-logged changes (HR mid-month hires recorded late)
P3 Automated Invoicing & Dunning Invoices generate themselves; overdue ones escalate

What to build

  • Auto-invoice cron — on billing anchor day, query all open billing lines for the period, generate a subscription_invoice with structured line items, GST, and UPI payee snapshot
  • Invoice preview endpoint — already exists at /billing/invoice-preview; wire it into the auto-generation as the dry-run step
  • Dunning workflow — 3-step escalation: reminder at due_date+3, warning at +7 (cc org owner), access degradation at +14 (read-only mode, not full lock). Write reminder_sent_at
  • Overage billing line — at period end, if overage_credits > 0, auto-create a billing line at CREDIT_PRICE_INR rate
  • Credit auto-reset cron — explicit scheduled reset instead of lazy reset, so idle orgs get a clean ledger entry
Dunning sends email via the existing Resend pipeline. No payment gateway — the escalation is informational + access degradation, never an auto-charge.
P4 Module Settings Framework Org-level customization per module

What to build

  • module_settings table — (org_id, module_code, settings JSONB) with one row per active module per org
  • Settings schema per module — each module declares its configurable keys with types, defaults, and validation. Stored as a registry in services/module_settings_registry.py
  • Settings API — GET/PATCH /v1/org/modules/{code}/settings; org_owner/org_admin; validates against the registry schema
  • Frontend: Module Settings tab — in org settings, under each module card, a "Configure" button opening a per-module settings panel
  • Initial settings per module:
    • Ganit (Finance): default payment terms (days), default tax rate, invoice numbering format, billing cycle preference
    • Graha (CRM): deal stage names, default currency, lead scoring toggle
    • Vikray (Sales): commission rate defaults, quota period (monthly/quarterly), sales tax region
    • Kray (Procurement): PO approval threshold, vendor payment terms, 3-way match toggle
    • Manav (HR): leave types and accrual rules, probation period default, notice period default
    • Vetana (Payroll): pay cycle (monthly/biweekly), PF/ESI toggles, TDS regime (old/new)
    • Prachar (Marketing): campaign budget caps, send-time optimization, unsubscribe policy
P5 Org-Level Client Billing (Module Tier) Orgs bill their own clients — the second tier

What to build

  • Client billing profile — extend graha_clients with: billing_cycle, payment_terms_days, credit_limit, billing_anchor_day, gst_treatment (registered/unregistered/composition/overseas)
  • Recurring service lines — client_billing_lines table mirroring org_billing_lines but scoped to (org_id, client_id): retainers, subscriptions, ongoing services with auto-invoice generation
  • Proration for client services — reuse services/proration.py from P2: mid-month service starts/stops generate proportional Ganit invoices
  • Payment ageing — GET /v1/ganit/ageing: 30/60/90/120-day buckets for receivables, surfaced in Ganit and Graha dashboards
  • Vendor rate cards in Kray — vendor_rate_cards table: contracted rates per vendor per item category, with effective dates and proration clause flag
  • Prorated salary in Vetana — payroll run calculates mid-month joiner/leaver pay by working days in the period, using the org's configured pay cycle from module settings
  • Sales quota proration — mid-period rep assignments get proportional targets based on remaining days in the quota period
P6 Usage Metering & True-Up Volume-based billing for both tiers

What to build

  • Usage meters registry — define countable metrics per module: invoices_generated, POs_created, emails_sent, payroll_runs, API_calls. Each meter has a quota (from plan or module settings) and an overage rate
  • Real-time usage counter — middleware that increments usage_tracking on metered actions, with quota enforcement (soft limit = warning, hard limit = block)
  • True-up endpoint — quarterly admin review: actual peak headcount and transaction counts vs contracted minimums. Generates adjustment billing lines
  • Tiered pricing engine — services/tiered_pricing.py: given (volume, tiers[]), calculate total cost. Used by both Aekam (metered module pricing) and org (client volume discounts in Sales)
  • PEPM auto-billing — monthly cron counts active employees per org, multiplies by the org's PEPM rate, creates a billing line
  • Committed minimum enforcement — if actual usage < contracted minimum, bill the minimum anyway with a note showing the delta

V. Key Decisions Required

1. Billing anchor policy

Should all orgs align to the 1st of the month (simpler, co-term by default), or allow per-org anniversary billing (more flexible, more code)?

2. Dunning severity

At +14 days overdue: full lockout, read-only mode, or just persistent banner? This affects customer relationships.

3. Module settings scope

Should module settings be org-wide only, or should some settings be per-user within a module (personal defaults vs org defaults)?

4. Client billing as a module

Should P5 (org billing their clients) be a feature of Ganit, a feature of Graha, or a new standalone billing module?

5. Proration method

Calendar days (30-day month = divide by 30) or working days (exclude weekends/holidays)? Payroll needs working days; platform billing is simpler with calendar days.

6. True-up frequency

Monthly, quarterly, or annual? More frequent = more invoices but less sticker shock. Enterprise usually expects quarterly.

VI. What NOT to Build

  • Payment gateway — permanently ruled out. Collection stays UPI-on-invoice + manual recording.
  • Self-serve plan changes — pricing is negotiated per-org. This is a product decision, not a gap.
  • Multi-currency — INR only, flat pricing. No forex complexity.
  • Automated card retry (Stripe-style) — no gateway means no retries. Dunning is email-based.
  • Complex entitlement tokens — database-driven gating works at current scale (3 orgs). Revisit at 50+.
