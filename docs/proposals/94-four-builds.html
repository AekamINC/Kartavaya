Vetana · Payroll

A firm sets its own statutory policy

Your instruction: “we need a settings page in payroll and HRMS where the org adds their own policy. We will not mandate.” This builds that, and nothing in it forces a firm to enter anything.

Today

  • 67 of 90 live payslips deduct ₹0.00 professional tax. The ladder covers 7 states of ~22. A firm in Chennai or Kochi deducts nothing, silently.
  • Neither module has a Settings tab. Vetana has 7 tabs, Manav 17. The PT ladder editor exists and works — it is buried at the bottom of the Statutory tab, under a compliance calendar.
  • Every statutory switch is per employee. A firm that does not operate ESI must untick it on 30 salary structures, one at a time. There is nowhere to say it once.
  • PT on a bonus is inexpressible at any price. PF and ESI have two inclusion switches each; PT has none. Maharashtra’s ₹25,000 exemption for women is likewise impossible — no gender on the slab table.

Proposed

  • A Settings tab in Vetana, and the same pattern in Manav. The existing ladder editors move there, where a person would look for them.
  • Four nullable columns, no new table — so no new tenancy surface to get wrong. Two inclusion switches for PT; gender and basis on the slab table.
  • Statutory defaults for new employees: say “we don’t operate ESI” once, and every salary structure created afterwards inherits it.
  • Half-yearly states (Tamil Nadu, Kerala, Puducherry) become expressible: the administrator types the government circular’s numbers verbatim, rather than dividing by six and hoping.
Every default preserves today’s arithmetic exactly. The migration must change not one payslip. That is the acceptance test, not a hope: re-run a processed month and every figure is identical.

Hub · Billing

What a customer is charged

The striking part of this one: almost nothing needs building. Every writer already exists. Four of the five steps are operator actions through screens that are already deployed.

Today

  • No Kartavaya customer has ever been invoiced. 0 subscription invoices, 0 billing lines, 0 invoice lines. All three tables empty.
  • ₹54,000 a month is charged by nothing. Four orgs carry a monthly price with no billing line: Demo ₹10,000 · E2E ₹12,000 · UK AekamINC ₹20,000 · Unicode ₹12,000.
  • Both admin screens are already built and mounted. Nobody has ever used them. Meanwhile the customer’s own billing page returns an empty ledger to every paying org.
  • /cron/billing is armed and real — but between rolling the period forward and raising the org→client invoice, nothing turns a billing line into a platform invoice.

Proposed

  • Steps 0–3 need no code and no migration. Four operator actions through the product, and the acceptance test is already deployed.
  • Step 1 — set the monthly price the row already carries, for the four drifting orgs. The write repairs the missing line in the same transaction.
  • Step 3 — raise one real platform invoice from a preview. A paying customer’s ledger stops being empty.
  • Step 4 — one ~40-line sweep, modelled line-for-line on the org→client one that already solved every one of these problems downstream.
The acceptance test is a single number. /api/health → billing_drift.platform_line must go 4 → 0. It has been 4 the whole time and nothing said so until last night.
One thing is genuinely blocked on you. Aekam Inc has no GSTIN and no state code, and the invoice builder refuses without them. That refusal is correct — a tax invoice the department would reject is worse than no invoice — and it must not be relaxed. It needs the real registration entered once.

Cross-module

One form, more than one destination

You asked whether web forms should become their own section, usable by HR and vendors rather than only CRM. Yes — and the table is already shaped for it. The only CRM-specific thing is where a submission lands.

Today

  • 24 submissions across 2 forms — and the feature only began working on 31 August, when a broken clause was fixed. Before that it had produced zero rows, ever.
  • The field builder does not exist. The fields column is rich jsonb that nothing reads; the public page renders a hardcoded list. Both live forms have fields = [].
  • Slugs are globally unique across all tenants. “careers”, “jobs” and “apply” are claimed once product-wide, first come — and the loser is told somebody else holds the word.
  • A job applicant cannot apply. All 18 candidates were typed by staff; no CV was ever uploaded, and there is no anonymous upload route anywhere.

Proposed

  • One column — destination, defaulting to today’s behaviour — plus one nullable foreign key per destination.
  • A server-side allowlist dictionary maps destination to handler. The column is looked up in it, never interpolated into SQL.
  • The submit becomes one transaction, which also fixes an existing split write, and starts refusing a non-object payload that today causes an unauthenticated 500.
  • A top-level Webforms section. The Graha tab stays as a filtered deep link — one builder, not two.
This is an unauthenticated public write, so the guards matter more than the feature. The job opening is read from the form’s own settings and never from the payload — the same rule the CRM handler already applies. A real foreign key per destination, not a polymorphic pair: a real key is checkable, and this codebase’s repeated lesson is that unverifiable columns rot.

Pahchan · iOS & iPadOS

Clock in on an iPhone, without an Apple account first

You wanted something runnable to show a director before asking for the developer account. That is achievable — because the web clock already works, and the demo needs no Apple account and no Mac.

Today

  • The web clock works. 14 punches, every one with a photo and a location fix. It is already an installable PWA, and the camera permission is verified live and pinned by a build gate.
  • There is no iOS project — and the Android container that does exist declares exactly one permission, internet. No camera, no location. It cannot clock in either.
  • 14 of 14 punches are flagged “no reference photo”, because there are 0 enrollment photos product-wide and the web has no self-enrollment screen at all.
  • 22 of 30 employees would be refused: only 8 are linked to a login. And nothing opens the clock by URL, so a home-screen icon lands on the dashboard.

Proposed

  • Phase 0 — no Apple account, no Mac, no new endpoint. Six changes to the web app: a URL that opens the clock, a self-enrollment screen, and four correctness fixes.
  • Phase 1 — the container. Add the iOS target to the Capacitor config that already exists, paste the two usage strings already written for Android, and run it in the simulator.
  • The two permission strings are already DPDP-worded — “your location is read at the moment you punch and at no other time.”
  • Only distribution is gated behind the paid account. Building and demonstrating on a simulator, or on your own device for seven days, is not.
A real defect found while surveying this. All 14 punches carry accuracy_m = 0 — the signature of a scripted browser, not a phone. The server flags a fix only when accuracy is missing or above the threshold, so a zero clears the very check it should fail. One-line guard, included in phase 0.
The honest blocker is not iOS. It is that 22 of 30 employees have no login, so they would be refused on any device. That is worth fixing before a demo, and it is not an Apple problem.
Approving this means

Phase 0 is six web changes and takes about a day — and it improves the Android app and the browser too, because they share the screen. Phase 1 is roughly another day to a running simulator build you can put in front of a director.

What the paid account actually buys is TestFlight and the App Store. Nothing before that needs it.
