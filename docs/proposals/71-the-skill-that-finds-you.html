Proposal 71 · 20 August 2026 · Aekam Inc

The skill that finds you

A small dock in the corner of every module page that names the skills belonging to that page, runs them in place, and opens the whole shelf when you want it. Because the shelf we built is real, complete, and almost nobody has ever walked past it.

Owner's idea, written up. Every figure below was read from the live catalogue on 20 Aug 2026, read-only. Nothing in this document has been built.

The case — and the number that cannot carry it

What I nearly argued, and why it is wrong

The obvious opening is "30 of the 40 skills have never been added by any organisation." True, and worthless as evidence. Twenty-one of those thirty were seeded today by migrations 167 and 171 — they have existed for hours. And there are three organisations in the entire database, all ours. Two of the three have run skills; 104 runs, 100 of them from one org.

There is no adoption problem visible in this data because there is no adoption data. Any argument built on those counts is a wish wearing a number. The case for the dock has to stand without it.

The case that does stand

40active skills on the shelf, after migrations 166 / 167 / 171
34of them genuinely free to run — no model call, no credits
5clicks from a module page to running one
6of 13 modules have no skill at all, and no way to tell us

Nothing is wrong with the skills. Four migrations put a real catalogue on the shelf — GST amendments, ITC about to lapse, duplicate vendor bills, unfillable orders, attendance the record cannot support.

The problem is where they live. A skill is reachable at Sahayak → Skills → Catalog → add to organisation → Active → run. That is a destination. But nobody wakes up wanting a skill. They want one at the moment they are staring at an ageing receivables list, or the payroll screen four days before cutoff, or a stock figure that cannot be true. At that moment the skill that would answer them is two navigations and one unfamiliar noun away, and the moment passes.

That is an argument from structure, not from usage, and structure is the only thing we can honestly read today. A forty-item catalogue behind a five-click path is dead weight the day the first real firm arrives — and it is cheaper to fix now, at one backend line, than after we have watched them not find it.

Build it because the path is wrong, not because a number says so. The number says nothing yet.

What the page already knows

This is the part that makes the idea cheap. Every template already carries a module column — migration 166 backfilled the last eight NULLs and put a CHECK constraint on the vocabulary. Every route already maps to a module (lib/moduleColors.js, lib/moduleAccess.js). So "which skills apply to this page" is a filter on a column we already populated. It is not a recommendation engine, it needs no model call, and it cannot be wrong in an interesting way.

Zero AI, on purpose

The suggestion is template.module === routeModule, ranked by skill type. No model is consulted to decide what to show you, so the dock costs nothing to open, cannot hallucinate a skill that does not exist, and stays instant. The models stay where they already are — inside the six srijan content packs that actually generate something.

The empty state is the most valuable thing here

Every time somebody opens the dock on a page with no skills, that is a firm telling us — with their hand, on the actual page — which module they wanted help inside. Today we have no such signal at all and we are guessing what to build next. One counter per module, logged locally and rolled up, turns six embarrassing zeros into a ranked roadmap. That is worth more than the dock.

Not a chatbot. A dock.

The instinct said "small chatbot in the bottom right", and the instinct is right about the placement and wrong about the shape. Three reasons to make it a list that runs things rather than a box you talk to:

  1. We already have a chat, and it is not finished. Sahayak chat exists; its citations render dead and nothing streams. A second chat surface in the corner of every page doubles the surface that has to be fixed and gives the user two places to ask the same question.
  2. A chat box asks the user to guess the vocabulary. The whole defect being fixed is that nobody knows a skill called "Input tax credit about to lapse" exists. A blinking cursor does not tell them. Four named rows do.
  3. A list can be honest about price and permission before you click. A chat reply cannot show you "0 credits · reads only · you may run this" in a way you trust.

So: a pill that expands into a short list, and one line at the bottom — Ask Sahayak instead — for anything that genuinely needs a conversation. Chat is the escape hatch, not the front door.

The corner is not empty

Two things already claim bottom-right, and one of them is a ghost:

  • .k-onboard — the setup checklist. fixed; right:20px; bottom:20px; z-index:400. Real, mounted in AppShell, dismissible, and only shows for brand-new orgs. It wins the corner while it is up; the dock offsets above it rather than fighting it.
  • .k-cust-launch — same coordinates, z-index:90, and no JSX in the repository renders it. Dead CSS from the Customize panel. Delete it, or let the dock inherit the class it was clearly written for.
  • Mobile. The corner belongs to the bottom nav on phones. The dock does not exist there; skills reach mobile later, if at all, and eSign has already established that not every surface is a mobile destination.

And the keyboard already has a front door

lib/commands.js is the one command registry — it exists because there were once three lists and two palettes both bound to ⌘K. Skills belong in it: type "duplicate" into ⌘K and the skill should be there beside the nav entries. The dock is the ambient discovery surface; the palette is the fast one for people who already know the name. Same registry, two surfaces. A fourth list would repeat a bug we already paid for.

What it actually costs

Backend — one line, no migration

GET /v1/hub/org/skills selects t.name, t.description, t.category, t.estimated_credits, t.icon, t.steps — and not t.module or t.skill_type. Add those two columns to the SELECT and the dock has everything it needs. GET /v1/hub/skills/templates is already SELECT *, so the catalogue side works untouched. No new endpoint, no new table, no migration, nothing armed.

Frontend — one component, one map, one mount

  • components/skills/SkillDock.jsx — pill, panel, list, run.
  • A route → module map. It is a dozen lines and it belongs beside moduleColors.MODULES, not inside the component.
  • Mounted once in AppShell, next to CommandPalette and OnboardingChecklist. Never per page — a per-page mount is how you end up with two of them.
  • Running reuses the existing call: POST /v1/hub/org/skills/{id}/run, the same one SkillsTab makes. Results render in the existing SkillDrawer.
  • Write gate via useModuleWrite; entitlement via moduleAccess.

Four rules it must not break

  • Offer only what the caller can actually run. services/skills/modules.py refuses a caller who does not hold every module a handler touches. A dock that lists a skill and then throws a 403 on click is worse than no dock. Filter against entitlement before rendering, and say why a skill is greyed rather than hiding it silently.
  • The credit figure must stay true. Migration 166 fixed thirteen cards that read "0 credits" and charged 2. The dock reads estimated_credits and must never round, hide, or default it.
  • Names, not IDs. The dock renders skill names and module names. No UUID reaches the DOM — check-rendered-ids.mjs is the ratchet and it is positional.
  • Say what a run does before it runs. "reads only" for a check, "drafts, sends nothing" for a pack. The collection pack drafting a chase per overdue invoice must never read as though it will send them.

Shipping order

Phase 1

The dock 1 backend line + 1 component

Pill, page-filtered list, run in place, honest empty state, corner arbitration with the setup checklist. Desktop only. This is the whole idea, and it is small enough to ship in one sitting.

Phase 2

The shelf, from anywhere registry

"All 40 skills" opens the full catalogue in a drawer rather than navigating away, and skills join lib/commands.js so ⌘K finds them by name. Add-to-organisation happens in the drawer, so discovering and adopting a skill never leaves the page you were working on.

Phase 3

The demand signal the point

Count dock opens per module and empty-state hits per module. Six modules have zero skills; this tells us which of the six a paying firm actually wanted. Feed it into what gets built after the year-end five.

Later

Page state, not just page identity only if phase 3 earns it

The receivables list filtered to 90+ days suggesting the collection pack first. Genuinely useful, genuinely more work, and worth nothing until the plain version proves people open it.

What I would cut

  • A chat box in the dock. One chat, in Sahayak, finished properly.
  • Hand-curated page → skill mappings. The module column already is one, and a second copy goes stale the way the duplicated price list did.
  • AI ranking of suggestions. Nineteen skills on the busiest page sort fine by type and name. A model call to order four rows is a cost with no answer attached.
  • Mobile, for now. The corner is taken and mobile invoices are already read-only.

What I need from you

  1. Dock or chat? I have argued for a dock that lists and runs, with a link into Sahayak chat. Say the word if you want the chat shape anyway.
  2. Does it live on every page, or only on module pages? My default: every page inside the app shell, because core PM (kartavya) has three skills of its own and the empty state is never wasted.
  3. Phase 1 only, or 1 + 2 in one go? My answer is phase 1 only. It is one backend line and one component, and until a firm that is not us opens it we have nothing telling us whether phase 2 is the right second move.
