PROPOSAL 87 · Extends P86 §D / P5

Org-Level Client Billing

One data layer, one engine, tabs in every relevant module. Ganit is the home; CRM, Sales, and Kray get the same screens when active.

Decision — resolves P86 §V open question

Ganit owns org-level client billing. It is not a new module code, not a feature of Graha, and not standalone. Billing is accounting. Ganit-only buyers get every capability below.

When CRM, Sales, or Kray are also active, those modules surface the same tabs and the same data — not copies, not synced mirrors. One component, one API, one table. The module flag gates tab visibility, nothing else.

1. The Visibility Matrix

Every feature lives in Ganit unconditionally. Other modules show the same tab when the org has that module active. One update from any module writes once and is visible everywhere.

Prorated Salary is the one exception. It stays HR-only. Salary calculation is payroll math, not client billing — a Ganit user managing invoices has no business seeing salary structures, and Manav/Vetana already own the pay cycle and working-day calendar.

2. Why Ganit, Not a New Module

  • No new module code. Adding one means a new ALL_MODULES entry, a module_subscriptions row for every org, a plan-feature key, and THREE DEPLOYS in a non-negotiable order because staging and production share one database. Procurement (proposal 77) already proved this trade-off: it gates on require_module("ganit") because a firm that holds the books holds its purchase orders.
  • Client billing IS accounting. Billing profiles configure how money moves. Recurring invoices land in ganit_invoices. Ageing reports read from ganit_payments. The data is already Ganit's; the features should be too.
  • Independence for Ganit-only buyers. An org that buys only Ganit can set up client billing profiles, create recurring service lines, track metered usage, and run ageing reports — all from Ganit. They are not blocked on buying CRM.
  • No sync, no lag. CRM and Ganit don't sync because there is nothing to sync. The CRM billing tab and the Ganit billing tab render the same component, read the same endpoint, and write the same table. Update from either side, it is already there.

3. How Cross-Module Tabs Work

Architecture

One component, conditionally mounted. The frontend checks the org's active modules to decide which tabs to show. The API is always /api/v1/ganit/billing/*. The tab component lives in frontend/src/pages/ganit/. Module pages import and mount it.

The pattern already exists: procurement.py gates on require_module("ganit") and the procurement tab appears inside Finance. This proposal extends the same pattern in the other direction — Ganit features appearing as tabs in CRM and Sales when those modules are active.

Frontend mounting

  • GanitPage.jsx — always shows the Billing Profiles tab, Recurring tab, Metered tab, Ageing tab
  • GrahaPage.jsx (CRM) — shows a "Billing" tab that mounts ClientBillingTab when Graha is active. Same component as Ganit's.
  • VikrayPage.jsx (Sales) — same "Billing" tab when Vikray is active
  • KrayPage.jsx (Procurement) — shows "Rate Cards" and "SLA Credits" tabs when Kray is active

Backend gating

All billing endpoints live in a new routers/client_billing.py, gated require_any_module("ganit", "graha", "vikray") for client-facing features, and require_any_module("ganit", "kray") for vendor-facing ones. This mirrors the existing _payables_gate pattern in ganit.py.

4. Schema

All tables in the staging schema, org-scoped, following existing conventions. Every table carries org_id UUID NOT NULL REFERENCES staging.organisations(id).

client_billing_profiles
id UUID PK org_id UUID FK client_id UUID FK → graha_clients billing_cycle TEXT anchor_day SMALLINT(1-28) payment_terms_days INT currency TEXT DEFAULT 'INR' gst_treatment TEXT credit_limit NUMERIC(14,2) notes TEXT created_by TEXT created_at TIMESTAMPTZ updated_at TIMESTAMPTZ
One profile per (org, client). client_id references graha_clients — the company, never a contact. A Ganit-only org creates the graha_clients row directly (the table already exists independent of the CRM module).
client_service_lines
id UUID PK org_id UUID FK profile_id UUID FK → client_billing_profiles kind TEXT CHECK (retainer|subscription|one_off) description TEXT amount NUMERIC(14,2) cadence TEXT CHECK (monthly|quarterly|annual|one_off) period_start DATE period_end DATE billing_direction TEXT DEFAULT 'advance' auto_invoice BOOLEAN DEFAULT FALSE created_by TEXT created_at TIMESTAMPTZ updated_at TIMESTAMPTZ
Mirrors org_billing_lines from P1 but scoped to (org, client). Lines are ended by setting period_end, never deleted. auto_invoice = TRUE means the billing cron generates a ganit_invoices row on period roll.
client_metered_usage
id UUID PK org_id UUID FK profile_id UUID FK → client_billing_profiles metric TEXT quantity NUMERIC(14,4) unit TEXT rate NUMERIC(14,2) recorded_date DATE source_ref TEXT invoiced BOOLEAN DEFAULT FALSE created_by TEXT created_at TIMESTAMPTZ
Individual usage entries. metric is freeform per org (hours, units, transactions). source_ref links to the originating record (task, timesheet, order). invoiced flips TRUE when rolled into a ganit_invoices line.
vendor_rate_cards
id UUID PK org_id UUID FK vendor_id UUID FK → ganit_vendors item_category TEXT rate NUMERIC(14,2) unit TEXT effective_from DATE effective_to DATE proration_clause BOOLEAN DEFAULT FALSE notes TEXT created_by TEXT created_at TIMESTAMPTZ updated_at TIMESTAMPTZ
Contracted rates per vendor. effective_to NULL = still active. When a PO references an item in a rate-card category, the procurement module can auto-fill the rate and flag deviations.
vendor_sla_credits
id UUID PK org_id UUID FK vendor_id UUID FK → ganit_vendors rate_card_id UUID FK → vendor_rate_cards sla_metric TEXT threshold NUMERIC(14,4) actual NUMERIC(14,4) credit_amount NUMERIC(14,2) period DATE applied_to_bill UUID FK → ganit_vendor_bills status TEXT CHECK (pending|applied|waived) created_by TEXT created_at TIMESTAMPTZ
When a vendor misses an SLA, the org records a credit. applied_to_bill links to the vendor bill it was deducted from. Stays pending until applied or explicitly waived.

7. Build Order

P5.1 Schema + Billing Profiles
  • Migration: create client_billing_profiles, client_service_lines, client_metered_usage
  • ALTER ganit_invoices to add billing_profile_id
  • CRUD API at /api/v1/ganit/billing/profiles
  • Billing Profiles tab in Ganit, mounted in Graha + Vikray when active
P5.2 Recurring Services + Auto-Invoice
  • Service line management UI (add/end/view history)
  • Cron extension: sweep client_service_lines WHERE auto_invoice AND period_start <= today, generate ganit_invoices with GST from the profile
  • Pro-rata calculation when a service line starts or ends mid-period, reusing next_anchor() and period_end_for()
  • Join table to prevent double-invoicing (same pattern as invoice_billing_lines)
P5.3 Metered Billing
  • Usage entry UI: manual + source-linked (from timesheets, tasks, orders)
  • "Generate invoice from unbilled usage" action — rolls un-invoiced rows into a ganit_invoices draft
  • Metered tab in Ganit, synced to CRM/Sales
P5.4 Vendor Rate Cards + SLA Credits
  • Migration: create vendor_rate_cards, vendor_sla_credits
  • ALTER ganit_vendor_bills to add sla_credit_applied
  • Rate card management UI in Ganit and Kray
  • SLA credit recording + application to vendor bills
  • PO rate auto-fill from rate cards in procurement
P5.5 Payment Ageing + Quota Proration
  • Ageing report: GET /v1/ganit/ageing?direction=receivable|payable — computed from ganit_invoices (receivables) and ganit_vendor_bills (payables), bucketed by days overdue
  • Ageing tab in Ganit, synced to CRM, Sales, and Kray
  • Sales quota proration: mid-quarter rep assignment → proportional target, using the same anchor math

9. What This Does Not Include

  • Prorated salary — stays in Manav/Vetana. Not client billing.
  • Payment gateway — permanently ruled out. Collection stays UPI-on-invoice + manual recording.
  • Multi-currency — currency column exists on profiles for future use but the engine processes INR only.
  • Dunning / overdue escalation — covered separately in P86 P3. The ageing report surfaces the data; automated reminders are a different build.
  • Platform-level billing — P1 through P4 in proposal 86. This is P5 only.
