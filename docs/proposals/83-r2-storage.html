Where the files live

Cloudflare R2, end to end: how a file gets in, how it is found again, why the test-connection button fails on correct credentials, and what the keys should look like so a person can find a file without opening the database.

Proposal 83 · 2026-08-22 · read from services/storage.py (583 lines) and every caller · 3 orgs, 1 with its own bucket

1 · The architecture, in one sentence

Every org gets its own Cloudflare account and its own R2 bucket, with credentials stored encrypted on staging.organisations. An org that has none falls back to the vendor’s platform bucket, where its files live under org/<org_id>/.

Today: 1 of 3 orgs (Unicode Group) has its own bucket. Aekam Inc and the test org are both on the platform bucket.

The commercial reason is that each Cloudflare account carries its own 10 GB free tier, so storage cost scales with customers rather than with us.

Upload — what actually happens

caller  upload_file(bytes, filename, content_type, user_id, folder, org_id)
   │
   ├─ ext    = Path(filename).suffix
   ├─ prefix = folder  or  "personal/{user_id}"        ← the default nobody chose
   └─ key    = "{prefix}/{uuid4().hex}{ext}"           ← original filename DISCARDED
        │
        ├─ LOCAL_STORAGE_PATH set? ─→ write to disk, return /local-files/ URL
        │
        └─ _resolve_r2(org_id) ─→ (client, bucket, key_prefix)
              ├─ org has own credentials  → (org client,      org bucket,      "")
              ├─ else platform env vars   → (platform client, platform bucket, "org/{org_id}/")
              └─ else                     → raise StorageNotConfigured (503)
                    │
                    key = key_prefix + key
                    put_object(Bucket, Key, Body, ContentType)
                    return { url: presigned GET, key, name, size, bucket }

The read path is cleverer than it looks, and the prefix is load-bearing

Every reader — sign_key, download_file, delete_file, refresh_signed_url — goes through one function, _client_for_key, and it decides the bucket from the key itself:

key starts "org/" or "shared/"  →  the PLATFORM bucket
otherwise                       →  this org's OWN bucket

That is why the org/<org_id>/ prefix exists, and it is not decoration. An org that adds its own credentials later keeps working: its old files stay signable against the platform bucket instead of 404ing against a new, empty one. Any scheme proposed below has to preserve this rule — which is why the new grammar does not simply prepend org/ to everything.

Why there is no third fallback

There used to be. With no bucket resolved, upload_file base64’d the bytes into the string it called a URL, and every caller wrote that string into its column. Two of three orgs had no credentials, so 11 files — 99 MB — accumulated inside database rows while every screen reported success. Moving them to R2 on 2026-08-19 took the database from 82 MB to 49 MB.

It now refuses with a 503. A refused upload is visible and recoverable; a stored one is invisible, compounding, and cannot be re-signed, expired or streamed.

2 · Two bugs, both found today

Bug 1 · Test connection fails on credentials that work

This is the one you hit while creating an org. The whole test is:

async def verify_r2_credentials(account_id, access_key, secret_key) -> dict:
    client = _build_client(account_id, access_key, secret_key)
    result = await ...(client.list_buckets)          ← account-level operation
    return {"valid": True, "buckets": [...]}

ListBuckets is an account-level permission. A Cloudflare R2 API token scoped to a single bucket — the least-privilege setup Cloudflare itself recommends, and the one most people create — cannot list buckets, and returns AccessDenied. That same token can read and write its bucket perfectly.

So the button fails on correct credentials, and the org cannot be created. The test is stricter than the thing it is testing.

It also never tests the bucket. R2Credentials carries bucket_name (defaulting to kartavya-storage) and the verifier is called with three of the four fields. The one thing that must work — writing an object to that bucket — is never attempted.

The fix: test what you are about to do

  1. head_bucket on the named bucket — does it exist and can this token see it?
  2. Write, read back and delete a tiny probe object under _probe/<uuid> — the actual capability being bought.
  3. Report which step failed, so “the bucket does not exist” is distinguishable from “this token cannot write”. Keep list_buckets only as an optional extra, never as the gate.

Bug 2 · The org id appears twice

routers/pahchan.py:467 builds its folder as f"pahchan/{org_id}/punch". On the platform bucket the resolver then prepends org/{org_id}/, so the stored key is:

org/64e7bea6-.../pahchan/64e7bea6-.../punch/9f2a....jpg
    └── added by the resolver ──┘   └── added by the caller ──┘

Harmless to reads, because the key is stored verbatim. But it is a caller reaching for a namespace the layer below already owns, and it makes every punch key twice as long as it needs to be. Nothing else does this: projects/{team_id} and crm/{client_id}/documents both scope by entity, not by tenant.

What is wrong with it

  1. Four different grammars for the same idea. A reader cannot predict a key without reading the caller.
  2. eSign has no entity id at all. Every signature ever captured, for every document, sits in one flat prefix. To answer “show me the files for this agreement” you must query the database; the bucket cannot answer it.
  3. No date, anywhere. So there is no cheap listing, no retention sweep, and no lifecycle rule — and 1,659 punches today becomes hundreds of thousands with any real customer, all in one prefix.
  4. The original filename is thrown away. The key is {uuid}{ext}, so a bucket listing is unreadable and a support question starting “I uploaded Invoice-Mar.pdf” cannot be answered from storage.
  5. crm/unfiled/documents is where a document goes when no client is known — a bucket of last resort that nothing ever revisits.
  6. Deleting an entity cannot delete its files, because its files are not gathered anywhere.

4 · One grammar

The owner’s shape, stated as four examples:

esign/document/user_id/...
projects/{team_id}/user_id/...
personal/user_id/...
pahchan/org#_id/user_id/...

The rule underneath them: the module owns the top folder, then what the file belongs to, then who did it, and the acting user is always the last folder before the files. Applied everywhere, with a date partition added so that retention and listing are possible at all:

{module}/{belongs to}/{kind}/{user_id}/{YYYY}/{MM}/{ulid}--{slug}{ext}

Two places the shape collides with the layer below — both need a decision

1 · pahchan/org#_id/ — the org is already there

The storage layer supplies the tenant itself, and it does so differently depending on which bucket the org is on:

own bucket       key_prefix = ""                 the BUCKET is the tenant
platform bucket  key_prefix = "org/{org_id}/"    the PREFIX is the tenant

So writing the org id into the caller’s folder as well is redundant on an org’s own bucket (the whole bucket belongs to them) and duplicated on the platform bucket, which is bug 2 above — the id appears twice in one key. It is never load-bearing, because no reader ever parses it: the key is stored verbatim and _client_for_key only looks at whether it starts org/.

Recommendation: leave the org out of every caller’s folder and let the layer that owns tenancy keep owning it. If you would rather see it, the honest way is to make the Storage tab display the resolved org above the key, not to write it into the key twice.

2 · esign/document/user_id/ — which document?

Written literally, this loses the one thing eSign most needs: every signature for every agreement still shares a folder, so the bucket still cannot answer “show me the files for this agreement”. The table above therefore reads the second segment as the document’s id — matching projects/{team_id}/, where you did write the id.

That also keeps “a folder per kind of content’’ from the earlier instruction: kind sits between the document and the user, so one agreement’s four file types stay together under one document folder.

Sahayak images are the worst case, and they hide the user entirely

Both places that store a generated image (ai_router.py:2168 and :2491) pass:

filename = f"srijan-{uuid4().hex[:8]}.{ext}"
user_id  = "system"                 <-- hardcoded, at BOTH sites
folder   = "srijan/images"          <-- flat

So every image any person generates, for any purpose, lands in one folder under a random name, and the person who asked for it is never recorded on the file at all — not in the folder, not in the filename, not even in the user_id the storage layer was handed. The personal/{user_id} fallback would not have helped either, because the value passed is the literal string system.

Two fixes, independent of everything else here: pass the real requesting user (one line at each site), and give the content type its own folder, taken from the brief Srijan already holds when it calls upload.

What this buys, concretely

  • A key explains itself. Paste one into a ticket and anybody can say what it is, whose it is and when it arrived — without a database.
  • “Everything this person uploaded” and “everything for this client” both become prefix listings instead of impossible questions.
  • Retention becomes possible. Punch photos older than the policy window are a date prefix, so a lifecycle rule can expire them — which the Pahchan retention setting currently promises and cannot deliver.
  • ULID sorts by time, so a listing is chronological for free, and stays unguessable.
  • The filename survives, so support can search for what the customer actually called it.

On the names-not-ids rule

The standing rule is that a user, member or org id is never rendered in the UI, and a storage key contains ids by nature. These do not conflict, but the distinction is worth stating: the key is a machine address, not a way of naming a person. So the panel shows the human label first — Supply Agreement, Kasti Pranami — and the key underneath as a technical, monospaced, copy-to-clipboard field, the way a support tool shows a request id. It is never the primary label for anybody or anything.

6 · Getting there without breaking the past

Old keys must keep working for ever, so nothing here is a rename. Four steps, in order:

#StepRisk
1Fix the test-connection check — head_bucket plus a probe write, reporting which step failed. Unblocks org creation immediately and is independent of everything else. none
2One build_key() helper in storage.py, with the grammar and a test per module. Callers stop hand-writing folder strings; upload_file keeps accepting a raw folder so nothing breaks mid-migration. none
3Move callers over one module per commit — eSign first, since it has the most to gain. New files get new keys; old files are not touched. Reads already resolve from the stored key, so both shapes coexist. per module
4The Storage tab, once at least one module writes the new grammar.additive
A backfill of existing keys is deliberately NOT proposed. It would mean copying objects and rewriting every column that stores a key, to buy tidiness on files nobody is looking for. The grammar pays off on what arrives next.
