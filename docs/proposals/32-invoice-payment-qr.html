What this demo is showing

  • The payment block sits between the amount-in-words panel and the bank details, so it survives a page break as one unit and never splits a code across pages.
  • Each card is bordered in the payment service's own brand colour, with the wordmark in the centre of the code. Error correction is set to level H, so the centre hole costs no scannability.
  • The org enters one VPA per service in bank_details on the org profile. Only the ones filled in are drawn — six here, but one filled field renders one code.
  • The amount encoded is the balance due, not the invoice total, so a part-paid invoice collects the right figure.
  • Nothing is drawn at all when the invoice is paid, cancelled, or the balance is zero.

One caveat worth your decision: a UPI QR is a standard — a PhonePe user can scan the Paytm code and it will work. Six codes is therefore a branding choice, not a technical requirement, and it costs a third of the footer. The alternative is one large code plus a row of small service badges underneath.
