Automation — the architecture

Every module, every state machine, every write path, every scheduled job — measured, then a design that makes automation a property of the platform rather than a feature bolted to two screens.
Aekam Inc · 9 August 2026 · proposal 41 · supersedes 39 and 44, both rejected

What changed in this pass. 44 audited the two automation screens. That was the wrong unit of analysis. This document audits the product: 46 live tables that carry a state, 25 real state machines, ~90 state-transition write sites, 13 cron jobs, 40 registered skill handlers, and 4 separate notification paths — and asks, for each, what a rule could hook onto and what is stopping it.

The conclusion is that the existing engines should not be repaired. There are zero rules in the product, so there is nothing to preserve, and the thing that is missing is not features — it is an event spine. Everything else follows from that.

0Method

Three kinds of evidence, named on every claim. Read — the path followed emitter → builder → engine → the statement that writes. Measured — read-only SELECT against the shared Supabase instance, 8–9 August 2026; nothing was written. Catalogue — the claim checked against information_schema, so "this handler reads a column" is verified against whether the column exists.

"The call site exists" is not used as evidence anywhere. Where an effect could not be shown, the row says broken, not "live".

1.4 · The action library already exists — 40 registered skills

services/skill_dispatcher.py holds a registry classified exactly the way an automation engine needs: READ (org-scoped, idempotent), DETECT (judgements, belong in front of a person), ACT (writes, sends, moves things). Ten ACT handlers exist: generate_due_invoices, mark_holidays_weekends, process_expiry, allocate_yearly, auto_schedule_week, execute_onboarding, send_campaign, execute_step, escalate, notify_multi. The dispatcher already meters credits, already refunds on failure, and already fails closed on missing params.

The engine must not re-implement actions. It must call these. Every action written inline inside an engine is a second copy of something the skills layer already does — which is exactly how the product ended up with two fire_automations and three copies of an invoice-sending path.

But the ACT layer has the same disease, and nobody has looked. escalate() — the handler any escalation ladder would be built on — declares five entity types and works for one:

  • "task" → staging.tasks: that table does not exist. Tasks are public.tasks. Four sibling handlers document having been fixed for exactly this; escalation_chain.py:9 was missed because nothing calls it.
  • invoice, ticket, leave_request: the query selects assigned_to, and none of those three tables has that column — UndefinedColumnError on first use.
  • deal: works.

Catalogue: every table and column checked against information_schema. This is the same class of defect as the CRM builder — a registry naming things the schema does not have — and it is why the plan below makes the action contract data that a test walks.

1.5 · Thirteen cron jobs, each a bespoke scheduler

Every scheduled behaviour in the product is a hand-written handler in routers/scheduler.py with its own cadence, its own failure semantics and its own idea of what "done" means. Three Railway services drive eleven of them; two (/cron/reports, /cron/esign) are 501 stubs that must never be armed. There is no time-trigger primitive anywhere — which is why the invoice ladder cannot simply be configured today. Read + env.

2The true state — what is broken, before anything possible

Zero rules exist. public.automations 0 · staging.graha_automations 0 · staging.prachar_automations 0 · staging.graha_automation_logs 0. Nobody has ever created one. Measured.

Two consequences, both load-bearing for this plan: nothing is at risk from a rewrite, and none of this has ever been exercised by a real user.

Two things that are right, and should not be "fixed"

Prachar's automations are honestly closed — tab unmounted, endpoint 501 naming the reason, tripwire test that goes red the day an engine lands. That is the pattern the rest of this should copy.

The statutory gates have not drifted. Supplier GSTIN, supplier PAN and recipient GSTIN are all advisory on an invoice; blocking is only invoice number, invoice date, supplier name, recipient name and line items — document identity, not registration. GSTR-3B blocks on GSTIN, which is correct: a return is filed against a registration. Read, all four. One stale sentence: the invoice-email docstring (ganit.py:836) still lists "the 409 for an org with no GSTIN" among refusals it inherits. That 409 is gone. Prose only — but it is the sentence that would talk the next person into restoring the gate, and I would delete it with the first stage of this work.

3Diagnosis — why repair is the wrong move

Six structural faults. Each one alone would be survivable; together they mean any per-screen fix is temporary.

  1. There is no event spine. Triggers are hand-written fire_automations(...) calls at six sites, against roughly ninety status-transition write sites across sixteen routers. The default behaviour of a new feature is to emit nothing, silently. This is not a bug that gets fixed once; it is the shape of the system.
  2. Two engines, sharing a function name and nothing else — two tables, two trigger vocabularies (measured: disjoint, zero overlap), two builders, two log formats, two idea of what "success" means.
  3. The config contract exists in one engine and not the other. The task engine learned to declare, as data, which keys each action reads and which it cannot run without. Its sibling was never given the same treatment — and the file's own header documents the bug class while the sibling still has it.
  4. Actions are re-implemented inline instead of calling the skills layer that already meters credits, fails closed and refunds.
  5. Nothing is idempotent, replayable, or simulatable. There is no event id, so a retry double-acts; no dry run, so the only way to learn what a rule does is to let it do it to real customers.
  6. There is no time primitive. "Three days after the due date" cannot be expressed at all — it must be a new cron handler, which is why there are thirteen of them.

4The architecture

4.1 · The spine: one event outbox

A new table, staging.org_events — deliberately not audit_log, which is a security log an org admin reads and the retention cron prunes.

org_events(
  id           bigserial,
  ts           timestamptz  default now(),
  org_id       uuid         not null,      -- every live business table has one
  entity       text         not null,      -- 'ganit_invoice', 'graha_deal', 'task'
  entity_id    text         not null,      -- text: tasks are 'task_<hex12>', not uuid
  verb         text         not null,      -- created | updated | deleted
  changed      jsonb,                      -- {"payment_status": ["unpaid","paid"]}
  snapshot     jsonb,                      -- the row as it is now, allow-listed
  actor_id     text,                       -- null = system/cron, and that is meaningful
  source       text,                       -- 'api' | 'cron' | 'webhook' | 'migration'
  dedupe_key   text unique                 -- makes replay safe
)

How events get written — and the honest trade

Two options, and I recommend the hybrid.

Application emit()Postgres row triggers → outbox
CoverageOnly where somebody remembered. Today: 6 of ~90. Total, by construction. A new router cannot forget.
Knows the actorYesOnly if the app sets a session variable
Knows intentYes — "invoice sent" vs "row updated"No — infers from the delta
Fires on migrations and backfillsNoYes — must be suppressible
Cost of adding a moduleEvery write siteOne CREATE TRIGGER

Hybrid: row triggers on the 33 live business tables give complete coverage; the application supplies actor and intent through SET LOCAL kartavaya.actor / kartavaya.source on the request connection; and every migration and backfill runs under SET LOCAL kartavaya.suppress_events = on. That last part is not optional — staging and production share one database, and a backfill that emits 759 invoice events would fire every rule in every org at once.

The tasks exception resolves org_id through teams.org_id and drops the event when it is null, rather than writing a row that violates the foreign key.

4.3 · Conditions — typed against what the event actually carries

The task engine died on this: the builder offered three fields, the event carried none of them, and the rule silently never fired. The fix is structural — the condition editor is driven by the entity's field registry, and only offers fields the event's snapshot carries. A field that cannot be evaluated cannot be selected.

  • Typed operators per field type: = ≠ > < between in not-in is-empty changed, contains for text and tags, within/older-than for dates.
  • AND/OR groups, one level of nesting. Not a full expression language — a firm has to be able to read it back.
  • Related-entity lookups, one hop, declared: invoice → contact.tags, deal → owner.department. One hop only, because two hops is a query planner.
  • Business-calendar awareness: "3 working days", honouring manav_holidays, which already exists.

The config contract, stated once

Each action declares — as data, not as cfg.get() calls — the keys it reads, which are required, and which must merely be present. That table drives three things at once: the builder's form fields, the save-time refusal, and a parity test that goes red if either side is renamed. It is exactly what fixed the task engine; the point here is that no action can be added without it, so the CRM failure cannot recur in a new module.

4.5 · Execution — the rules that make it honest

  1. An action reports success only if it did something. Unknown action type is a failure with a reason, never a silent fall-through. This is CRM fault #1, made structurally impossible.
  2. Idempotency on (rule_id, event_id). A retry, a replay or a double delivery cannot act twice.
  3. Stop conditions re-checked immediately before every step, not only at enrolment. A ladder that dunned a customer who paid yesterday is the failure mode that matters, and a five-day-old decision is not a current one.
  4. Delivered ≠ handed off. The run row records what outbound actually did, including suppressed. Fault #5 is a reporting bug before it is a delivery bug.
  5. Recursion depth and per-org ceilings, with the ceiling visible on the screen rather than silently truncating.
  6. Dry run and simulation. "What would this rule have done over the last 30 days of real events" — answerable from the outbox before the rule is ever switched on. Nothing in this product has ever had this, and it is the single largest safety gain in the document.
  7. Kill switches: per rule, per org, global. And a first-run confirmation for any rule whose first tick would touch more than N records — the /cron/reminders lesson, which would have written 254 rows on its first tick.
  8. Every run visible on the record it touched — a timeline on the invoice, the deal, the leave request. A log on a settings page is not where anyone looks.

4.6 · Where it lives, and who may touch it

Under the existing /automations, per your rule. One page, three tabs — Rules, Runs, Templates — with a module filter rather than a separate screen per module, and the same builder embedded in each module's own settings tab so a CRM admin does not have to leave Graha. The CRM tab and the task page both become views of one engine.

  • Rules are scoped to the org and gated on the module: an org without Vetana cannot write a payroll rule, and an org that loses Vetana has its payroll rules paused, not deleted.
  • Editing requires org owner/admin or the module's own admin. Running touches whatever the rule touches, so the rule executes with the permissions of its author, recorded on the rule — an automation must not be a way to act beyond your own reach.
  • Sensitive modules (vetana, ganit, manav, pahchan) keep their existing extra gate: no rule may move money, and salary-reading rules are org-admin only.

6Build order

Ordered so that each stage ends with something observable, and so nothing that lies survives into the next stage. The approved invoice ladder is S3 — it arrives early because it is the proof the spine works, not because it is bolted on first.

  1. S0 · Tell the truth about what exists. The CRM log stops reporting success for work that did not happen; the dead triggers come out of both builders; escalate()'s four broken entity types are fixed or removed; the stale GSTIN docstring goes. No new capability — this is the stage that makes everything after it measurable. Observable: a rule that does nothing now says so.
  2. S1 · The spine. org_events, row triggers on the 33 live tables, session variables for actor/source, the suppression switch for migrations. Nothing consumes it yet. Observable: every state change in the product appears as a row, and a week of real events accumulates to test against.
  3. S2 · The engine. Rules, runs, steps; the config contract as data; typed conditions from the field registry; idempotency; the wait primitive; dry run against S1's real backlog. One page under /automations. Observable: a rule can be simulated over last month's events before it is ever switched on.
  4. S3 · The invoice reminder ladder — the approved work, now expressible as configuration. Addressed to the customer, not the invoice's author; carrying the pay link and the PDF that P3 and P5 already built; stop conditions re-checked before every step; the run history on the invoice drawer. Observable: a real ladder, and a reminder history you can read. Gated on the delivery decision in §7.
  5. S4 · Retire the duplicates. The four reminder scan blocks, the stalled task_reminders system with its 94 unsent rows, and auto_send all become rules on the engine. Thirteen cron handlers become one time sweep plus the genuinely bespoke jobs. Observable: one reminder table, one cron, one place to look.
  6. S5 · CRM and Core PM onto the engine. Both existing engines deleted — zero rules to migrate. Conditions on priority and assignee work because the snapshot carries them.
  7. S6 · Manav and Vetana. The largest untouched surface: leave, probation, offboarding, attendance patterns, payroll variance, statutory dates. Mostly wiring existing skills to triggers.
  8. S7 · Vikray, eSign, Prachar enrolment, Sahayak review. Prachar's tab is remounted and its 501 lifted the day its triggers exist — the tripwire test is already written to demand exactly that.
  9. S8 · Templates. Ten or fifteen prebuilt rules an Indian firm switches on in one click — the payment ladder, the GST calendar, the probation reminder, the stale-deal chase. This is what makes it feel finished, and it should be built last, from rules that have run.
  10. S9 · WhatsApp as a channel, when an org has a connected number.

What I am not proposing. No visual flow canvas — trigger → conditions → actions is the shape the page has and the shape a firm can read; if you meant the canvas literally, say so and I will re-plan, it is roughly a quarter more work. No autonomous AI writes: Sahayak may draft and suggest, never act unattended. No rule may move money.
