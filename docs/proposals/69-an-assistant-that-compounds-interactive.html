Your database is not big

You pushed back on 49 MB, so I broke it apart. It holds 28,589 rows across 282 tables — and most of what you are looking at is not your data:

WhatSizeCan it shrink?

So: 49 MB is roughly the smallest a schema this wide can be. 126 of your 282 tables are genuinely empty — schema built ahead of the product. The part that was actually wrong was the 33 MB of screen recordings, and that is fixed. For scale, Supabase’s free tier is 500 MB.

Now the correction

A model does not learn from your database. Nothing written to Postgres changes a single weight, and at 208 messages there is not enough signal to learn from statistically even if it did. Anyone offering to fine-tune at this volume is offering an expense that also welds you to one vendor.

The one everybody asks for first

A semantic answer cache — right idea, wrong month

Cache an answer against a question’s meaning, serve repeats free. Standard advice, and the measurement does not support it: of 104 questions ever asked, 102 were distinct. Two repeats in the product’s lifetime. A cache would buy storage and a correctness risk — every cached answer must die when the data behind it moves — to save $0.00.

Build it when a trigger fires, not before: repeat rate above ~20%, or spend above ~$50/month. Both are one query away at any time, and the cache is a week of work whenever that day comes.

What I would not build

  • Fine-tuning. 208 messages is not a dataset. Real money, one vendor, nothing measurable.
  • Embedding everything by default. This is where database bills actually explode. Embed the knowledge base and nothing else until a measurement says otherwise.
  • An external vector database. pgvector 0.8 is already installed, and the database stays on Supabase.
  • Model-extracted “user memory” on every turn. A model call per message to learn preferences buys guesses at the price of the thing being guessed about.

Order of work

Phase 1 — free, no migration, no decision needed start here

Latency-ordered routing, the glossary, the eval set in CI, full-text knowledge-base search, and feedback wired into the evals. Files, existing tables and query changes. Nothing touches the shared database.

Phase 2 — small, still cheap

Question → metric mappings and rolling conversation summaries. Both want Phase 1’s eval set first, so their effect can be proven rather than asserted.

Phase 3 — the migration, only when it earns itself your call

Embeddings and the semantic cache. The only part that touches the schema, and the only part needing your word — the vector column has to be widened, and the shared database means production feels it. It is free to do now only because the chunk table is empty, and that stays true only while it stays empty.

The fork, when you get there: bge-m3 at 1024 dimensions is free on the HuggingFace key you already have and scores 0.899 across English/Hindi, but needs the column widened. e5-base at 768 fits today’s column and scores 0.938, but truncates near 512 tokens while chunks are 500 words, so chunk size must drop to ~350. OpenRouter sells no embedding models at all — I listed the catalogue to be sure.
