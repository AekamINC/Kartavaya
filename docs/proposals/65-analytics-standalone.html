Analytics without Dristi

Not every org will buy the reporting module. The rule this plan builds to: whatever modules an org holds, each one carries its whole analytics story on its own page — see the numbers, download the file, schedule the email, set the alert — and Dristi remains the cross-module room for those who have it, never the gate for those who don’t.

The entitlement half is already true and needs no work: the catalogue withholds by source module, so a Ganit-only org already sees Ganit analytics on GanitPage with no Dristi anywhere. What is missing is everything around the numbers — the files, the schedules, the alerts — which today either live only in Dristi or exist only as API.

2 · The rule

Analytics lives where the work lives. A module’s page answers everything about that module: the figures, the file of the figures, the weekly email of the file, and the threshold that raises an alarm. Dristi keeps what is genuinely cross-module — the pivot, the blended dashboards, the client report’s CRM-beside-spend blend — as a richer room, not a prerequisite. Nothing below adds a single new place where dristi is checked.

3 · The plan

S1 — Download chips on every widget ½ session

The Downloads component the Ganit cards already carry, mounted on every ViewGrid widget. Same URL, format= swapped — the file can never disagree with the card. Nothing server-side to build.

S2 — The module report: one file per page 1–1½ sessions

GET /v1/analytics/module-report?module=&date_from=&date_to=&format= renders the module’s resolved arrangement — saved view, else preset, else the derived default; the same resolution the screen performs — as one XLSX (a sheet per widget) or one PDF on the org’s letterhead. A Download button sits beside Customise on every module tab. Filename carries module and period, never an id. This is A6’s discipline (“format is a parameter”) applied to a whole page, and it is the artifact S4 emails.

S3 — Alerts get their screen 1 session

A bell on every KPI widget — “tell me when this crosses…” — and a small thresholds panel on each module’s analytics tab listing that module’s alerts. Org-admin to write (the API already enforces it); everyone may see. Breaches already flow: the sweep evaluates analytics_alerts every 15 minutes and raises metric.threshold Niyam events, and the metric-threshold-tell-admins starter rule delivers them. The whole D7 pipeline is built and idle for want of this screen.

S4 — Scheduled delivery, through Niyam 1½–2 sessions

Retire the parallel Dristi-only scheduler rather than arming it. A report.due temporal predicate (the schedule is the dedupe window — daily/weekly/monthly, the attendance-summary pattern) plus a report.send action verb that renders S2’s file and attaches it — replacing today’s JSON-dump body. Every module tab gains “email me this weekly”; recipients are staff tokens, membership-filtered; OUTBOUND_MODE and the owner’s arming decision sit underneath, exactly like every other send. One delivery spine instead of two half-built ones; the existing dristi_scheduled_reports rows migrate into rules.

S5 — The client report’s second door ¼ session

Mount ClientReportTab in Graha (its natural audience: the CRM). The backend already serves Graha-only callers; only the door was Dristi’s. The Dristi tab stays.

S6 — Homes for the homeless three ½ session + one decision

Pay is already home: its four metrics are declared under Ganit and appear on Ganit’s tab — state it, build nothing. Niyam’s metrics are core/work figures; its console gets a small stats strip (runs, outcomes, events this week — numbers its own history screen already knows). Sanvaad is the one decision: its chat shell has no tab strip, so its four metrics either get a small analytics drawer inside the chat surface, or stay Dristi-only — owner’s call, both honest.

S7 — Mobile, later deferred

A read-only analytics screen per module in the phone app, riding the same catalogue and /run. Nothing blocks it; nothing hurries it. After the catalogue settles.

4 · Gates and guarantees, unchanged

  • Entitlement is the module. The catalogue withholds by source module; a page you cannot read has no analytics to show you. Dristi is never consulted.
  • Writes are org-admin. Alerts, schedules and org-scoped views stay behind the same admin gate the API already enforces.
  • Absence is stated, never zero. Not-yet-measurable metrics keep their reasons on every module’s page and inside every file.
  • Every file is the org’s paper. Letterhead on PDF, identity header on XLSX, period in every filename; names, never ids.
  • Sends obey the stack. OUTBOUND_MODE, staff-token recipients, membership filtering, and the owner’s arming switch — S4 adds no new transport.
  • The window cap holds. Five years is the maximum span everywhere, files included.

5 · Order and cost

S1 → S3 → S2 → S4 → S5/S6 — alerts before the module report because the D7 pipeline is finished and dark, and one screen lights it. Roughly 5–6 sessions end to end. S4 is the only phase with a migration (schedule rows → rules) and the only one that touches delivery; everything else is additive UI over APIs that already exist.

6 · Risks, plainly

  • S4 replaces a half-built thing people can see. The Dristi Reports tab works as CRUD today; the cutover must migrate its rows and keep run-now working, or it reads as regression.
  • The module report renders arrangements of arbitrary size. Cap widgets per file the way the screen caps its derived default; state what was cut in the file itself.
  • Alert sprawl. Thresholds are org-admin-only and capped per org (the API already caps at 200 checks per sweep); the screen should show the cap honestly.
