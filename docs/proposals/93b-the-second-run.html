All of it again — half the work, none of the scope

Same phases. Same stages. Same waves. Same 22 suites. Same two rules, the same target, and the same reason. Every population halved so it fits a night instead of a weekend — and rewritten against everything docs/plans turned up after v3 was written.

Why this one is different from every run before it

Every previous pass drove staging. This one drives the thing customers get. main is now staging @ 16f6fdfb — 1,898 commits — and production runs the same code and the same schema. Verified live, not assumed:

production /api/health -> {"schema":"staging","environment":"production"}

So the rehearsal is the performance. Every row typed lands in production. Every delete removes production rows. Every defect found is one a paying customer would otherwise have found first. That is not a reason to do less of it — it is the reason it matters most. It is a reason the gates get harder, and §5 and §7 are where that shows.

What "50% less work" means here, precisely

Nothing is removed. All 22 suites run. All 9 waves run. All six stages run. R0 through R9 all run. Suite 00 still goes first, Stage 4 still replays on UK, Stage 5 still does both AVDs, §12 still guards Aekam Inc, §13 is still excluded-by-decision rather than blocked.

What halves is the number of rows behind each assertion. 30 employees becomes 15. 45 invoices becomes 20. 240 punches becomes 110. The path is driven exactly as many times; it just carries less freight.

About twenty counts physically cannot halve — six bad passwords is the rate limiter, three bank files is three positional parsers. Those are held, and the elastic populations are cut deeper to pay for them, so the programme total still lands on 50%. §4 shows both halves of that arithmetic.

1The rule this is built on, and the target

Rule 1 — every row is typed by a user

Playwright opens the page, fills the form, picks from the real picker, uploads the real file, clicks the real button. Nothing is inserted by SQL and nothing is posted straight to an API. A row created by SQL proves the table exists; only a row created by a click proves the product works. There is no exception anywhere in §4 — and halving the volumes does not create one.

Gate: frontend/scripts/check-e2e-no-bypass.mjs. Five bypasses in real-user.spec.ts are baselined and owned by Suite 08, and that number may go DOWN, never up. page.request.get is verification and is allowed; a write is not. Minting a token is the precondition for the rule, not a breach of it.

Rule 2 — stop and fix, and prove which it was first

What happenedWhat happens next
A step fails or does the wrong thingStop. Fix the product. Re-run it green. Then continue. Nothing is reported complete with a known failure inside it
It's the test's own faultFix the test — after proving it. Suite 02 opened 3/7 and three of four failures were test bugs; last session four checks accused the product and all four were wrong
Blocked on the ownerdocs/OWNER-ACTIONS.md, in that file's own format, and the run continues past it. A skip that lives only in a run log is a skip nobody actions
A missing feature, not a bugLedger + evidence + estimate; run continues. This programme does not silently build features it wasn't scoped to build
Excluded by decisionNot a failure. Not run. Recorded as a choice — never blurred with "couldn't test"

Rule 3 — never write without asserting the org first

assertOrg() asserts the org ID, never the name. The name is what got corrupted: a platform_admin credential resolved every request into Aekam Inc through platform_bypass, the save genuinely succeeded, and the suite went green while renaming the one org this programme guarantees is untouched. Write suites use org-scoped accounts only. God mode is Suite 19 and nothing else.

The target — the owner's words, and they do not change

"Imagine giving a client a completely new org, and then they start using it and things break and they are not happy. Start from thinking that you are the client who will be using this."

"Every function works" and "a new customer's first week works" are different questions, and the second is the one that loses customers. Three consequences, all unchanged by halving:

  • Delete first, then build from zero. A suite written against a populated org can silently depend on rows it did not create — it passes, and nobody knows whether the code works or a client already happened to exist.
  • An emptied org is not a new org. Unicode keeps its profile, GSTIN, state, R2, senders and series — the configured-org lane. UK AekamINC gets its configuration cleared too and is built from nothing — the brand-new-org lane. Two fidelities, no sixth organisation.
  • A new customer doesn't work in dependency order. They try payroll on day one with no employees and open Reports before anything exists. That disorder is where the ugly failures live, and Suite 00 runs first, at full size, because it creates no data to halve.

What "driven as a user" means — the interaction vocabulary is the deliverable

A row landing in a table proves the write path and says nothing about whether the drawer opened, the drag persisted, the tooltip appeared, or the button was reachable by keyboard. Every defect this product has shipped in those classes was invisible to the database. Each interaction asserts its own observable consequence — never merely that it did not throw.

Provider, region, senders and the recipient mix are all unchanged: AWS SES, ap-south-1, nine purposes per org on the already-verified unicodegroup.com, and the recipient mix 5% / 20% / 30% / 45% AWS mailbox simulator. The simulator is reputation-exempt, so the whole mass-bounce hazard stays structurally absent. Volumes halve to ~115 sends per org, against a 50,000/day quota — never a constraint.

⚠ What did change, and it is the sharpest edge in this rescope

OUTBOUND_SUPPRESSED_ORGS is EMPTY on both environments — suppressed_orgs_digest: "0" — despite code comments describing it as holding E2E's ~1,600 @example.com addresses. And outbound.py:181 defaults the mode to live.

So OUTBOUND_MODE=dry is the only protection there is, on a schema production now shares. During the promotion a bulk variable paste silently reverted it to live while the Railway variable list still displayed the old value. Rescoped rule: outbound state is read from /api/health, on both environments, at R0′ and again immediately before Suite 11 — the one suite that mass-sends. Never from the variable list. The mode itself is decision 2 in §9.

Still true and still worth stating honestly: without a webhook the product cannot learn a bounce happened. There is no SNS endpoint and outbound_log has no bounced status — the vocabulary is queued · sent · suppressed · failed. The 45% proves the full send path runs for every one of those addresses. It does not prove bounce handling, because there is none. The simulator makes those bounces free and harmless; it does not create the feature. Scoped separately, not folded into this estimate.

How the knob gets built — because it does not exist yet

v3 promised the specs take a volume constant. Checked: 8 of 24 suites do — 103 const N_* = n declarations. The other sixteen embed volume in hand-built arrays (suite07 holds a literal 30-employee array with names, codes and work states) and in derived counts — "18 linked to logins", "150 roster cells", "12 employees × 5 days" all descend from that 30. Slicing the array without re-expressing the derived counts breaks them silently.

  1. frontend/e2e-real/_volumes.ts — SCALE from the environment, scaled(n) flooring at a minimum of 1, and a HELD registry scaled() refuses to touch.
  2. Route the 103 constants through it, with the dependent pairs asserted in the module: N_FINAL + N_DRAFT === N_INVOICES is checked, not hoped for.
  3. Make the sixteen literal suites sliceable — the array stays the source of truth, and every derived count is re-expressed against the sliced length.
  4. Prove it bites. Put a held count through scaled(), watch it go red, restore. A knob nobody has seen refuse is decoration — the same sentence assertOrg earned the hard way. And SCALE=1 must reproduce v3's numbers exactly before 0.5 is trusted.

5Fixtures and the R2 sweep — three corrections that change the method

Fixtures halve: 15 synthetic faces, 110 punch selfies re-used from that set, 6 multi-page PDFs for eSign, 4 KB documents with answerable facts, ~20 mixed attachments plus the oversized file, 2 org logos. held at 3 the bank statements — parsing is positional, so a hand-written file with the right headers and wrong column order proves nothing.

⚠ Correction 1 — Aekam Inc is NOT isolated from the whole wipe

§5 concluded that because each main org has its own bucket in its own Cloudflare account, Aekam is protected by "a physical separation". True for Unicode and UK. False for E2E. E2E has r2_bucket_name NULL and no credentials, so it falls through to the platform bucket — R2_BUCKET_NAME=aekaminc, R2_PREFIX=staging/ — the same bucket Aekam Inc uses.

Corroborated by key shape, not inferred: staging/e2e/sign-doc-35.pdf against Unicode's pahchan/<org_id>/reference/<uuid>. So a prefix-level delete in the platform bucket is the catastrophic case §5 believed it had designed away. Key-list deletion is not merely preferable — it is mandatory.

⚠ Correction 2 — "E2E has no R2" is wrong

§5's org table records E2E as R2: no and skips the file suites there "by design". E2E holds 51 real sign_documents.file_key objects. It has no bucket configuration, which is not the same as having no files. Rescoped: E2E's file suites are not skipped, and its 51 objects are in the key list.

⚠ Correction 3 — the table list was incomplete, and empty string is not NULL

Eleven more key-bearing columns exist that §5 never names — pahchan_punches.photo_key, pahchan_regularisations.evidence_key, manav_candidates.resume_key, hub_content_items.image_key, hub_scraper_runs.results_r2_key, ganit_contracts.file_key, organisations.logo_key, the three sign_documents keys, and message_attachments.r2_key. Several tables carry only a *_url and no key at all, so their objects can only be recovered by parsing the public prefix off the stored value — real work the sweep needs. And manav_assets, which §5 does name, has no key column at all.

And the one that nearly produced a wrong inventory: file_key IS NOT NULL counts rows holding ''. The first pass reported E2E at 211 objects and Unicode at 89; filtering on nullif(btrim(col),'') IS NOT NULL gives the true 51 and 73. A sweep written from the naive predicate goes hunting ~150 objects that do not exist — and reports them as deleted.

So the sweep, rescoped

  1. Enumerate from the database, every key column above, with nullif(btrim(...),'').
  2. Subtract the protected set's keys — 11 of the 20 protected tasks carry a non-empty attachments jsonb. Enforced by set arithmetic, not by care.
  3. Subtract anything not under an org — personal/<user_id>/ and shared/ belong to people, including the users being kept.
  4. Delete key by key, count reported. Three buckets, three credentials. No prefix delete, no bucket operation, ever.
  5. Re-run the inventory immediately before the delete — the numbers above are a 28 Aug measurement, and the whole point of the ordering rule is that the list is current when it runs.

Sequencing gate: the inventory is captured in R2′, before the rows go in R4′. After the delete the references are gone and the objects are orphans — paid for, unreachable, unattributable. Capturing it late is the one ordering mistake that cannot be undone.

6Runtime

~18,000 interactions — ~11,300 data entry, ~4,500 sweep clicks and ~2,200 non-click events — at 1.2–2.0 s each is 6–8 hours single-threaded. Sharded across the wave graph with dependency order respected, that is a ~2 hour run. Designed to run overnight and to be re-runnable from empty, because a seed you can only build once is not a test.

Gate: the run is idempotent — a second execution recognises its own output and verifies rather than duplicating. §6 idempotence is proved by running the suite twice, never by claiming it, and the report reads "0 typed, N already present".

7The stages — all six, and what each one gates

The dividing line — what agents do, and what they never do

Agents write and run. An agent that hits a failure stops, reports, and waits — it does not diagnose and it does not fix. An agent that both writes the test and rules on whether the test or the product is wrong will, under time pressure, edit the test, and a green run over a broken product is the one outcome that makes all of this worthless.

Held in one pair of hands and never sub-delegated: product-bug vs test-bug · every delete · every migration · every go/no-go gate. During Stage 2 no agents run at all — one still driving a screen mid-delete writes rows into a half-emptied org and corrupts the evidence the programme exists to produce.
