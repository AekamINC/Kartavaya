Procurement as its own module क्रय

Proposal 85 · rescope · 23 August 2026

Purchase orders currently live as two tabs inside Finance (Ganit). Proposal 77 put them there to avoid minting a module code, but the consequence is that procurement is invisible in the sidebar, ungrantable independently, and impossible to sell separately. This proposal moves it out.

What changes

1. New module code: kray new

क्रय (kray) — Sanskrit for "purchase", consistent with the naming convention (ganit, vikray, graha, manav, vetana, etc.). Added to ALL_MODULES, HIERARCHICAL_MODULES, and LADDER_MODULES in role_tiers.py.

Under the Revenue · राजस्व section, after Finance:

4. Backend gate: require_module("kray") move

procurement.py currently gates on require_module("ganit"). Change to require_module("kray"). The router prefix /api/v1/procurement stays unchanged — the URL names the domain, the gate names the entitlement.

5. Remove from GanitPage drop

Remove the ['purchase orders', PurchaseOrdersTab] and ['po approvals', POApprovalsTab] entries from GanitPage.jsx's TABS array. Finance keeps its 14 remaining tabs.

The migration

Staging and production share one database, so entitlement rows must exist before the gate changes. Order matters.

Migration 214: insert kray into staging.module_subscriptions for every org that currently holds ganit. This is a read-only addition — no existing behaviour changes.
Migration 214 (same file): copy every staging.org_member_modules row where module_code = 'ganit' as a 'kray' row at the same level. Everyone who can see Finance can see Procurement on day one.
Deploy backend with require_module("kray") in procurement.py and "kray" in ALL_MODULES.
Deploy frontend with KrayPage, the new nav entry, and the two tabs removed from Ganit.
Shared-DB risk: steps 1–2 are additive INSERT statements — they cannot break existing behaviour. The danger window is between step 3 (backend gates on kray) and step 2 (rows exist). If the backend deploys first without the migration, the route 403s for everyone. Apply migration before deploying the backend.

What this unlocks

  • Grantable independently. An org that does books but not purchasing can turn off kray without losing ganit. An org that only does purchasing (construction, manufacturing) can subscribe without paying for invoicing.
  • Visible in the sidebar. A module that has no sidebar entry is a module nobody finds. The whole reason procurement "wasn't there" was that it was buried behind Finance's 16th tab.
  • Separately sellable. A plan can include or exclude kray the way it does esign or prachar.
  • Own KPI strip. Committed spend, open orders, late suppliers, and 194Q warnings surface on entry — not after clicking through Finance.

What stays the same

  • The API prefix /api/v1/procurement/* — no URL changes.
  • The database tables (ganit_purchase_orders, ganit_po_lines, ganit_po_receipts, ganit_po_revisions, ganit_po_approvals) — table names are not module codes.
  • Vendor management stays in Ganit (ganit_vendors) — procurement reads vendors but doesn't own them.
  • Bill linking stays cross-module — a vendor bill in Ganit can still link to a PO in Kray.
  • The product catalogue stays shared (ganit_products) — one catalogue, many surfaces.
  • All existing settings, approval rules, and data — zero data migration.

Naming decision

CandidateSanskritNotes
krayक्रयPurchase/buying. Mirrors vikray (selling). One syllable. Reads naturally beside the others.
kharidखरीदHindi/Urdu, not Sanskrit. Breaks the naming pattern.
procurement—English. Every other module code is transliterated Sanskrit.

Recommendation: kray — it is the buy side of vikray (sell), which is exactly what procurement is. The pairing is both etymologically correct and easy to remember.
