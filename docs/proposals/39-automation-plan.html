The dead triggers, by name

A rule built on any of these saves, appears in the list, and never runs. Its run count sits at zero for ever, which reads as "nothing has happened yet" rather than "this cannot happen".

This is the failure mode the whole plan is designed around. Every one of those triggers was added to a dropdown without a call site behind it. Nothing errors, nothing logs, and the screen looks finished. A firm sets up "email me when a task goes overdue", trusts it, and finds out it never ran by missing the deadline it was meant to catch.

The automation nobody can see

Meanwhile the product does automate a great deal — invisibly. There are 14 cron endpoints and a reminder service with four hardcoded reminder types (invoice_overdue, follow_up_due, approval_pending, task_due). They are real, they run nightly, and:

  • no screen lists them, so no customer knows they exist;
  • none is configurable — the timing, the wording and the recipients are in Python;
  • changing "7 days overdue" to "5" is a code change and a deploy.

So there are two automation systems: one that is configurable and mostly does not run, and one that runs and cannot be configured. The plan is to make them the same system.

2The shape

One engine. One page — the /automations route that already exists. Rules gain a module, so the page groups by module and each module contributes its own triggers and actions to a shared registry.

The four rules of the design

  1. A trigger may not appear in the picker unless something fires it. The registry declares each trigger beside the call site that emits it, and a test walks the source to prove every registered trigger has one. This is the ratchet, and it is the single most important line in this document — it is what stops section 1 happening again. Same shape as check-rendered-ids and the sender-bucket AST test, both of which have already caught real bugs.
  2. Time-based triggers come from the cron that already runs, not from a new scheduler. /cron/reminders already scans for things that are due; it emits invoice_overdue into the engine instead of building its own email. One clock.
  3. Every rule is off until switched on, and every run is logged with what it matched and what it did. graha_automation_logs already models this; it becomes the shared log.
  4. Actions that reach a customer are rate-limited and guarded — see §5. An automation that emails your client is not the same class of thing as one that sets a field.

Graha — CRM engine already runs

Four triggers fire today (lead_created, deal_created, deal_stage_changed, activity_created). Three do not (contact_updated, deal_stale, followup_overdue) — and the last two are time-based, so /cron/crm is where they belong. Fixing those three is the cheapest real win in this document.

Worth wanting: a lead with no activity for 7 days pings its owner; a deal that reaches Negotiation creates a follow-up; a client whose invoice went overdue is flagged on their CRM record, which is the first cross-module rule and the reason one engine matters.

Vetana — payroll sensitive

payroll_run_approved, payslip_disbursed, salary_revised, loan_instalment_due.
Constrained on purpose: payroll is in SENSITIVE_MODULES. Automations here may notify and may create tasks; they must never move money or approve a run. The approval is the control, and an automation that presses it removes the only human check in payroll.

Pahchan — attendance sensitive

punch_flagged, absent_without_leave, late_arrival, enrolment_approved. The punch review endpoint exists; the daily ones need a scan in /cron/hr.
DPDP line: attendance data reaches god mode only. An automation must not become a route that copies it to someone who could not otherwise see it — actions here are limited to notifying the employee themselves and their own manager.

Prachar — marketing

Retire staging.prachar_automations rather than wire it: six of its seven triggers are CRM events that Graha already fires. Marketing's own are campaign_sent, sequence_step_completed, event_registered, email_bounced.
The bounce one is the valuable one and is needs data — there is no webhook from Resend or SES today, so nothing knows a message failed.

document_sent, signed, declined, all_parties_signed, expiring_in_n_days. The first four are 1 call site each on endpoints that already exist.
Warning: /cron/esign is a 501 stub. The expiry trigger needs it built; do not arm the schedule expecting it to work.

Sanvaad / Varta — messaging

message_received and mention. Inbound WhatsApp arrives with P7's webhook, which is exactly the piece that makes P7 worth paying for. Until then this is needs data: nothing tells the product a customer replied.

Dristi / Sahayak

Dristi is a consumer, not a source: report_ready depends on /cron/reports, another 501 stub.
Sahayak contributes actions rather than triggers — draft a reply, summarise a thread, classify an incoming lead. Each costs a model call, so any Sahayak action must debit credits and must be capped per rule per day, or one badly-written rule empties an org's balance overnight.

4What a firm would actually switch on

If only five rules ever ship, these are the five — every one of them is a thing an Indian practice does by hand today:

  1. Invoice finalised → send the pay link on WhatsApp.
  2. Invoice overdue 7 days → remind the client, notify the partner.
  3. Payment recorded → thank the client, close the follow-up.
  4. Lead untouched for 7 days → ping its owner.
  5. Employee joins → create the onboarding checklist.

5Guardrails

  • No loops. An action that fires a trigger must not re-enter the engine — depth-1, enforced in the dispatcher, not by asking rule authors to be careful.
  • A per-org daily ceiling on outbound actions, and quiet hours for anything that reaches a customer. Sending reputation is shared across every org on the domain: one firm's runaway rule degrades everyone's delivery.
  • Dry run. Show what a rule would have matched over the last 30 days before it is switched on. Cheap to build, and it is the only honest way to let someone trust a rule that acts on their customers.
  • Every run logged — matched, acted, skipped, failed — visible on the same screen as the rule.
  • Sensitive modules never act, only notify. Payroll and attendance.

7What I am not proposing

  • A visual flow builder. Trigger → conditions → actions is the shape the existing page already has and the shape a firm can read. A canvas is a quarter of work that makes simple rules harder to write.
  • Arbitrary webhooks or user-supplied code. Outbound HTTP from a rule is an SSRF surface pointed at our own network, and this product holds payroll data.
  • Automating any approval. The approval is the control. A rule that grants one deletes the reason it exists.
Every claim about the current state was measured against the code on 8 August 2026 — trigger counts by grepping call sites, table names from the migrations, the marketing table's zero rows from the note already in routers/prachar.py. Where something is marked needs data it means the product does not record it today, not that it is hard.
