What Kartavaya costs to run — and what actually caps it

Measured on the live Railway project and Supabase database, 5 August 2026. Railway figures are 7-day averages over 10,081 per-minute samples per service. Nothing below is estimated where it could be measured.

Users are not your cost driver. At 20 users the app is consuming 0.59% of one CPU core. Going to 50 users across 4 organisations adds roughly $2–3/month of real load. That is the small number.

The large numbers are three decisions that have nothing to do with how many people sign in: two always-on environments, a storage fallback writing video into Postgres, and AI image generation. Today's bill is about $14/month against a $5 Railway budget — and the $5 was already exceeded twice over before a single extra user arrived.

Read the composition, not the total. Memory is 73% of the bill, egress 24%, and CPU 2.2%. Nothing you do to make the code faster will change this bill. The bill is what it costs to keep two Python processes resident, whether or not anyone uses them.

Why staging costs more than production

Staging's egress is 7.7× production's — 43.9 GB against 5.7 GB — and its CPU peaked at 0.9999 (a full core) where production peaked at 0.106. That is not customer traffic. That is the end-to-end test suites. They are worth running; they should just not run against an environment that bills by the resident minute.

finding retention-cron has recorded zero CPU, zero memory and zero maximum across the full 7-day window. It has not run once. Either data retention is silently not happening, or the service is dead weight. Both are worth knowing; only one is free to ignore.

3. The storage fallback — the one to fix first

The design is correct: attachments and generated images go to Cloudflare R2. The implementation has a fallback that does not.

backend/services/storage.py:155
    if client is None:                    # ← no R2 credentials for THIS org
        b64 = base64.b64encode(file_bytes).decode()
        return {"url": f"data:{content_type};base64,{b64}", ...}

_get_org_r2() reads R2 credentials per organisation from staging.organisations. When an org has none, the file is base64-encoded and written into the database row. Measured in public.tasks today:

Six rows are 45% of the entire database. And the reason is not exotic:

OrganisationR2 configuredMembersConsequence
Unicode Groupyes5Files go to R2 correctly
Aekam Incno9Every upload is base64'd into Postgres
E2E Test & Associatesno6Same
This is a per-org bomb, and it is armed by onboarding. Every organisation you add without R2 credentials writes its customers' files into your production database — silently, with a success message. At 50 users across 4 orgs, if two lack credentials, expect 100–300 MB/month of database growth that belongs in object storage. The Supabase free tier dies in about two months; Pro's 8 GB dies in about two years.

It also costs more than storage. A base64 attachment is dragged through Postgres, the connection pool, Railway's memory and Railway's egress on every read of that task — so one bad row is charged repeatedly, on three meters, forever.

The free tier is disqualified for a reason that has nothing to do with size. It pauses after 7 days of inactivity, and it has no daily backups. For a product with paying customers that is not a cost trade-off, it is an outage and an un-recoverable data loss. Pro at $25/month is required the day you have your first paying customer — but fix the base64 fallback first, or you are buying 8 GB in order to fill it with video.
Staging and production share this database. Test data sits on the same meter as customer data. The E2E organisation's ~5,600 seeded rows are billable, and every migration is a production change.

5. AI, skills and scrapers

The only line item that genuinely scales with users — and the only one already designed to be capped.

MeasuredValueWhat it means
AI calls, 12 Jul → 2 Aug25121 days of real use
Total AI spend$2.15~80% of it is image generation
Average tokens in / out111 / 1,354 Output is 12× input. Prompt caching and RAG will not reduce this bill — the cost is generation, not context. Build the vector layer for answer quality, which is the right reason.
Scraper runs33$1.75 total, ≈ $0.053/run

The credit ledger already built is the correct cap, and it is the right shape: it debits skills, scrapers and generation at the point of use. Three known gaps in it were deferred. Those gaps are now the difference between a bill you set and a bill you receive.

Three hard caps worth adding

  1. A per-org monthly image ceiling, enforced server-side. Images are 80% of AI spend and the only AI cost that scales with headcount.
  2. A price assertion on scrapers. BLOCKED_ACTORS already exists. Add a stored expected cost per actor and refuse any run that exceeds it by more than 2×. A third-party actor silently repriced 21.5× once already and nothing noticed.
  3. Image reuse. Same prompt, same org, return the existing R2 object instead of regenerating.

The $5 Railway budget cannot hold two always-on environments. It can hold one, with staging asleep and WEB_CONCURRENCY trimmed — and that stays true at 50 users, because 50 users cost you about $2 of real compute. Everything above $5 is a decision about environments and image generation, not about growth.

What this does not cover

  • Railway's published rates were applied, not invoiced. The arithmetic is shown so it can be checked against your actual bill. Regional pricing and the Hobby plan's included $5 credit may shift the total.
  • Measurements were taken while two agent swarms were running against the database, which inflates the read load slightly. CPU is so far below its limit that this does not change any conclusion.
  • The 50-user projections are models, not measurements, built from per-resource scaling behaviour. The measured figures — everything about today — are not estimates.
  • Vercel, Resend, R2 and OpenRouter balances were not queried. R2 in particular will grow once the base64 fallback is fixed, because that is where the files should have gone.
