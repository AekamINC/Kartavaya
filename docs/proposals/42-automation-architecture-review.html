2Where 41 is wrong

2.1 · The actor mechanism cannot work, and has already failed here

41 proposed carrying actor and source into the row trigger through SET LOCAL kartavaya.actor. Three facts kill it:

  1. The app connects through PgBouncer. db.py builds the pool against the Supabase pooler on port 6543 with statement_cache_size=0 and a fallback that rewrites the DSN to 5432 — the textbook transaction-pooling setup. Session state is not guaranteed to survive between statements, and which mode is in force depends on whether the primary DSN connected.
  2. Almost every write is autocommit. There are 129 acquire() / transaction() sites in the tree — real ones, in billing and admin — but the ordinary router write is a bare pool.execute(...), its own transaction. SET LOCAL outside a transaction sets nothing and warns.
  3. This was tried before and is dead in the database right now. docs/STAGING_SETUP.md §6 states that every staging table has RLS enabled "with org-isolation policies using current_setting('app.current_org_id')::uuid" — the same session-GUC idea. Measured today: 57 of 234 staging tables have RLS on, and the sampled tables have zero policies. The mechanism was specified, the policies were never created or were dropped, and the document still asserts they exist.

The correction. Keep the row triggers — they need no session state to record what changed. Split the producers honestly:

  • Trigger-sourced events record the delta, the org and the entity. actor_id is current_setting('kartavaya.actor', true), which returns NULL when unset — so the 129 transactional paths can populate it and everything else degrades to NULL instead of to a lie.
  • App-emitted events carry actor and intent, added deliberately at the sites where a rule needs to know who — an approval, an assignment, a stage change.
  • A condition may only reference the actor on an event type that carries one. Same discipline as typed conditions, enforced by the same field registry. This is the rule that stops the task engine's defect being reinvented one layer down.

2.2 · Row triggers on a shared database fire for production too

Production deploys main, 1,144 commits behind, and writes to the same staging schema. A trigger is a property of the table, not of the deployment — so production traffic writes outbox rows from a codebase that has never heard of them, with no actor and no source. That is survivable (the rows simply accumulate) but it must be a stated decision, not a surprise, and the retention rule has to account for the volume. The same point applies to DDL: adding triggers to 33 tables is a migration against the database production uses, in the same class as 128–130.

41's suppression switch for migrations and backfills is therefore not a nicety. A backfill that emitted 759 invoice events would fire every rule in every org at once.

2.3 · Shadow tables: the same table name exists in two schemas, and the empty one wins the lookup

Four Core PM tables exist in both public and staging:

Tablepublicstaging
activity_events1,238 rows, last write 8 Aug0

Core PM refers to all of them unqualified — INSERT INTO activity_events …, INSERT INTO field_values …. DB_SCHEMA=staging is set on the Railway service, and db.py issues SET search_path TO staging, public per connection, which would resolve those names to the empty staging copies. The data says it is not taking effect: the rows are in public and still arriving there.

So the product depends, today, on a schema-routing instruction failing. Restore it — a pooling-mode change, a direct 5432 connection, a DSN options parameter — and Core PM activity, time entries and custom field values silently start writing to empty tables.

Catalogue + row counts + code read. Two mechanisms are in play at once: the SET in db.py:108, and the ?options=-c search_path=… that STAGING_SETUP.md:78 documents on the DSN.

Directly relevant to automation: the task engine's set_field action writes unqualified field_values (automation_engine.py:322) while fields.py reads it unqualified too — so they agree today and would diverge the moment one runs under a different search_path. Every table this engine touches must be schema-qualified, and the shadow copies should be dropped once proven unused.

3.1 · A fifth automation surface, with live endpoints and no engine

staging.varta_auto_replies — trigger_type ∈ {keyword, first_message, off_hours, fallback}, trigger_value, response_type, response_content, template_id, is_active. Specified in MESSAGING-ATTENDANCE-SPEC.md:35.

So the tally is: one engine that works but is deaf (tasks), one that runs and lies (CRM), one honestly closed (Prachar), one silently dead behind live endpoints (Varta), and a drip engine nothing enrols into. Read + measured.

3.2 · The realtime layer is dead where it is wired, and published where it is not

Recommendation, independent of automation: either drop staging.samvada_messages from the publication, or enable RLS with a real policy, before that variable is set anywhere. It is one statement either way.

3.3 · A designed automation that has never existed

design-reference/design_handoff_kartavya_v2/REPORTS_ADDENDUM.md specifies three automated email reports — daily, weekly, monthly — "sent by cron to all admins + team owners of every workspace", with cron expressions in IST, subject lines and Excel filenames. _REQUEST-2026-07-26.md §3.7 asks for the same thing for attendance and notes the backend "already has scheduler.py, report_generator.py, employee_email.py and an OUTBOUND_MODE kill switch, so this is mostly wiring".

Today /cron/reports returns 501 and must never be armed. The specification and the stub have coexisted for weeks. Scheduled reports are one of the clearest wins the time-trigger primitive unlocks, and they are already designed down to the subject line.

3.4 · The competitive research already argued for the triggers this plan proposes

RESEARCH.md is explicit that activity-based selling — "every deal needs a next step", with a "rotting" indicator for deals that sit in a stage too long, configurable by number of days — is the pattern to follow. That is deal_stale: a trigger the CRM builder has offered since it was written, that nothing has ever emitted. The product rationale was written down before the feature was stubbed.

4Governance the docs already impose, that 41 ignored

4.1 · Eight notification kinds, and a hard rule about the ninth

21-notifications-inbox.md defines exactly eight kinds — assigned, mention, comment, approval, approved, rejected, due, support — and states the rule:

Do not add a ninth kind without adding its email template and its row in the preference table — a kind the user cannot switch off is a kind they will mute entirely by disabling notifications.

41 listed "in-app notification" as an action with no constraint on what it may say. An engine that mints notification types per rule breaks this rule at scale and produces exactly the outcome the research warned about: notifications "overwhelming in quantity and hard to curate".

The rule for the engine: an automation notification must resolve to one of the existing kinds. A rule that needs a new kind is a product change — template, preference row, and the map — not a configuration option.

4.2 · Quiet hours exist, are enforced on three paths, and the automation that runs today ignores them

services/push_service.prefs_allow(pool, user_id, kind) reads notification_prefs including quiet_start / quiet_end, and fails open on a database error — careful, tested work, with a dedicated parity suite.

Delivery pathConsults prefs_allow?

task_reminders dispatchyes
reminder_service.process_pending_reminders — the hourly job that produced all 331 reminders no — calls send_email and send_expo_push directly

So the single automation currently running is the single one that bypasses the user's stated preferences and their quiet hours. It has not been noticed because everything it sends is suppressed. Fix this before the engine multiplies the volume, not after.

4.3 · The delivery evidence can go silent permanently

41 proposed that a run row records what outbound_log actually did. Worth knowing what that depends on: migrations/README.md documents that services/outbound_log.py treats a single unexpected column as "the table is not what we were promised" — it sets _dormant, discards its buffer, logs one warning and never writes again for the life of the process. The README is explicit that you must redeploy after touching that table.

An engine that reports delivery from a writer that can quietly stop writing needs the run row to distinguish "suppressed" from "not recorded". Three states, not two.

4.4 · Automations are desktop-only, by decision

Both mobile handovers state it in the same words: "Setup, reporting, automations, time tracking, and project/team management stay on desktop." Consistent with 41 and with the owner's ruling that mobile invoices are read-only. No mobile work in this programme.

4.5 · Who may write a rule

RBAC-SPEC.md puts "manage automations" at the admin tier of the module, alongside views and templates, and project-level owner for project automations. 41's "org owner/admin or module admin" is compatible; this is the citation, and the four-tier model (viewer/editor/approver/admin) is what the gate should read.

5The corrected design, in one page

  1. Outbox staging.org_events. Schema-qualified everywhere. Retention decided up front and added to staging.cleanup_old_data() — the same function 098 flagged as existing in no migration in this repo.
  2. Two producers, honestly labelled. Row triggers for coverage, actor NULL unless a transactional path set it; app emit() for intent and actor at the sites that need it. source on every row so a rule can refuse to fire on migration traffic.
  3. Registry-driven triggers and typed conditions. A trigger nothing emits cannot be listed; a condition the event cannot answer cannot be selected; a condition on the actor is only offered on events that carry one.
  4. Actions call the skills layer, spend through services/credits.py, and declare their config as data. Communication actions resolve to one of the eight notification kinds and pass through prefs_allow — no automation may bypass a user's quiet hours.
  5. Execution: idempotent on (rule, event); wait as a first-class step; stop conditions re-checked before every step; delivered / suppressed / not-recorded as three distinct outcomes; dry run against real past events; per-rule, per-org and global kill switches; a first-run confirmation for any rule whose first tick would touch more than N records.
  6. One page under /automations, module-filtered, with the builder embedded in each module's settings tab. Both existing engines deleted — zero rules to migrate.
