Unicode Group as the full product

Every number below was measured against the live database today, not estimated. Nothing here runs until you say go.

The exercise is not "add more rows to Unicode Group". It is drive the whole product as a person would, in one org, until every screen has something true on it — and then delete the org that was only ever filled by script. Twenty-one tables in Unicode are completely empty today, and they are not obscure ones: WhatsApp, events, sequences, the knowledge base, bank reconciliation, web forms.

1Why by hand and not by INSERT

This is the thing we already agreed and it is worth restating, because it decides the whole shape of the plan. Inserted rows prove the schema accepts them. Only rows created by driving real screens prove the flows work — and a guided session is somebody watching the screens.

The E2E org is the proof. Its 5,600 rows were created by 38 Playwright specs clicking through the product, and that is how we found: e-sign had never produced a signed PDF; order invoices were born fully paid; the reminders cron would have written 254 rows, 190 of them to one hard-bouncing address. Not one of those was visible in the data. They were only visible in the doing.

The measure of scope is elements, not modules. Twelve modules is not twelve units of work — a module is thirty or fifty elements, and "Ganit is done" has never once been true when someone said it. Every table, every column, every form field, every empty state, every filter, every export. Fifty per module is the floor, not the target.

4The plan, in seven phases

PHASE 0 · SAFETY, BEFORE ANY WRITE

  • Confirm the SHA actually deployed on staging matches origin/staging, and that the staging service still tracks the staging branch. It silently tracked main once before.
  • Re-confirm OUTBOUND_MODE=dry on staging by reading outbound_log, not by reading the variable.
  • Snapshot every Unicode row count — the table in §2 becomes the before-picture, so "did this exercise actually create anything" is answerable rather than felt.
  • Take the credit balance and the R2 object count. Both will move and both cost money.

PHASE 1 · REPOINT AND PROVE THE HARNESS

  • Swap .env.e2e for .env.e2e.unicode, keeping the original as .env.e2e.testorg.
  • Run the existing 15 spec files unchanged against Unicode. Expect failures, and expect them to be informative — the specs assert against E2E's data shapes and Unicode's are different. Each failure is either a spec that hardcoded a fixture (fix the spec) or a product behaviour that only works with E2E's data (fix the product). Sorting those two is the first real output.

PHASE 2 · THE 21 EMPTY SURFACES — the highest-value phase

  • One pass per surface in §2's first table, driven through the UI: create a WhatsApp contact and conversation, an event with registrations, a drip sequence with steps, a web form and a submission, a territory, a scoring rule, a custom field, a KB document, a bank statement import, a contract, a regularisation, a scheduled report, a brand profile.
  • Each one answers a question the data cannot: can you actually do this in the product? On past form roughly one in three will turn out to be unreachable, unwired, or 403.

PHASE 3 · DEPTH, ELEMENT BY ELEMENT

  • Module by module, every element: each table's every column, each form's every field, sort, filter, group, paginate, export, the empty state, the error state, the permission-denied state.
  • Target the ratios in §2's second table — not by inserting, by doing. That is 50–70 real operations per module across twelve modules.
  • This is the bulk of the work and it is where the schedule lives.

PHASE 4 · THE CROSS-MODULE JOURNEYS

  • Lead → deal → order → invoice → payment → GSTR-1, as one continuous act by one person.
  • Candidate → employee → salary structure → payroll run → payslip → the payslip actually arriving.
  • Contract → e-sign → signed PDF in R2 → the audit trail.
  • Attendance punch → regularisation → approval → the month's register → payroll consuming it.
  • These are where the eight "backend works, screen renders, nothing joins them" defects have always been found.

PHASE 5 · THE SEND PATHS — only after blocker 2 clears

  • Campaign send, reminders, payslip delivery, e-sign requests, scheduled reports.
  • Every recipient already resolves to @simulator.amazonses.com (migration 105, applied): success+ for most, one bounce+, one complaint+, so the bounce and complaint columns get something real without costing reputation.

PHASE 6 · MOBILE

  • The same org on the Expo app. The parity audit rates mobile diverged, and it just had a crash that took the entire signed-in app down — so this phase is not a formality.
  • Android via EAS preview. iOS is dropped, as settled.

PHASE 7 · RETIRE THE E2E ORG

  • Only once §2's first table reads zero. Then delete 64e7bea6 and its 5,600 rows.
  • Deleting it also releases whatever R2 objects it holds, which is the reason you wanted it gone.

6How we will know it worked

  • The §2 table re-run, side by side. Twenty-one zeroes become non-zero or we say which ones did not and why.
  • A defect ledger, in the shape of the last three — measured, adversarially re-checked before it is believed, with the refuted count stated. Half of every finding set this week has been stale on inspection; that rate should be assumed, not hoped against.
  • Absolute dates on everything. No "yesterday", no "last week".
  • A demo script that walks Unicode Group end to end, so the guided session is a rehearsal rather than an exploration.

7The one decision I need from you

Do the 99 parity findings come before or after this?

They interact. Fourteen of them are blockers and several are exactly the kind of thing this exercise would otherwise re-discover the slow way — onboarding is unreachable, the approval gate has no input, task status has no transition guard, the skills request path does not exist. Driving the product through screens that are known-broken produces findings we already have.

My recommendation: fix the 14 blockers first — they are concentrated and mostly small — then start Phase 0. The other 85 can be fixed as this exercise walks into them, which is cheaper because it walks into them with a reproduction already in hand.

Either way I will not start until you say so.
