Three things the measurement exposed

The RAG index is empty. 60 knowledge-base documents, 0 chunks, 0 embeddings. services/rag.py exists in full — chunking, embedding, hybrid vector search, the lot — and has never indexed a single document. Every "grounded" answer the chatbot has ever given was grounded on nothing. Sixth defect of this exact shape: built, finished, never reached.
Those 74 free GLM calls are the chatbot — on the wrong model chainhub_chat.py:399 passes agent_type="chatbot". The router branches on task == "chatbot", which it is never given, so every chat answer fell through to the English-bulk chain ["glm", "qwen_flash", …] and was served by glm-4.5-air:free. The intended chain — ["gemini", "qwen_plus", …] — has never once been used.
WRONG CHAIN
Web grounding is dead twice overIt only fires when task == "chatbot", so it never fired. And even if it had, ai_router.py:292's success return omits grounding_sources entirely — the key hub_chat.py reads to render citations is dropped before it gets there.
DEAD
90 calls record no tokens at allglm-4.5-air (74) and gemini-2.5-flash-lite (16) log null prompt and completion tokens. Free tiers today, so $0 is right — but the moment either stops being free, the spend is invisible.
BLIND
Latency, not cost, is what a user feelsqwen3.6-flash averages 15.6 seconds and gemini-2.5-pro 37.6 seconds. Nobody waits 37 seconds twice. This is the number a demo audience notices, and no amount of token trimming touches it.
REAL
pgvector 0.8.0 is already installedSo is the schema — hub_kb_documents, hub_kb_chunks with an embedding column. Nothing has to be built from scratch; it has to be connected and filled.
READY

So what actually makes it cheaper

1 · Attack the images, not the tokens80% of spend, and the easiest win in the product: do not regenerate an image that already exists. There are 208 content items with images already made. Reuse, a cheaper default size, and a confirm before a paid regenerate.
2 · Fill the RAG indexNot to save prompt tokens — to make the 60 documents do anything at all, and to stop paying for grounded web search to answer questions the org's own files already answer. This is also exactly the "learns from previous chat" you asked for: the chat writes back into the same index.
3 · Log the tokens nobody is loggingTwo providers, 90 calls, no accounting. Fix before either leaves its free tier, not after.
4 · Then the shared retrieval layerOne index that the chatbot, skills, content generation and scraper enrichment all read. Worth building — as the thing that makes answers BETTER and stops repeated external calls, which is a real saving. Just not a token saving.
The honest summary. Build the vector and retrieval layer — it is the right architecture, it is half-built already, and it is what "learns from previous chats instead of going out to fetch" actually means. But do not expect it to cut the bill much, because the bill is images and the prompts were never the problem.

If cheaper is the goal, the fastest saving in the product is not regenerating an image that already exists — and the most valuable fix is that the knowledge base has been empty this whole time.
