A live defect, found while measuring — the exit-completion guard has never fired

complete_offboarding refuses to close an exit while clearance is outstanding. Its check is:

pending = [c.get("item") for c in clearance if isinstance(c, dict) and not c.get("done")]

That assumes clearance is a list of objects, which is what _DEFAULT_CLEARANCE and migration 083 both specify. Ten of the eleven live rows hold an object instead, identical in every one:

{"hr": false, "finance": false, "it_assets": true}

Iterating a dict yields its keys — three strings. isinstance("hr", dict) is False, so the comprehension is empty, pending is empty, and the refusal never happens. Every one of those ten exits can be completed with nothing ticked. The single row that is correctly an array has 6 items with keys item / owner / done / done_at — exactly as designed.

The frontend is already defensive about this (asClearance() in ExitsTab.jsx returns [] for a non-array), which is why the screen shows “—” rather than crashing, and why nobody noticed. The ten rows look like seed data, not user input. Out of scope for this proposal to fix — but the mirror must not inherit it, which is why the schema below carries a jsonb_typeof CHECK that 083 did not.

1 · The schema

Two tables, mirroring the two that exist. Naming, column order, defaults, nullability and comment style are taken from 083 and 164 rather than chosen: uuid PK defaulting to gen_random_uuid(), uuid org_id and employee_id, text actor columns because users.user_id is text throughout this schema, and no foreign keys to manav_employees — the org_id + employee_id pair is how every other table in this module scopes, and adding FKs on only these two would be inconsistent without being safer. That is 083's argument verbatim and it has not stopped being true.

One migration, not two — and the reason is a house rule

164 had to add its roll-up columns to an existing table with ADD COLUMN IF NOT EXISTS. An inline CHECK on ADD COLUMN IF NOT EXISTS is skipped entirely when the column already exists — the whole clause is, not just the column — so a re-run of a partially-applied migration leaves a column with no constraint, and pg_constraint, not the migration file, is the only honest answer to “is it enforced”.

This design has no such exposure and must keep it that way: everything here is CREATE TABLE, where inline CHECKs are unconditional. The roll-up columns 164 had to bolt on are declared inline from the start. Nothing is ALTERed, so the rule never comes into play.

-- The ledger. One row per THING, not one row per joining.
-- ─────────────────────────────────────────────────────────────────────────────
--
-- 164's argument, mirrored: `checklist` above is the right shape for a firm's
-- own steps ("desk ready", "first-week plan sent"). It is the WRONG shape for
-- provisioning, for the same reason it was wrong for custody — a grant or an
-- issue names a SECOND thing, and the question actually asked later is "who
-- else holds this laptop" or "which joiners are still waiting on IT", which a
-- jsonb blob on one person's row cannot answer without scanning every joining
-- the firm has ever recorded.
CREATE TABLE IF NOT EXISTS staging.manav_onboarding_provisioning (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id          uuid NOT NULL,
    onboarding_id   uuid NOT NULL,
    employee_id     uuid NOT NULL,

    -- THREE verbs where offboarding has two, and the asymmetry is real rather
    -- than sloppy. Custody at exit has exactly two directions: work moves to
    -- somebody (reassign) and access stops (revoke). Joining has those two
    -- inverted — access starts (grant), a thing is handed over (issue) — plus
    -- one with NO exit equivalent: the firm COLLECTS something from the joiner
    -- (a PAN copy, a signed Form 11, a degree certificate). Nobody hands the
    -- firm a document on their way out. Folding 'collect' into 'issue' would
    -- lose the direction, and direction is the whole content of the row.
    action          text NOT NULL,

    -- What kind of thing. Deliberately NOT a foreign key, for 164's reason:
    -- the subjects live across two schemas and key on different types
    -- (staging.manav_assets.id is uuid, staging.user_roles.role_code is text,
    -- staging.hr_documents.id is uuid). An FK would have to pick one and would
    -- then refuse to record the others.
    subject_type    text NOT NULL,

    -- The machine handle: manav_assets.id::text, user_roles.role_code,
    -- hr_documents.id::text. NULL is legal — "the desk by the window" has no
    -- row to point at, and refusing that record is how it ends up in nobody's
    -- notes instead.
    subject_ref     text,

    -- NAMES, NOT IDS. Every reader of this register displays this column and
    -- never subject_ref. A row that cannot be labelled cannot be shown to
    -- anybody, so it is refused at write time rather than rendered as a raw
    -- uuid later. 164's rule, and check-rendered-ids depends on it.
    subject_label   text NOT NULL,

    -- 'issue' only. Both columns, for 164's reason: the id alone renders as an
    -- opaque handle, the name alone cannot be re-resolved later.
    issued_by_user_id text,
    issued_by_name    text,

    -- 'grant' only. `granted_at` is when access actually started, which is NOT
    -- when the row was written: accounts are commonly opened on the joining
    -- day and recorded the following week, and an access-review answer that
    -- reports the recording date understates the window.
    granted_at      timestamptz,
    granted_by      text,

    -- 'collect' only. Points at staging.hr_documents (which exists and holds
    -- 0 rows) when the file has been uploaded; NULL while it is still awaited.
    document_id     uuid,
    due_on          date,

    -- 'pending' is the default because that is what a newly-raised item IS.
    -- 'waived' exists so a firm can close a line honestly — the joiner has no
    -- prior PF account, the role does not need the portal — instead of marking
    -- it done and lying to its own records.
    status          text NOT NULL DEFAULT 'pending',
    waived_reason   text,

    note            text,
    recorded_by     text,
    created_at      timestamptz NOT NULL DEFAULT now(),
    updated_at      timestamptz NOT NULL DEFAULT now(),

    CONSTRAINT manav_onb_prov_action_ck CHECK (action IN (
        'grant', 'issue', 'collect'
    )),
    CONSTRAINT manav_onb_prov_status_ck CHECK (status IN (
        'pending', 'done', 'waived'
    )),
    CONSTRAINT manav_onb_prov_subject_ck CHECK (subject_type IN (
        'account', 'role_grant', 'module_grant', 'team_membership',
        'device', 'asset', 'workspace',
        'statutory_declaration', 'document', 'bank_mandate',
        'training', 'introduction', 'policy_acknowledgement', 'other'
    )),
    -- A grant marked done means a time. "Done" with no timestamp cannot answer
    -- the only question an access review asks, which is when it started.
    CONSTRAINT manav_onb_prov_granted_at_ck CHECK (
        action <> 'grant' OR status <> 'done' OR granted_at IS NOT NULL
    ),
    -- An issue with nobody issuing it is the exact failure this register exists
    -- to prevent: equipment marked handed over, by nobody. Enforced only on
    -- completion, so an item can be raised before IT has picked it up.
    CONSTRAINT manav_onb_prov_issuer_ck CHECK (
        action <> 'issue' OR status <> 'done'
        OR (issued_by_user_id IS NOT NULL OR issued_by_name IS NOT NULL)
    ),
    -- A waiver without a reason is a tick-box. This is the one column that
    -- turns "we decided not to" from an absence into a record.
    CONSTRAINT manav_onb_prov_waived_ck CHECK (
        status <> 'waived' OR waived_reason IS NOT NULL
    )
);

-- One row per (joining, verb, thing). Without this, a service that re-scans on
-- every page open writes a duplicate line per visit. Partial, because
-- subject_ref is legitimately NULL for free-text items and NULLs are distinct
-- in a unique index — those rows must be allowed to repeat rather than
-- silently collapsing into one. 164's reasoning, unchanged.
CREATE UNIQUE INDEX IF NOT EXISTS manav_onb_prov_one_per_subject
    ON staging.manav_onboarding_provisioning
       (org_id, onboarding_id, action, subject_type, subject_ref)
    WHERE subject_ref IS NOT NULL;

CREATE INDEX IF NOT EXISTS idx_manav_onb_prov_onb
    ON staging.manav_onboarding_provisioning (org_id, onboarding_id);

-- "What is still open on this joiner" — the query the whole module exists for.
CREATE INDEX IF NOT EXISTS idx_manav_onb_prov_pending
    ON staging.manav_onboarding_provisioning (org_id, employee_id)
    WHERE status = 'pending';

COMMENT ON TABLE staging.manav_onboarding IS
    'One row per joining: dates, probation, the checklist and confirmation. The mirror of manav_offboarding.';
COMMENT ON TABLE staging.manav_onboarding_provisioning IS
    'One row per thing a joiner is given or must hand over: grants (with the time access started), issues (with a named issuer) and collections. subject_label is the display field; subject_ref is a machine handle and is never rendered.';
COMMENT ON COLUMN staging.manav_onboarding.provisioning_scanned_at IS
    'When provisioning was last scanned. NULL distinguishes "never checked" from "nothing outstanding".';
COMMENT ON COLUMN staging.manav_onboarding.buddy_employee_id IS
    'Chosen by a human. NOT derived from manav_employees.reporting_to, which is unwritten on all 98 live rows.';

2 · The checklist model — why both shapes, and which is which

Offboarding already answered this question twice and gave two different answers, correctly. 083 put the clearance list in jsonb; 164 put custody in a real table and spent a paragraph explaining why it was not more jsonb. Onboarding takes the same split, drawn on the same line, and invents no third pattern.

jsonb checklist

Steps that are a tick. One subject, one owner, one boolean. Nobody will ever query across joinings for them.

  • Desk and seating ready
  • Buddy assigned and introduced
  • First-week plan shared
  • Team introduction done
  • Payroll set up
  • Induction / policy walkthrough

..._provisioning rows

Things that name a second party or need querying from the other end.

  • Accounts & access (grant — needs the time it started)
  • Equipment (issue — needs who handed it over; 70 of 100 assets are already assigned)
  • Documents (collect — lands in hr_documents)
  • Statutory declarations (collect — Form 11, Form 2, PAN, previous-employer Form 16)

The test that decides which side an item falls on

Does anybody ever ask this question from the other direction?

“Which joiners are still waiting on an IT account” and “who issued this laptop” are asked from the other direction. “Was the desk ready” is not. 164 put it as: “what did Iyer inherit” is a question a jsonb blob on Sharma's row cannot answer without scanning every exit the firm has ever recorded. The joining-side form of that sentence is “what is IT still owed, across everybody who started this month”.

The two are not alternatives and the roll-up columns are the seam: access_granted_at, equipment_issued_at and documents_collected_at summarise the ledger onto the joining row so “is this joining safe to close” is one query. They are a summary, never a substitute — the ledger says WHICH account, these say whether all of it is done. Exactly 164's relationship between manav_offboarding_custody and the six columns it added.

The default checklist

The mirror of _DEFAULT_CLEARANCE in routers/manav.py:1837, same shape, same owner vocabulary, and it goes in the router beside it rather than in the migration — 083 seeds nothing and neither does 195.

The jsonb tick is never the source of truth for anything the ledger covers; /complete reads the ledger.

The isinstance is a refusal, not a coercion. A silent [] is exactly how the exit guard became decoration; a 500 that names the row is how a bad container gets fixed instead of tolerated. Where it hooks into create_employee

create_employee (:1056) already runs an INSERT and employee_joined in one transaction, on the stated principle that the event exists iff the personnel file does. The onboarding row joins that transaction, on the same principle: a joining record that can be absent for a person who has joined is the same defect offboarding had before 083.

async with pool.acquire() as _conn:
    async with _conn.transaction():
        row = await _conn.fetchrow("INSERT INTO staging.manav_employees … RETURNING *", …)

        # NEW — third statement in the existing transaction.
        # date_of_joining is the planned date; §1 explains why it is copied
        # rather than joined. Every one of the 98 live employees has one.
        await _conn.execute(
            "INSERT INTO staging.manav_onboarding "
            "(org_id, employee_id, joining_type, joining_date, checklist, initiated_by) "
            "VALUES ($1::uuid, $2::uuid, 'new_hire', $3::date, $4, $5)",
            org_id, row["id"], row["date_of_joining"],
            _DEFAULT_ONBOARDING, user["user_id"])

        await employee_joined(_conn, org_id=org_id, actor_id=user["user_id"],
                              employee_id=row["id"], row=dict(row))

The invitation stays exactly where it is — outside the transaction, after the commit, non-fatal. That placement is argued at length in the existing comment and none of its reasons change: public.invites is read by the login path, and holding an HR transaction open across an SMTP call means a slow mail server locking a personnel table.

The response gains nothing. create_employee returns {status, id, name, employee_code} plus an optional invite key, and the comment there is explicit that RETURNING * must not widen what leaves the API. An onboarding key would be a key that is always present and usually says nothing — the same argument that made invite absent rather than null.

The 98 employees who already exist

None of them gets a row from the hook, because they were created before it. Two doors, and no backfill migration:

  • POST /v1/manav/onboarding is the manual door — an admin starts a record for anyone, including someone who joined in 2019. The unique partial index is the only thing that can refuse it.
  • The Joiners tab offers “14 people joined in the last 90 days and have no onboarding record” as a one-click seed, exactly as the Exits tab filters out people who already have a live exit. Opt-in per person, because a record seeded for someone who joined in 2019 is 10 unticked boxes nobody will ever tick, and a checklist that starts wrong is worse than no checklist.

Niyam

employee.joined already exists and already fires — it is emitted from the INSERT and 2 events have been recorded. It stays exactly as it is; the onboarding row is a sibling of the event, not a consumer of it.

Add employee.onboarded to services/niyam/subjects.py, the mirror of employee_exited (:885) which is emitted at completion and not initiation for the reason its docstring gives — someone serving notice has not exited. Someone in their first week has not been onboarded. Carry joining_type off the onboarding row (its CHECK is the vocabulary, passed by the caller since the employee row does not hold it), plus department and designation and nothing else — PAN, Aadhaar and bank details must never be event material, which employee_joined's docstring already states.

Measured, and it changes what to promise: there are 8 armed Niyam rules in the database and not one is on any employee event (they are on task.status_changed ×2, task.created, task.overdue, invoice.overdue, report.due, contact.stale, lead.converted). Proposal 39's line — “Employee joins → create the onboarding checklist” — describes an automation that fires for nobody today. That is the argument for the hook above being a direct write rather than a rule: the record must exist because the employee exists, not because somebody remembered to arm something.

The rules the screen must not break

  • Names, not IDs. The row shows employee_name and employee_code from the server join, the buddy by name, the issuer by issued_by_name, and every ledger line by subject_label. subject_ref is never rendered — it exists to be passed back, not shown. check-rendered-ids.mjs is positional, so an id must not reach a text position at all.
  • --row-h. The table sits on the token like every other; the expanded panel is a sibling <tr>, which is how ExitsTab does it, so the row contract is not violated by a variable-height cell.
  • The employee picker excludes anyone who already has a live record — ExitsTab's leaving Set, mirrored. Offering a name that will 409 is a form that knows better than it behaves.
  • The form says what it does not do. ExitsTab's create form carries a paragraph explaining that starting an exit does not remove anyone. The mirror: “This starts the checklist. It does not create a login — invite them from the employee record or Settings → Members.” The two are genuinely separate and the screen should stop people assuming otherwise.

5 · execute_onboarding — replace it

Read in full at backend/services/skills/action/onboarding_chain.py (83 lines). It is registered in skill_dispatcher.py:393, listed in modules.py:367 as needing manav + vetana, and pinned by three tests. It has never run.

#FindingSeverity
1 It is a report wearing an action's name. Of its five steps, four only CHECK whether something is already true and then append the label to steps_completed. It provisions nothing, assigns nothing and creates nothing. A firm reading five ticks would believe five things were done. fatal
2 completed.append("allocate_assets") is unconditional — the comment says “just log, actual allocation is manual” and there is no log. That step reports success for every employee, always, including one who was given nothing. fatal
3 Step 2 queries staging.user_roles WHERE user_id = $1::uuid but binds manav_employees.user_id, which is TEXT — and users.user_id is text throughout this schema, which is why every actor column in 083 is text. A non-uuid handle raises. It is unobserved only because 2 of 98 employees have a user_id at all, so 96 of them skip the branch. bug
4 It calls send_email synchronously from inside an async skill. Its own comment records that the await raised once and "welcome_email" was silently never recorded. smell
5 The welcome-mail template hand-writes its markup and never passes through _base(), where the product's escaping lives — one of the nine preview_emails.py flags. The body escapes correctly; the pattern does not follow the email_service.py choke points. smell
6 Unreachable. 78 skill templates exist; 3 carry module='manav'; none names execute_onboarding in its steps[].skill_function. Measured against the live catalog 2026-08-22, not read off a migration. dead

Verdict: the module does not call it, and no template is seeded for it as written

Do not call it. A module whose whole value is an honest record of what was done cannot delegate to a function that reports success for work it did not do. Point 2 alone disqualifies it, and it is not a bug that can be patched out — there is no allocation for that step to perform, because allocation is manav_assets.assigned_to and a provisioning row.

Do not seed a template for it either. Seeding is the one thing that would make it reachable, and the first time it ran it would email a joiner and return four false ticks.

Rewrite it in place, keeping the name. The name is load-bearing in three test files (test_every_skill.py:123 pins its required argument as employee_id; test_a_skill_can_run_unattended.py:56 lists it as needing to be told which employee; modules.py:367 pins its module set) and renaming it churns all three for nothing. Re-point the body at staging.manav_onboarding so it answers “what is outstanding on this joining” — a read, no mail, no writes — and only then seed a template. The vetana entry in modules.py stays honest, because salary_structure_id is one of the things it reports on.

manav_onboarding_checklist must stay a ghost

It is one of the seventeen names in GHOSTS_OF_059 (tests/test_every_skill.py:231), a documented function that was never written. The test asserts that frozenset is exactly equal — “if it has been edited, the exclusion needs rewriting rather than extending”. Implementing it, or adding the new module's function to that set, breaks the assertion in both directions. It has nothing to do with this design and should be left alone.

6 · The two moments the owner named

“Onboarding missing on invite and new employee.” Two moments, two different people, and only one of them is fixed by everything above.

Moment one — the admin, adding an employee

Today: fill the form, tick create login or not, press save. One row is written, one Niyam event fires, and if the box was ticked one email goes out. Then nothing at all. There is no list of what is owed, nobody is told, and the 13 employees with no salary structure are invisible. Sections 1–4 are the whole answer to this moment.

Moment two — the joiner, following the link

What the joiner sees today, in full

/accept-invite?token=… → a preview of the invitation (org name, inviter) → two fields, name and password → submit → a toast reading “Welcome to Kartavaya!” → navigate('/dashboard').

That is the entire joining experience. The dashboard of an established firm is somebody else's board, somebody else's tasks, and a sidebar of modules they may or may not have been granted. Nothing tells them what they are expected to do, nothing tells them who their buddy is, and nothing collects the PAN copy HR is waiting on.

Measured: 37 invites, 20 accepted, and exactly one carries an employee_id (migration 187 is recent). 2 of 98 employees have a linked login at all.

OnboardingChecklist.jsx is not the answer, and cannot be made into one

It is the org's setup guide, not a person's: its four steps are create your first project, invite a team member, add your first task, name your organisation. Derived live from /teams, /users and /tasks — org-wide counts, nothing about the viewer.

For anyone joining an established firm all four are already true on the first render. allDone becomes true, the effect at :123 calls dismiss(), and the card removes itself before it has been read. Its state also lives in localStorage under kartavya_onboarding — per browser, so it is not a record of anything either.

It is also the component that once crashed the entire product for every new customer at the exact moment they finished setup (a dismiss() effect below an early return → “Rendered fewer hooks than expected”). It is mounted by AppShell outside the page ErrorBoundary. Leave it alone.

What should exist: /welcome

A first-run route, reached from AcceptInvitePage's submit handler instead of /dashboard — only when the accepted invite carried an employee_id. That column exists (migration 187) and is exactly the signal: an invite with one is a joiner, an invite without one is a colleague being given access. The existing branch already discriminates (data.user?.role === 'client' ? '/client' : '/dashboard'); this adds a third arm and changes nothing else.

The page showsSourceWhy only this

Uploads land in staging.hr_documents (0 rows, correct shape) with the file in R2 — no file bytes in any column, ever. The provisioning row's document_id then points at it and the item closes itself.

The gate is a real one: the joiner is not an HR admin. This page must not go through _gate at admin. It is the require_module_or_self case the dependency is named for — a person reading their own record, the same door that lets an employee see their own HR row and nothing else. A dedicated GET /v1/manav/onboarding/me that resolves the employee from the caller's own user_id and never takes an id from the URL is the safe shape.

And it reaches almost nobody until the linking problem is solved. 2 of 98 employees have a login; the largest org has 71 employees and 0 links. Everything in this section is correct and will be invisible for most of the register. That is an argument for building moment one first, not an argument against moment two — but the sequencing should be honest.

7 · Risks

Staging and production share one Supabase database. Migration 195 runs against live rows in two real organisations.

OperationEffect on live dataRisk
2 × CREATE TABLE IF NOT EXISTS Catalog-only. No existing table is read, locked, rewritten or touched. A new table cannot conflict with a running query because nothing references it yet. none
7 × CREATE INDEX IF NOT EXISTS On the two new, empty tables. Instant. CONCURRENTLY is deliberately not used — it cannot run inside the transaction block the SET LOCALs require, and on an empty table it buys nothing. none
ALTER TABLE None. Unlike 164, nothing existing is modified — so the lock-queue hazard 164 had to cap with lock_timeout does not arise at all. The timeouts are kept anyway, as house style and as a floor. none
INSERT / UPDATE / DELETE / DROP None. No seed data, so a second run cannot restate a fact a human has since corrected. none
Running it twice Nothing happens. Every statement is IF NOT EXISTS and there is no ADD COLUMN, so the inline-CHECK-skipping rule never applies. Re-running is free. none
The create_employee hook This, not the DDL, is the only real write-path change. It adds a third statement to a transaction that today writes a personnel row and an event. An INSERT that fails now fails the hire. contained
Why it is contained: the only constraint that can refuse that INSERT is manav_onboarding_one_live_per_employee, and it cannot collide — the employee_id was generated by the statement immediately above and no other row can hold it. The checklist CHECK cannot fire on a server-side constant. joining_date is nullable and date_of_joining is already validated upstream. If the belt-and-braces position is wanted, the INSERT can go after the commit alongside the invitation — but then a joining record can be absent for a person who has joined, which is the exact defect 083 was written to end.
Production reading these tables Production runs main, which is far behind staging and has no code referencing either table. It sees two tables it never queries. Confirm meta.branch before trusting any live probe of the deployed behaviour — staging has silently tracked main before. none
The 10 malformed clearance rows Not touched by this migration. Fixing them is a separate data-repair decision on production rows and needs its own risk report and its own approval. Named here so it is not lost. out of scope
