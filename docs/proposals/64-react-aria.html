React Aria for Kartavya

Proposal 64 · 17 August 2026 · accessibility of the interactive primitives
Status, 17 Aug 2026: fixed by hand. React Aria not adopted — and no longer needed for this. Everything below was written to make the case for the library. It was then cheaper to close the defects directly: Picker, Menu and Tooltip are fixed, and keyboardA11y.test.jsx — 7 tests, committed failing before any fix — now holds them. The page is kept because the evidence and the demos are still the clearest statement of what these controls owe a keyboard user. The calendar is now fixed too — and the fix removed a whole duplicate calendar with it: PickerDate and DateInput carried byte-identical month markup, and both now render one CalendarGrid. Nothing on this page is outstanding.
The original recommendation: yes, but only for four components — not as a UI framework. React Aria ships behaviour, not appearance. Adopting it does not touch editorial.css, the k-* classes, or a single pixel of the design. It replaces the keyboard and screen-reader logic inside Picker, Menu, modal and Tooltip — where the build currently has real, reproducible holes — and leaves everything else alone. Cost is roughly 18–26 KB gzipped and about a week of work.

01 What is actually wrong today

Measured against the components in frontend/src/components/ui/, not against a general worry about accessibility.

ComponentWhat it declaresWhat it doesVerdict
Picker.jsx
345 lines		 role="listbox" with role="option" rows, aria-selected, aria-multiselectable Correction. The first draft of this page said “zero keyboard handling”. Wrong: usePicker carries a document-level keydown listener with Arrow/Home/End/Enter, which a grep for onKeyDown does not find. What was really missing: the trigger never opened on Down/Up, so that handler was unreachable; nothing took focus and there was no aria-activedescendant, so the cursor was a CSS class announced to nobody; no typeahead; the cursor opened at row 0 instead of on the current value; and Tab walked the options one by one instead of leaving. fixed
Tooltip.jsx
230 lines		 role="tooltip" on the bubble The trigger has no aria-describedby, so nothing links the bubble to the control. A screen reader never reads it — the text is visual-only. Fixed: the child is cloned to carry aria-describedby, and focus now opens with no dwell, because a description arriving 300ms after focus has already missed the announcement it was part of. fixed
Menu.jsx Arrow keys, Home/End, Escape, focus return — all deliberately written The cursor counts enabled rows but focuses the nth rendered row, so any menu with a disabled item above the cursor lands on the wrong entry. Also no typeahead, and no collision flip — a row menu near the bottom of a long table opens off-screen. Fixed: the focus lookup now filters :not([disabled]) so it indexes the same list the cursor counts, and the panel measures itself after mount and opens upward when it would otherwise run past the fold. Live in 8 call sites including KanbanView, MemberTable and Sanvaad's Message. fixed
PickerDate / calendar role="grid" No role="row"/gridcell, and no arrow-key date navigation. A grid you cannot walk is not a grid. Fixed: real rows, column headers and gridcells; a roving tabindex so the month is one tab stop instead of 42; arrows moving a day sideways and a WEEK vertically; Home/End across the week, PageUp/PageDown across months (clamped, so the 31st does not roll past February); and every cell named “Monday, 17 August 2026” rather than “17”. fixed
Native <select> — 181 uses — Fully accessible for free. Do not touch these. fine

Scale of the surface: 70 aria-expanded attributes and 32 role="dialog" across 507 JSX files, against only 81 onKeyDown handlers in the whole frontend. Most custom disclosure widgets in this app open with a mouse and close with a mouse, and that is their entire keyboard story.

05 What it costs

ConcernAnswer
Does it change the look? No. React Aria hooks return prop objects — {...triggerProps}. You keep your own elements and your own classes. This is the reason to pick it over Radix, MUI or Spectrum: those bring markup and styling opinions, and this design system already won that argument.
Bundle≈18–26 KB gz for the four hooks + their state packages. Tree-shaken per hook; not the whole library.
Effort Picker ~2 days (it is the largest, and the only one that is genuinely broken), Menu ~1 day, modal ~0.5 day, Tooltip ~0.5 day, plus regression passes. ~1 week.
Blast radius Small — these primitives are barely adopted: 5 <Picker> call sites, 6 <Tooltip>, 2 <Tabs>. Fixing them now is cheap; fixing them after the rest of the app migrates onto them is not.
Mobile Out of scope. React Aria is DOM-only; the Expo app is untouched.
What we lose Some of the careful hand-written behaviour in Menu.jsx — the exit animation tied to the user's Animations preference — has to be re-attached on top of the hooks. It survives, but it is re-work, and it is the main argument for doing Menu last.

06 Plan

  1. Ship a failing check first. Add an axe pass to the vitest run and a Playwright keyboard spec that opens a Picker and selects an option using only keys. It fails today. That is the point — the gate proves the bug before the fix claims to close it.
  2. Picker — useSelect, useListBox, useComboBox for the searchable variant. Highest value: it is the only primitive that is outright unusable by keyboard.
  3. Tooltip — useTooltipTrigger. Half a day, and it makes six existing labels audible for the first time.
  4. modal / ConfirmDialog — useDialog + useModal, replacing the hand-rolled FocusTrap.
  5. Menu — last, because it is the one that already works and has the most bespoke motion to preserve. Fix the disabled-index bug immediately regardless; it is a four-line change and should not wait for a library decision.
  6. Leave alone: the 181 native <select>, DateInput (deliberate, replaces the native date input), tables, and everything in mobile/.
