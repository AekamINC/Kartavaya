The finding that reframes the inbox

Nearly half the task table was written by test accounts. 351 of 736 tasks were created by a Playwright or QA login. Two of those logins hold real user_roles in Unicode Group, a live organisation, and five hold active memberships in its projects. One is an admin of “Keval To Do” and authored 13 of its 39 tasks.

This is why the email you received looked like a leak and was not one: the test account was a genuine member, so every fan-out correctly included it. The bug was that the fan-out went to everyone; the test accounts merely made it visible.

Consequence for this scope: several inbox items describe symptoms of polluted data rather than broken code. Cleaning first retires some of the list without a line being written, and stops me diagnosing ghosts through six other workstreams.

Storage — two bugs found after this scope was first written

Test connection fails on credentials that work. verify_r2_credentials tests by calling list_buckets, which is an account-level permission. An R2 API token scoped to a single bucket — the least-privilege setup Cloudflare recommends — cannot list buckets and is rejected, though it can read and write that bucket perfectly. It also never tests the bucket at all: R2Credentials carries bucket_name and the verifier is called with three of its four fields. This is what blocked the new org.

The org id is written twice. pahchan.py:467 builds pahchan/{org_id}/punch, and on the platform bucket the resolver prepends org/{org_id}/ as well. Harmless to reads, but no other caller does it.

Beyond the bugs, the keys have four different grammars, no date partition, no entity id on any eSign file, and discard the original filename — so a bucket cannot answer “show me the files for this agreement” without the database. Proposal 83 has the full flow, the proposed single grammar, and a sketch of the Storage tab.

5 · Two-factor authentication

It is not built, and the settings screen already admits it

Verified from four directions today:

  • TabSecurity.jsx renders both toggles as <Toggle checked={false} disabled />, and its own copy says the product has no two-factor flow to enforce.
  • auth_router.py — zero matches for TOTP, MFA, two-factor or authenticator.
  • Neither staging.user_totp nor staging.user_mfa_factors exists.
  • Migration 081 records it in as many words: MFA not shipped.

auth.mfa_factors does exist in the database, but Supabase creates that table in every project whether or not it is used. It is not evidence of a feature.

The fact that sets the size: this authentication is ours, not Supabase’s

auth_router.py:1092 verifies a password against our own password_hash and salt and issues our own JWT. Login does not pass through Supabase Auth.

So this cannot be enabled — every part of it has to be built: enrolment, secret storage, the challenge step in login, recovery codes, and the reset path for someone who loses their phone. That is why it is sized large rather than medium.

Your rule, applied: optional for the org, but available

Same shape as every compliance setting in proposal 80 — nothing is mandatory unless a firm ticks the box. Two org-level settings, both off by default, and the second only reachable once the first is on:

SettingDefaultMeaning
Allow two-factor authenticationoff Members may add an authenticator app to their own account. Opt-in, per person — which is exactly what the disabled toggle already promises today.
Require two-factor authenticationoff Every member must enrol. Only settable while “allow” is on, and it needs a grace period — switching it on must not lock out the firm’s whole staff at nine on a Monday.

What the build contains

PieceNote
Enrolment table — secret, confirmed_at, last_used_at The secret is a credential: encrypted at rest, and never returned by any endpoint after enrolment.
Enrol flow — QR plus a typed fallback A first correct code must be verified before the factor activates, or a mistyped secret locks the person out immediately.
The challenge step in login The one genuinely delicate change: password success must yield a short-lived partial token that can do nothing except answer the challenge.
Recovery codes Hashed, single-use, shown once. Without these, a lost phone is a support ticket that only god mode can close.
Admin reset An org admin clears a member’s factor — and that action must be written to the audit trail, because it is a way to take over an account.
Rate limiting Login is 5/min today. The verify step needs its own limit, keyed on the last X-Forwarded-For entry — the proxy-counting bug is already recorded.
Enable the two toggles TabSecurity.jsx is already written and waiting; today it only lacks something true to switch.
Mobile needs a build for this too — the login screen has to handle a challenge step it has never seen.

3 · Does updated_by justify ~90 tables? My answer: no

Measured: of 301 base tables, 109 carry updated_at, 81 carry a created_by, and exactly 2 carry updated_by.

The reason not to sweep is not cost, it is truth. A column arrives in one migration; the write paths that populate it land one module at a time. In between you have a column that is NULL on almost every row — and a blank updated_by reads as “nobody has edited this”, which is a claim, not an absence. That is worse than not having the column, because someone will eventually settle an argument with it. The 81 tables that already carry created_by and never render it are the same lesson, already paid for once.

So: add updated_by where an edit is actually disputed — invoices, tasks, clients and companies, employees, payroll, purchase orders, quotes, orders. Roughly 12–18 tables, each in the same commit as the write path that fills it and the column that shows it. Not one migration; one per module, as that module is touched.

4 · The derived Sales customer — the question dissolves

I framed this as a choice between three dates. Checking the schema, there is no choice to make: a Sales customer is a graha_clients row, and that row already carries created_at, created_by and updated_at. Nothing is derived about its provenance — only its customer-ness is derived, from whether an order points at it.

So, per your instruction — customer, client and company show created by and modified by, with the date carried for the log even though it is not the point:

  • created_by already exists on graha_clients, crm_contacts and vikray_orders. It only needs rendering.
  • updated_by exists on none of them and must be added — three or four tables, which is exactly the targeted approach argued above rather than the 90-table sweep.
  • ganit_vendors is the outlier: it has created_at and nothing else.
