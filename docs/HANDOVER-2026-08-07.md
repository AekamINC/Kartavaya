## 5. Traps worth knowing before touching anything

**The search_path does not survive PgBouncer.** `db._init_conn` issues
`SET search_path TO staging, public`, but staging connects through PgBouncer on
port 6543 in transaction pooling mode, where a session-level SET does not survive
the connection returning to the pool. **Unqualified names resolve to `public`.**
Measured: `public.notifications` holds 1,259 rows, `staging.notifications` holds
1. Always schema-qualify a staging-only table.
`backend/tests/test_cron_column_names.py` now fails on any unqualified one.

**`npm run check` is a single `&&` chain.** One undeclared token failed
`check-tokens` and **the six checkers behind it never ran at all**, hiding two
contrast failures, an unstyled empty state and a write-gate result. When it
fails, fix the first failure and run it again — do not assume the rest are clean.

**One `staging` schema, and production writes to it too.** Every migration is a
production change.

**`railway run -e staging -s Kartavya --` reaches the live DB and R2 from this
machine.** An older note said asyncpg could not connect; that is wrong and cost
real effort. The CLI defaults to the **production** environment — always pass
`-e staging`. Write the script to a FILE; `railway run` swallows stdout from some
multi-line `python -c` invocations.

**A dead workflow does not mean lost work.** When the A/B/C + Wave 3 swarm died,
9 of 10 agents never reported — and every edit was on disk. Assess the tree; do
not re-run the swarm.
